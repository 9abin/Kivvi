## 요약
후보 풀(문항당 62.5개, 정답 91개 중 89개 포함)을 사람이 읽을 수준으로 줄이는 방법을 개발 100에서 같은 후보 · 같은 정답으로 비교했다. **출처별 분리(규칙 후보 = 판단 모델, RAG 후보 = Luna 목록 리랭킹, 7번)가 정답 89개를 모두 5.7개 목록에 남겼다.** 안 거른 순서보다 Recall@10이 +0.176(구간 +0.093 ~ +0.260) 높고 정밀도는 0.014 → 0.156이다. 유사도 리랭커는 안 거른 순서보다 순위가 나빴고, 한 가지 방법으로 모든 후보를 거르면 목록이 길거나(판단 모델 18.1개) 정답을 잃는다(Luna 단독 14개).

## 설정
- 정답: 개발 100(v2), 정답 91개 · 정답 있는 문항 55 · 정답 0개 문항 45. 후보 풀: 문항당 62.5개, 정답 89 / 91 포함.
- 규칙 후보 판단 모델 문턱 0.7(확정급 · 정의 변경 USES_TERM은 항상 남김). 규칙 후보 점수는 현재 코드(입력 자르기 · 단계 설명, 리포트 97)로 다시 채점한 값이다. LLM은 후보 순서를 섞어 두 번 묻고 합친다. Luna = gpt-5.6-luna.

## 해석
- **7번이 균형이 가장 좋다.** 후보 풀의 정답 89개를 하나도 잃지 않고 5.7개로 줄였다. 안 거름 대비 정밀도 0.014 → 0.156, Context Precision 0.329 → 0.438, Recall@10 +0.176이다.
- **유사도 리랭커는 쓰지 않는다.** 모든 순위 지표가 안 거른 순서보다 나쁘다(Recall@10 −0.198). 후보가 이미 유사해서 가져온 것이라 유사도로는 가려지지 않는다.
- **판단 모델 단독(3)은 정답을 거의 안 놓치지만 목록이 길다.** 정답 4개만 잃었고(0.934) 정답 0개 문항에서도 17.3개를 낸다.
- **RAG 후보를 로컬 Gemma로 거르면(6) 정답 8개를 더 잃는다.** 7번의 Luna를 Gemma로 바꾸면 최종 재현율이 0.978 → 0.890(차이 구간 −0.163 ~ −0.029), 목록은 5.7 → 6.8개다. 외부 API 없이 돌릴 수 있지만 문항당 68.2초가 든다. Gemma 단독(4)은 0.725라, 출처별로 나누는 구조가 로컬 모델의 손실도 줄인다.
- **Luna 단독(5)은 정밀도가 가장 높지만 정답 14개를 잃는다.** 최종 재현율이 7번보다 0.154 낮다. 규칙 후보(확정급 포함)까지 LLM이 고르게 하면 근거가 확실한 후보도 빠진다. 출처별로 나누는 이유다.

## 한계와 주의
- **seed 0 한 번이다.** 7번의 최종 재현율 0.978은 리포트 97의 0.945 · 0.967(seed 0 · 1)보다 높다. 변동 범위를 보려면 seed 1 · 2가 필요하다.
- **7번이 유리하다.** 문턱 0.7 · LLM 프롬프트 · 후보 개수를 개발 100으로 정한 설정이고 다른 방법은 기본 설정이다. 최종 점수는 시험 100에서 고른 구성 하나로 한 번만 낸다.
- **판단 모델 점수 정정.** 처음 실행에서 낡은 규칙 후보 점수 파일(11월 12일 16:17, 팀의 입력 자르기 · 단계 설명 수정 전)을 써서, 현재 코드로 다시 채점하고 3 · 7번을 다시 계산했다. 팀의 Luna 선택에 새 점수를 얹으면 팀이 적은 값(개발 0.934, 시험 0.900)이 그대로 재현된다.
- **정답은 AI 초안이다**(현업 검수 전). 후보 풀에 없는 정답 2개는 검색 단계의 한계라 모든 방법에 공통이다.
- **Luna는 외부 API다.** 규정 원문과 후보 조문이 외부로 전송된다. 작업 규칙(내부망 · 로컬 LLM)과의 관계는 배포 전에 정한다.
- **로컬 LLM 결과는 4비트 모델 한 번 실행이다.** 4 · 6번 모두 Gemma 4 12B-it(4비트)로 seed 0 한 번만 돌렸다.
