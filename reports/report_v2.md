# 진행 기록 v2: 기능 2 먼저 (2026-11-06 방향 전환)

기능 1(기존 오류 탐지) 기록은 `reports/report_v1.md`에 있다. 이 문서는 기능 2(조항을 고치거나 지우거나 더할 때 영향 가는 곳을 알려 주기)를 먼저 하기로 한 이후의 기록이다.

## 1. 결정

- 기능 1은 여기서 일시 중단하고 기능 2를 먼저 한다.
- 이유(사용자 판단): 이 서비스가 줄 가치는 "조항을 수정·삭제·추가하면 어디에 영향이 가는가"를 알려 주는 것이다. 기능 2에서 조항 사이의 관계를 만들어 두면, 오류 탐지(기능 1)는 그 관계 위에 나중에 얹을 수 있다.
- 기능 1은 지운 것이 아니라 멈춘 것이다. 1차 결과(아래 §2)는 그대로 쓴다.

## 3. 기능 2의 현재 위치

팀이 이미 만들어 둔 것(PR #11, #12, 지표 요약 `261106-1500-83-metrics-summary.md`):

- 조항 관계 그래프: 노드 3,503, 선 13,040, 관계 18종. 개정 종류 8가지별 경로표.
- 후보 수집 → 단계 나누기 → 판단 표시 → 사람이 결정. 후보를 확정하거나 충돌을 판정하지 않음.
- PR #12: 가상 개정 120문항 평가(RAG 77/120, 도메인 그래프 + RAG 88/120). 인사·보수·휴가·휴직 4개 영역, 실제 개정 대상 9개 문서.

팀 지표의 한계(문서가 스스로 밝힌 것):

- 정답이 전부 AI 초안이고 현업 확인이 0건(근거 등급 U).
- 후보 찾기는 규칙을 조정한 묶음에서 92~95%였으나 처음 보는 5차에서 18/31(58%). 정의 형식을 고친 뒤 25/31(81%)이나 이는 놓친 정답을 보고 고친 개발 수준 수치. 6차 49/50은 정답이 정의 변경 3문항에 몰림.
- 순서 정렬의 개선(판단 모델, 그래프 재정렬)은 새 문항에서 확인되지 않음.
- 알려진 빈틈: 위임받은 규정의 하위 조·별표, 법령 조 단위 노드, 표현 수정 후보.

우리가 기능 2에 더할 수 있는 것:

1. 기준선: 개정 전 이미 있던 문제 목록(`final_errors_v2.csv`). "변경과 무관한 기존 문제는 보고하지 마라"를 실제로 지키려면 필요.
2. 번호·인용 차이를 코드로 계산하는 부분(개정 전후 상태에 번호·인용 검사를 돌려 비교). 단, 팀의 `src/regcheck/change_check.py`가 이미 비슷한 점검(깨지는 인용 99.6%)을 하므로 **중복 확인이 먼저**다.
3. 법령 DB 대조(법령이 바뀔 때·법령 인용이 걸린 개정): 팀 그래프는 법령을 이름 단위 노드로만 가짐.
4. 검증된 충돌 목록: 팀 규칙(COUNT-01, AUTH-01, VALUE_DIFF, DEF_DIFF 등)의 정밀도는 표본이 1~5건이라 측정 못 했음. 우리 충돌 판정 23건 안팎이 정답으로 쓰일 수 있음.
5. 정답 라벨 검증: 팀 정답의 일부를 사람 확인표 방식으로 확인.

## 6. 기능 2의 입력과 출력 정의 (2026-11-06 정리)

시나리오: 내부 규정의 어떤 문서의 어떤 조를 수정하는 이벤트가 생긴다. 그 수정이 영향을 주는 것, 곧 충돌이 새로 생기거나 기존 인용 관계가 깨지는 곳을 찾아야 한다. 유사도와 그래프로 탐색한다.

1. **입력.** "어느 조를 어떻게 바꾸는가". 조 번호만이 아니라 바꾸는 내용(전후 문안, 예: 만 8세 → 만 10세)까지 들어가야 한다. 같은 조라도 무엇이 바뀌었는지에 따라 영향 가는 곳이 달라지기 때문이다.
2. **영향 후보 찾기(세 갈래).**
   - 유사도(RAG): 수정된 조와 문구나 의미가 비슷한 조. 같은 사항을 다른 규정에서 따로 정한 조가 대표적이고 값 충돌의 후보다.
   - 규칙 그래프(PR #11): 이 조를 인용하는 조, 같은 제목의 조, 같은 값을 쓰는 조, 같은 용어를 쓰는 조. 깨지는 인용은 문구가 안 닮아도 인용 선으로 잡힌다. 90개 규정 전체를 덮는다.
   - 도메인 그래프(PR #12): 같은 개념의 같은 속성(기간, 지급률, 횟수)을 정한 다른 항. 인사·보수·휴가·휴직 4개 영역만 덮는다(양이 많아 4개로 줄였다).
3. **영향 판정.** 모은 후보를 읽고 충돌이 생겼는지, 인용이 깨졌는지 확인한다. PR #11은 후보와 근거 카드까지만 내고 사람이 결정한다. PR #12 평가는 판정 모델(Luna)이 새 문제와 해소된 문제를 직접 보고하게 해서 점수를 낸다.
4. **출력.** 영향 후보 조 목록과 근거. PR #11은 확정급, 확인 권장, 참고 순으로 줄을 세운다.

범위 결정: 삭제와 추가(신설)는 추후 과제로 둔다. 현재 PR #12의 120문항도 개정 연산이 값·문구 바꿈 536개와 번호 이동 80개뿐이고 삭제·추가는 0개다.

용어 정리(혼동 방지):
- 이 평가의 "RAG"는 평가를 위해 PR #12 안에서 만든 단순 기준선이다. 개정된 조 하나마다 "규정명 + 조 + 제목 + 바뀐 부분 + 바뀐 항 원문(1,200자)"을 질의로 만들고, 임베딩 유사도 상위 200과 BM25 상위 200을 합쳐(RRF) 개정된 조 자신을 뺀 순위에서 최종 10개를 판정 모델에 넘긴다. 검색 대상은 3,244개 단위(본문 조 2,027, 부칙 540, 별표·서식 419, 문서 앞 텍스트 258).
- 세 방식은 각각 `rag`(RAG 순위만), `pr_graph_rag`(RAG 순위 + 규칙 그래프 후보), `domain_graph_rag`(RAG 순위 + 도메인 그래프 후보)다. **세 가지를 모두 합친 방식은 PR #12의 120문항이든 새 60문항 설계든 시험된 적이 없다.**
- "전후 비교 수정 지시"는 판정 모델에 주는 지시문을 한 번 고친 것이다(새 문제만 묻던 것을 새 문제와 해소를 전후 각각 확인하게). 세 방식에 똑같이 적용했고 같은 개발 문항의 재평가다. RAG 77→83, 규칙 그래프 80→78, 도메인 그래프 88→93.

## 7. 세 방식 합치기: 후보 찾기 단계 오프라인 확인 (API 없음)

방법: PR #12가 저장해 둔 검색 기록(`results/reviewed/retrieval.jsonl.gz`)과 정답(`gold.jsonl`)으로, 채점기의 "검색 적중"(정답 이슈 쌍의 상대 조항이 최종 후보에 들어온 수, 개정 전후 두 상태 합계 354)을 다시 계산했다. 먼저 내 계산이 저장된 상위 10과 240/240개 상태에서 똑같이 나오는지 확인했다(세 방식 모두 일치). 판정 모델은 호출하지 않았다.

| 후보 | 적중 /354 |
|---|---|
| RAG, 후보 10 | 196 (55.4%) |
| 규칙 그래프 + RAG, 후보 10 | 240 (67.8%) |
| 도메인 그래프 + RAG, 후보 10 | 226 (63.8%) |
| 두 그래프 순위를 한 순위로 합침(근사), 후보 10 | 225 (63.6%) |
| 위 + RAG 한 번 더(근사), 후보 10 | 213 (60.2%) |
| 규칙 그래프 + RAG 후보 15 / 20 | 253 (71.5%) / 257 (72.6%) |
| 도메인 그래프 + RAG 후보 15 / 20 | 242 (68.4%) / 250 (70.6%) |
| RAG 후보 15 / 20 | 222 (62.7%) / 234 (66.1%) |
| **두 그래프 방식의 상위 10을 각각 뽑아 합집합(평균 후보 15.3개)** | **276 (78.0%)** |
| 같은 방식, 각각 상위 8 합집합(평균 12.4개) | 260 (73.4%) |

개정 유형별(상위 10 기준): 새 문제 발생(214) RAG 104, 규칙 그래프 140, 도메인 그래프 118, 합집합 152. 기존 문제 해소(140) RAG 92, 규칙 그래프 100, 도메인 그래프 108, 합집합 124. 정상 변경 문항은 정답 이슈가 없어 해당 없음.

해석:
- **두 그래프는 서로 다른 것을 찾는다.** 규칙 그래프는 새 문제 발생 쪽(140/214, 65%)에서, 도메인 그래프는 기존 문제 해소 쪽(108/140, 77%)에서 강하다. 합집합은 후보 15.3개로 276(78.0%)이고, 후보 수를 맞춰도 규칙 그래프 단독 15개(253)보다 23건, 20개(257)보다도 19건 많다.
- **순위를 한 줄로 합치는 방식은 도움이 안 됐다**(225, 후보 10개 고정). 다만 이 값은 근사다. 저장된 기록에는 각 그래프의 원래 순위가 없고 "RAG와 합친 뒤의 순위"만 있어서, 합친 순위를 다시 합치면 RAG가 2~3번 반영된다. 정확한 값은 원래 코드에서 `fuse(rag, pg, dg)`를 돌려야 알 수 있다.
- **이것은 후보 찾기 단계의 결과이고 최종 점수가 아니다.** 앞서 본 대로 후보 적중이 가장 높은 규칙 그래프가 최종 점수는 가장 낮았다. 합집합으로 늘어난 후보가 판정 모델에게 도움이 될지는 판정까지 돌려야 안다.
- 한계: 같은 개발 문항이고 정답은 AI 초안이며, 4개 영역에 한정된다. 후보 10개를 고정한 평가 설계에서 합집합은 15개를 쓰므로, 판정 입력이 길어진다.

## 8. 충돌 관계 정리 (그래프 확정용, 2026-11-06 초안)

기준 문서: 팀의 `docs/06-conflict-definition.md`(검토 대상 → 저촉 후보 → 확인된 저촉의 세 겹, 네 조건 ①같은 적용 대상 ②같은 행위·사안 ③시점이 겹침 ④한쪽을 따르면 다른 쪽을 지킬 수 없음)와 선행 연구 GReX(두 규칙이 충돌한다 = 판단이 다르고 한쪽의 조건이 다른 쪽을 포함한다). 우리 네 조건은 GReX 정의와 같은 뼈대다.

용어: 기능 2가 내는 "문제"는 **검토 대상**(1겹)이다. 네 조건을 모두 확인한 것만 **저촉 후보**(2겹)로 올리고, 하나라도 확인하지 못하면 UNKNOWN으로 둔다. 확정은 사람이 한다.

### 8-1. 이번에 그래프에 넣는 것 (1차)

| 관계 | 정의 | 판정 | 그래프에 저장할 것 | 지금 성적 |
|---|---|---|---|---|
| 깨진 인용 | A가 인용한 B가 없거나(삭제, 이동, 번호 변경) 인용 번호가 맞지 않음 | 코드 | 인용 선(CITES: 출발 단위, 도착 단위, 원문 표현, 상태) | 규칙 104/104 (PR #12 정답, 개발 수준) |
| 값 불일치 | 같은 제도·속성·적용 대상에서 숫자 값(기간, 횟수, 비율, 금액)이 서로 다름 | 값은 규칙, 표현이 다르면 모델 | **사항 카드**: 제도, 속성, 적용 대상, 값(단위 정규화), 조건·예외 표시, 근거 인용문, 상태(AI 초안/사람 확인) | 규칙 54/114 (47%) |
| 위계 표시 | 충돌이 규정 사이면 어느 쪽이 상위인지(법령 > 정관 > 규정 > 지침) | 코드 | 규정 노드의 위계 속성(이미 있음) | 해당 없음 |

저장 규칙:
- 충돌 자체를 선으로 저장하지 않는다. 사항 카드가 저장되고, 같은 제도·속성·적용 대상이면 "비교 가능" 관계가 파생되며, 값이 다르면 "충돌 의심"이 파생된다. 파생 관계에는 두 근거 인용문이 붙고 인용문이 원문에 있는지 코드로 검증한 결과를 함께 저장한다.
- 적용 대상 칸이 비면 "비교 불가(UNKNOWN)"로 두고 추측하지 않는다.
- 속성과 제도는 닫힌 목록을 쓴다. 처음 목록은 우리가 확인한 충돌 23건과 인사·보수·휴가·휴직에서 만든다.

### 8-2. 다음 차례 (2차, 같은 카드 구조로 확장)

- **주체·절차 차이:** 결정권자(대표이사, 이사회, 주주총회)와 정족수(과반수, 2/3)를 값이 열거형인 속성으로 카드에 넣는다. 우리 확정 충돌 23건 중 6건이 여기에 속한다.
- **용어 정의 불일치:** 같은 용어를 규정마다 다르게 정의. 23건 중 5건.
- **법령 대조:** 내규와 법령의 값·옛 법령명 차이. 법령 DB와 법령 조 인용 선(CITES_LAW_ART)을 쓴다. 23건 중 5건.

### 8-3. 나중으로 미루는 것

- 포함 관계(일반 규정과 특별 규정, 직원 전체와 일부 직원): 지금은 주체가 다르게 명시되면 비충돌, 단서·준용이 있으면 UNKNOWN.
- 미반영(법령이 요구하는데 내규가 침묵): 법령 개정을 입력으로 받을 때 필요. 정의 문서(06)에도 아직 없다.
- 의무·금지·허용 같은 양태 충돌(숫자 없는 충돌): 판정 세션이 "의무 문구" 유형을 직접 추가해야 했을 만큼 필요하지만 탐지 규칙이 없다.
- 시점(효력일, 시행일): 문서 단위 최종 개정일 가정(G6)을 쓰며 조문 단위 이력이 없다.
- 오인용(인용 대상은 있으나 내용이 다름): 의미 판단이 필요해 모델과 사람이 맡는다.

### 8-4. 충돌이 아닌 것 (정의에서 뺀다)

- 중복(06 제21조가 따로 둠), 표기 오류, 업무상 개정 필요성, 법적 효력의 확정.

### 8-5. 근거

우리가 확정한 충돌 23건(판정 세션 16건과 새 비교 7건)의 유형 분포: 수치 5, 용어 5, 법령 5, 주체 3, 절차 3, 의무 문구 1, 규정 내 모순 1. 1차는 이 중 숫자 값을 먼저 하는 것이고, 주체·절차와 용어, 법령은 같은 카드 구조에 열거형 속성이나 법령 DB를 더해 2차로 간다. 확정 충돌이 23건뿐이라 유형별 비율은 방향만 참고한다.

## 9. 그래프 탐색 방법 비교 실험 (2026-11-08, 코드로 직접 돌림, API 없음)

코드, 출력, 재현 방법은 `eval/graph_traversal/`(README.md가 결과 전체). 수정된 조에서 시작해 영향 후보를 모을 때 탐색 방법을 바꾸면 정답 조가 상위 k개 안에 얼마나 드는지를 두 평가셋에서 잰 것이다. 후보 찾기 단계만 재고 판정(오경보)은 포함하지 않는다.

- 그래프: 팀 코드(`feature/ontology-boost-external-eval-261106`의 `src/regcheck`)로 규정 90개에서 다시 만듦. 노드 3,697, 선 13,485.
- 평가셋: PR #12 문제 있는 80문항(정답 짝 177), 팀 5~7차 가상 개정 36건(정답 106, 팀이 규칙을 맞춘 개발용).
- 비교한 방법: 팀 규칙표 1홉, 전관계 BFS 1~3홉, 가중 BFS 2~3홉, 개인화 PageRank(되돌아옴 0.15/0.3/0.5, 허브 감쇠, 종류 맞춤 가중치, 방향 제한), 규칙 먼저 + PageRank 채움, 순위 합치기(RRF), 가지치기 번지기, 관계별 번갈아 뽑기, 관계 가중치 학습(관계 묶음 단위 5겹 교차검증), 저장된 RAG 순위와 합치기.

결과 요약 (두 평가셋 재현율의 단순 평균, 상위 10 / 상위 20):

| 방법 | @10 | @20 |
|---|---|---|
| 팀 규칙표 1홉 (현재) | 53% | 64% |
| 규칙표, 개정 종류를 몰라 전 종류를 합침 | 63% | 75% |
| 개인화 PageRank (팀 관계 가중치) | 66% | 78% |
| **규칙 1홉 먼저 + PageRank로 채움** | 65% | **80%** |
| 가중 BFS 2홉 | 65% | 80% |
| 가지치기 번지기(규칙 상위 12개에서 한 걸음 더) | 규칙표와 같음 | 같음 |

확인한 것:
1. 현재 규칙표가 가장 낮다. 정답 짝이 전부 1홉 안(PR12)인데도 규칙표는 한쪽 방향 관계만 따라가서 놓친다(값 변경 표에 `CITES` 나가는 방향과 `MENTIONS_TITLE` 나가는 방향이 없음). 개정 종류를 잘못 분류하면 후보가 통째로 빠진다.
2. 방향을 열고 관계 가중치로 순위를 매기면 PR12에서 상위 10이 64%에서 81%로 오른다. 이득은 대부분 `CITES` 선에서 나온다(`CITES`를 빼면 143건 중 51건이 사라짐).
3. 가지치기하며 번지기는 효과가 없다. 규칙표 후보에서 한 걸음 더 가도 새 정답이 안 들어온다.
4. 관계 가중치를 학습해도 이득이 작다(교차검증 상위 10: 학습 82.5%, 팀 가중치 80.8%, 균등 70.6%). 팀 가중치를 그대로 쓴다.
5. 정의 변경은 규칙표가 낫다(팀 문항 정의 변경 7건, 상위 20 적중 규칙 94%, PageRank 74%). PageRank는 같은 용어를 쓰는 많은 조에 점수를 흩뿌린다. 그래서 규칙 후보를 앞에 두는 조합이 안전하다.
6. 법령 변경은 모든 방법이 약하다(위임·법령 변경 5건, 상위 20 적중 11~22%). 법령 조 노드가 규정이 인용한 조에서만 시작되기 때문이다.
7. 저장된 RAG 순위를 더해도 PR12에서는 이득이 없다(PageRank 단독 81%, RAG 2자리 + PageRank 80%, RAG와 PageRank 순위 합치기 73%, RAG만 55%). PR12 정답이 가까운 짝뿐이라 그래프만으로 거의 잡히는 평가 설계의 영향이다.
8. 불확실성: 팀 36문항에서 PageRank 단독은 현재 규칙표 대비 95% 구간이 0을 포함한다(-4 ~ +30%p). 규칙 먼저 + PageRank 채움은 두 평가셋 모두 구간이 0 위에 있고 나빠진 문항이 거의 없다(팀 문항 0개, PR12 4개 대 나아진 22개).

권장: 후보 수집의 기본을 **규칙 1홉 후보를 먼저 두고 뒤를 PageRank로 채우는 방식**으로 바꾼다. 개정 종류를 몰라도 동작하고, 정의 변경을 보호하며, 계산이 가볍다.

한계: 후보가 늘면 판정 단계의 오경보가 늘 수 있다(PR12에서 규칙 그래프가 그랬다). 판정까지 돌린 비교는 하지 않았다. PR12 정답은 쉬운 설계이고 팀 문항은 작고 개발용이다. 정답은 AI 초안이다. 팀 문항에서는 문구 검색과 의미 검색(RAG)을 쓰지 않은 그래프 단독 비교다.

## 10. 후보 줄이기: 리랭커와 판단 모델 비교 (2026-11-09, 로컬 GPU, API 없음)

코드, 출력, 표 전체는 `eval/graph_traversal/rerank/`(README.md). 규정 본문은 외부로 나가지 않았다(모델 파일을 내려받아 로컬 RTX 4070 노트북 GPU에서 실행). 답변 생성과 판정은 하지 않았다.

비교한 점수 모델: bge-reranker-v2-m3, Qwen3-Reranker-0.6B, jina-reranker-v3(목록 단위), 카카오 판단 모델 `kanana-2-v-decide-3b-2611`(예/아니오 확률과 4단계 점수, 별도 가상환경 `torch 2.10` `transformers 5.5.3`). 후보 풀은 §9의 방식 F(규칙 먼저 + PageRank)의 앵커별 상위 50(팀 문항) 또는 25(PR12).

결과:
1. **일반 리랭커(bge, Qwen3-0.6B)는 그래프 순위를 못 이긴다**(상위 10: PR12 68%, 44% 대 그래프 75%. 팀 43%, 45% 대 56%). 정답이 문장 유사가 아니라 인용·제목·용어로 이어진 조이기 때문이다.
2. **카카오 판단 모델의 4단계 점수가 가장 믿을 만한 단일 점수**다(상위 10: PR12 80%, 팀 59%로 둘 다 그래프 순위보다 높음). jina는 PR12에서 1위(85%)이나 팀 문항에서는 그래프보다 낮다(50%).
3. **그래프 + 카카오 + jina 순위 합치기(RRF)**가 두 평가셋에서 고르게 좋다(두 평가셋 평균 상위 5 / 10 / 20 = 56 / 69 / 84%, 그래프만은 47 / 65 / 80%). 이득은 작다(+4~9%p).
4. **후보 개수**: 앵커당 기본 10개. PR12는 5개에서 포화(97%). 정의 변경은 N을 키워야 한다(팀 문항 정의 변경 47건 중 N=10에서 27, 20에서 41, 30에서 45). 용어 사용처는 구조로 정해지는 목록이라 순위 없이 30개까지 낸다. 위임·법령 변경은 풀 자체에 정답이 6/18뿐이라 N과 무관하다(후보 풀 보강이 필요).
5. **점수 기준선은 거짓 경보를 줄이지 못한다.** 정상 변경 40문항(앵커 270)과 문제 있는 문항(앵커 346)의 카카오 점수 분포가 비슷하다(후보 최대 점수 평균 1.85 대 2.08, 앵커 구분 AUC 0.68, 정답 후보의 80%를 지키는 기준선에서 통과 후보 수 4.5 대 4.8). 점수는 후보를 줄이는 용도로만 쓰고, 오경보는 개정 전후 값 비교 판정(규칙 판정기는 정상 변경 오경보 0)에서 다뤄야 한다. 대리 지표이고 정상 변경 문항은 후보 조항도 함께 개정된 경우가 많아 조건이 다르다.
6. 속도(RTX 4070 노트북): bge 14쌍/초, Qwen3-0.6B 24쌍/초, jina 약 30쌍/초, 카카오 약 2쌍/초(질문 둘 포함). 앵커 하나에 후보 25개를 카카오로 점수 매기면 약 12초.
7. 라이선스: jina CC-BY-NC 4.0(비상업), 카카오 kanana-open-license(상업 이용 조건 미확인). 운영 전 확인 필요.

한계: 개발 수준 평가셋(PR12 쉬운 설계, 팀 36문항), 정답은 AI 초안, 판정(오경보) 직접 측정 안 함, Qwen3-Reranker-4B는 8GB GPU에 맞지 않아 못 돌림. 카카오 질문 문구는 한 번 정해 조정하지 않았다.

다음 후보: ① 후보 풀 보강(법령 조, 서식), ② 개정 전후 값 비교 판정(규칙) 연결, ③ 로컬 판정 모델 여부는 사용자 결정(규정 본문 외부 전송 방침 확인 전에는 `gpt-6-luna` 사용 안 함).

## 11. 판단 모델 추가 비교와 논문 탐색 방식 (2026-11-09, 로컬 GPU, API 없음)

**판단 모델 3개 추가** (d3-nano, hs-decide-1-flash, Jev-Style 2B v3, 모두 Apache-2.0, 로컬 실행). 상세와 표는 `eval/graph_traversal/rerank/README.md` 끝 섹션.
- 단독 점수는 d3-nano가 가장 좋다(케이스 단위 상위 10 재현율 73%, 카카오 70%, jina 67%, 그래프 65%). hs-decide 57%, Jev-Style 55%는 약했다.
- **권장 갱신: 그래프 + d3-nano + 카카오를 순위 합치기(RRF)로 합쳐 앵커당 10개.** 상위 10 75%, 상위 20 87%(이전 권장 69%, 84%). 약한 모델까지 5개를 다 섞으면 나빠진다.
- 주의: PR12는 쉬운 평가셋이라 d3-nano의 100%는 큰 근거가 아니고 학습 데이터 섞임은 확인하지 않았다. 팀 문항은 d3-nano 57%, 카카오 59%로 비슷하다.
- TypeSafe Jev(호스팅)는 외부 전송 허용을 받았으나 API 키가 없어 돌리지 않았다.

**논문에서 가져온 탐색 방식** (`eval/graph_traversal/README.md` 끝 섹션): 허브 감쇠(HippoRAG, BeamRAG), 퍼짐 활성화, 인용 폐쇄, 단계적 확대(A2RAG)는 기준선(PageRank, 규칙 먼저 + PageRank)을 넘지 못했다(두 평가셋 평균 상위 20에서 최고 81% 대 80%). 이전 "일반 방법만 비교했다"는 한계를 이 조사로 일부 보완했다.

**PCST(G-Retriever)**: 최단경로 트리 근사로는 재현율 이득이 없었고(상위 20 80%) 근거 경로가 나오는 점이 장점이었다. 논문 구현(`pcst_fast`)은 설치했으나 결과가 비정상(후보가 거의 나오지 않음)이라 원인을 찾는 중이며 수치를 쓰지 않는다.
