# 07. 조항 수정 에이전트 평가 종합

조항 수정 에이전트(점검 · 개정 지원)를 **무엇으로, 어떻게 재었고, 결과가 어땠는지** 한곳에 모은 문서다. 숫자는 각 리포트에서 옮겼고, 자세한 근거 · 판정 · 버린 대안은 링크한 리포트에 있다. RAG 챗봇 평가는 [rag-experiment-pipeline](rag-experiment-pipeline.md) · [리포트 59](reports/261019-1050-59-rag-experiment-decision.md).

- 작성: 261019. 새 평가를 하면 해당 절의 숫자와 리포트 링크를 갱신한다.
- 평가 데이터: `eval/agent/` (규정 원문 문장이 들어간 파일은 git 제외, 시드로 다시 만든다 — `.gitignore` 참고)

**읽는 법**: 2 · 3번처럼 정답을 코드가 만드는 평가는 **기계적 정합성**(글자 단위로 확인되는 것)을 재므로 점수가 높다. 실제 업무에서 「같이 고쳐야 할 곳을 다 찾는가」는 1 · 4번(사람이 고친 실제 오류 · 실제 개정)이 더 가깝고, 여기는 표본이 작다. 업무 판단이 필요한 부분은 결론 내지 않고 현업 검수(UAT)로 넘긴다.

## 1. 기준선 점검 정답 원장

- **무엇**: 규정 원문만 보고(개정 없이) 이미 있는 오류를 찾는 점검이 사람이 실제로 찾아 고친 오류를 몇 개 찾는가.
- **평가셋**: 사람이 확인한 오류를 정답 원장으로 모음 — 1주차 우리 검토(기준 조정에 씀), 김가빈 검토 정리본, 가빈 `corrections.json` 155건 중 우리 점검 범위 23건(**규칙 조정에 쓰지 않은 독립 자료**). 사람이 「맞음」으로 확인한 정상 10곳도 함께 넣어 오탐을 잰다.
- **구현**: 인용 추출(관련 조항 표) → 규칙 점검(없는 조 · 삭제된 조 · 옛 법령명 · 법령명 오기) + 개정 이력 신호(인용하는 조는 그대로인데 대상 규정이 나중에 개정됨, 리포트 22) + 의미 비교. 정밀도를 올리려고 법령 나열 · 연결어 · 별표 개념어 등 오탐 원인을 일반 규칙으로 걸렀다(리포트 46).
- **결과**
  - 1주차 16/16, 가빈 정리본 7/7(대상 불일치 3건은 「낮음」 우선순위로만), 가빈 corrections 17/23 → 개정 이력 신호 뒤 **20/23**(남은 3건은 부칙 옛 조문 — 오류에서 빼는 정책 차이). 전체 **43/46**. 정상 확인 10곳 오탐 0.
  - 정밀도: 점검 결과 279 → 257건으로 줄이고 재현율 그대로. 주 목록 원문 대조 정밀도 약 **48%**(2차 표본 29건 중 14건, 1차만 보면 25%). 「참고」로 내린 묶음은 22건 중 진짜 1.
- **한계**: 정밀도가 절반 수준이라 결과는 「확인 대기」 목록이다. 판정은 담당자.

## 2. 오류 주입

- **무엇**: 정상 조문에 오류를 하나씩 넣고, 점검이 **그 자리에서 그 유형으로** 찾는지(위치 · 유형 둘 다 맞아야 정답).
- **평가셋**: 정상 조문 151곳 × 오류 7가지(없는 조 인용, 삭제된 조 인용, 옛 법령명, 법령명 오기 등). 시드를 바꿔 다시 만든다(`scripts/eval_inject.py --seed N`).
- **결과**: 재현율 시드 1 **0.96**(145/151), 시드 2 **0.98**(148/151). 놓친 것은 모두 「짧은 법령명에서 글자 하나 빠짐」 → 고친 뒤 시드 1 151/152, 시드 3 152/152(남은 1건은 처음부터 있던 다른 유형).
- 규칙 밖 오류(잘못된 조 인용)는 규칙으로 약 18%만 잡혀 → 7번 LLM 인용 검토로 이어짐.

## 3. 변경안 골든셋

- **무엇**: 이 에이전트의 본래 목표 — 조항을 추가 · 삭제 · 수정했을 때 **다른 곳에 생기는 문제**(깨지는 인용, 다른 규정과 수치 충돌, 새 문장 속 옛 법령명 · 오타, 다른 규정 확인)를 잡는가.
- **평가셋**: 개정 유형별 문항을 시드로 생성하고, 정답은 생성기가 원문 검색으로 정한다(`eval/agent/change_gold_s*.jsonl`). 문제없는 변경(예: 「하여야 한다」 → 「해야 한다」)도 넣어 오경보를 잰다. 설계에 쓰지 않은 **새 시드 2 · 3 · 4(각 482문항)** 로 독립 확인(리포트 51).
- **구현**: 개정문 적용(사본) → 변경안 점검 6경로(인용받음 · 문서 인용 · 같은 제목 · 정의 용어 · 의미 유사 · 재검사) + 법령 대조 + 오타. 문항당 채점 수 초.
- **결과**

  | 유형 | 시드 1 (개발용, 182문항) | 새 시드 2+3 (482 × 2) | 시드 4 (오타 끔) |
  |---|---|---|---|
  | 깨지는 인용 | 99/100 | 517/519 = **99.6%** [98.6, 99.9] | 276/276 |
  | 새 문장 속 법령명 | 31/31 (처음 0/16 → 고친 뒤) | 153/153 | 77/77 |
  | 다른 규정과 새 충돌 | 10/10 | 60/60 | 30/30 |
  | 다른 규정 확인 | — | 86/86 | 39/39 |
  | 법령 수치 | 4/4 | 8/8 (표본 작음) | 4/4 |
  | 오타 | 2/4(로컬 30B) · 7/8(luna) | 256/374 = **68.4%**(로컬 9B) | — |
  | 문제없는 문항 높은 우선순위 경보 | 0 | 182개 중 9 | 91개 중 0 |

  - 오경보 9건: 정답 쪽 한계 2(시스템이 맞음), 시스템 오경보 4(막연한 「규정 제5조」를 같은 문서 인용으로 읽음 2, 「하여야 → 해야」를 오타로 봄 2), 원인 미확인 3.
  - 평가 중 **정답 생성기 결함 5개**를 찾았고 모두 시스템이 맞았다(규정명 부분 일치, 부칙 이력 표시를 인용으로 셈, 법 조문 다른 항의 숫자 등). 실제 버그 1개(문장 덧붙이기 IndexError)도 찾아 고쳤다.
  - 모델 없이 글자 연쇄로 찾는 근접 오타 검사를 추가해 LLM 없이 재현 약 77%(커밋 3f96806, 리포트 없음).
- **한계**: 정답을 코드가 만들므로 **실제 개정에서의 연동 탐지력을 뜻하지 않는다**. 규정명을 조금 틀리게 쓴 인용(「전화 녹음관리 및 운영지침」 → 「전화 녹음 및 운영지침」)은 비슷한 이름으로 연결돼 깨짐으로 안 잡힌다(고치지 않은 한계).

## 4. 실제 사례 · 과거 재현

- **실제 사례 S01~S03** (`docs/08-demo-scenario.md`): S01 육아휴직 분할 4/4, S02 당연면직 삭제 4/4(실시간 의미 유사를 켠 뒤 — 「당연해직」을 0.74로 잡음, 대신 카드가 5 → 11장이라 모델 추정 카드 6장 상한), S03 12/12(깨짐 10 → 연쇄 수정 0). 오탐 0. S02는 설계 때 본 사례라 독립 확인은 아니다.
- **과거 재현**: 이 회사의 조 신설 · 번호 이동 개정 44건을 그날 이전 구조로 되돌려 에이전트에 넣고 실제와 비교.
  - 다른 규정에 함께 고칠 곳이 실제로 있었던 1건(**급여규정 2025.03.28 → 성과급지급지침 제1조 「제21조」 → 「제22조」**)을 제안했고, 정답 G01(가빈 검토) · P007(corrections)과 일치. 실제로는 그 뒤 성과급지급지침이 3번 개정되고도 고쳐지지 않았다.
  - 정답에 없는 제안 0건. 개정안 자체의 확인된 문제 1건(전산업무지침 제12조의1 근거소멸)도 알렸다.

## 5. 자연어 개정 요청

- **무엇**: 「인사규정 육아휴직 분할 횟수를 3회로 늘려줘」 같은 말을 **의도에 맞고 원문에 그대로 적용되는 개정문**으로 바꾸나.
- **평가셋**: 외부 모델(gpt-5.4-mini)이 쓴 요청 120건 = 말투 4(A 격식 · B 구어 · C 규정명 없음 · D 짧고 거침) × 개정 3(숫자 변경 · 삭제 · 문장 덧붙이기). 정답은 코드가 정한다. 비용 약 50원.
- **구현**: 규정 · 조 찾기(규칙) → 삭제 · 신설 · 번호 이동은 규칙으로 개정문 → 문구 수정은 **LLM이 조문을 다시 쓰고 우리가 원문과 비교해 개정문을 만든다** → 적용기로 검증 + 의도 검사(신설인데 신설 없음, 다른 조까지 바꿈, 원문과 거의 안 겹치는 본문 등) → 실패하면 오류를 돌려주고 최대 3번.
- **결과**
  - 첫 시험(리포트 28, 내가 쓴 8건): 7/8, 요청 밖 변경 0.
  - 120건(리포트 51): 로컬 7B 88 · luna 103. D 말투는 둘 다 절반 — luna의 D 실패 14건은 모두 규정 이름을 못 찾은 것.
  - 규정 이름 느슨한 인식(리포트 56) · 의도 검사 보강 뒤 다시 잼(리포트 57, 엄격 채점): **로컬 7B 93 · 로컬 30B 108 · luna 116**. 이 결과로 웹의 개정안 작성 모델을 luna로 정했다(폐쇄망은 `DRAFT_MODEL`로 로컬).
- **한계**: 정답이 코드로 정해지는 세 가지 개정만 다룬다. 여러 조 · 여러 항을 함께 바꾸는 복합 개정은 아직 없다.

## 6. 개정 위치 찾기

- **무엇**: 규정 · 조 번호가 없는 요청(「출장비 기준을 올리고 싶다」)에서 고칠 조를 후보 상위에 올리나. 1위를 자동으로 쓰지 않고 **후보를 보이고 사람이 고른다**.
- **평가셋**: RAG 팀의 독립 라벨 평가셋 질문 90개(필수 근거를 규정 · 조로 매핑, 10문항은 매핑 안 돼 제외).
- **구현**: Qwen3-Embedding-4B 전용 색인 + 리랭커(조문 800자) + 순위 섞기 + 적용 대상 규칙(요청이 말하지 않은 해외 · 파견 · 임원 · 계약직 전용 규정은 뒤로). 규정 이름을 대충 쓴 요청은 비슷한 이름으로 인식.
- **결과**

  | 지표 | 시작(bge-m3) | 최종 | 짝지은 차이 [95%] |
  |---|---|---|---|
  | 조 @1 | 41% | **57%** | +15.6%p [+5.6, +25.6] |
  | 조 @3 | 62% | **74%** | +12.2%p [+3.3, +21.1] |
  | 조 @5 | 71% | **79%** | +7.8%p [+1.1, +15.6] |
  | 규정 @1 | 58% | **77%** | |

  - 짧고 거친 요청(D)의 규정 인식 18/30 → 28/30, 엉뚱한 규정 0, 이름 없는 질문 · 요청 108개에서 오작동 0.
  - 버린 것: 질문 바꿔 쓰기(조 @3 62 → 60%, 효과 없음), 30B로 다시 순위 매기기(효과 없음).
- **한계**: 질문 문장으로 쟀다(개정 요청 문장이 아님). 조 @1이 57%라 자동 선택에는 못 쓴다.

## 7. LLM 인용 검토

- **무엇**: 「있는 조인데 엉뚱한 조를 가리키는 인용」(예: 제15조를 말해야 하는데 제14조라고 씀). 규칙(설명구 + 리랭커)으로는 10~15%만 잡혔다.
- **구현 (선택형)**: LLM에게 대상 규정의 조 목록을 주고 「[인용] 자리에 가장 알맞은 조」를 고르게 해, 원문이 가리킨 조와 다르면 후보로 올린다.
- **결과**
  - 주입 시험: API(luna) 98~100% 잡음 · 맞는 인용의 20%를 다르게 고름, 로컬 30B 95~100% · 32~35%, 로컬 7B는 구분 못 함.
