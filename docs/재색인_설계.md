# 검색 색인 재설계 (재색인 기준)

전처리 결과(`out/chunks.jsonl`)를 BGE-m3로 임베딩해 PostgreSQL(pgvector)에 넣는 방법을 정리한다.
청킹 규칙은 `docs/전처리_규칙.md`를 따른다. 이 문서는 **색인 단계**만 다룬다.

**기준일: 2026.10.06**

---

## 1. 색인 대상

| 구분 | 개수 | 처리 |
|---|---|---|
| 정상 청크 | 4,554 | 기준 집합 |
| └ 부칙 | 89 | **색인하지 않음.** `cites`와 옛 규정 판정용으로만 둔다 |
| └ 색인 대상 | **4,465** | 임베딩하여 pgvector에 저장 |
| 삭제 조문 | 25 | **색인하지 않음.** `cites` 조회용으로만 둔다 |

**부칙을 뺀 이유**
- 부칙은 과거 개정의 시행 경과와 개정 지시다. 현행 규정 내용이 아니다.
- 검색 상위에 올라오면 답변을 흐린다. 그래서 검색 대상에서 뺀다.

---

## 2. 임베딩 입력

| 항목 | 결정 |
|---|---|
| 모델 | BGE-m3 (로컬, GPU `cuda`, fp16) |
| 차원 | 1,024 |
| 입력 글자 | `본문_검색` (확정 오탈자 반영 글자) |
| 저장 본문 | `본문` (원문 표기). 답변 인용과 `정정안내`에 쓴다 |
| 정규화 | 임베딩 벡터를 정규화하고, 거리 함수는 코사인 |
| 머리말 | **붙이지 않는다** (아래 3절) |

### 머리말을 붙이지 않는 이유
- 머리말(`[문서명 · 조항]`)을 붙이면 같은 규정의 청크가 상위를 독점하는 쏠림이 생길 수 있다.
- 문서명으로 묻는 질문이 약하다는 문제는 있다. 하지만 하이브리드 검색(BM25)과 문서명 필터로 먼저 보완한다.
- 그래도 부족하면 그때 머리말을 추가하고, 그때는 쏠림을 함께 측정한다.

---

## 3. 머리말 방식 (보류)

지금은 쓰지 않는다. 검증 결과에 따라 다시 정한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 머리말 없음 (**현재**) | 재색인 한 번이면 끝난다. 쏠림이 없다 | 문서명으로 묻는 질문에 약하다 |
| `[문서명 · 조항]` 머리말 | 문서명·조 번호 질문에 강하다 | 같은 규정 청크가 상위를 독점할 수 있다. 짧은 항은 머리말이 본문보다 길어질 수 있다 |

머리말을 붙이기로 하면 샘플 200개로 먼저 비교하고, 전체 재색인은 한 번만 한다.

**2026-10-07 결정:** 색인(임베딩·BM25)에는 여전히 붙이지 않는다. 대신 리랭커 입력에만 `[문서명 조항]` 머리말을 붙인다 (`config.RERANK_HEADER`). 놓친 질문 2개가 모두 리랭커 단계에서 밀렸고, 리랭커 입력은 검색 때 만들어지므로 재색인 없이 바꿀 수 있다. 측정 결과와 쏠림 비교는 `검색_설계.md` 5절에 있다.

---

## 4. 긴 조 처리

**추가 청크를 만들지 않는다.** 색인은 항 단위로만 둔다.

긴 조는 이미 항별로 나뉘어 있다. 800자를 넘는 청크 71개 중 68개는 부칙이고, 항 청크는 3개뿐이다. 부칙은 1번에서 색인 대상에서 빠지므로 긴 조 문제는 거의 없다.

**검색 후 형제 항 확장 (답변 단계)**
1. 검색으로 항 청크가 나온다. 예: `23234_제5조_2항`
2. 같은 `고유번호`와 `조항`(조 번호)을 가진 형제 항을 **메타데이터 조회**로 가져온다. 벡터 계산과 저장이 없다.
3. 검색된 항을 먼저 두고, 나머지 항은 조 순서대로 붙인다.
4. 붙이는 양은 **상한 3,000자**로 제한한다. (제안값, 미확정)
5. 한 줄로 된 조는 형제 항이 없으므로 그대로 쓴다.
6. 조 제목은 1항 청크에 있다. 2항 이후만 검색되었을 때는 1항의 조 제목을 함께 넣는다.

---

## 5. 호 처리

- 호(`1.`, `2.`)는 항으로 나누지 않는다. 항 본문 안에 그대로 둔다 (`docs/전처리_규칙.md` 4.8절).
- 호 번호는 청크 ID에 없다. 호 단위 인용은 항 청크 안에서 찾는다.

---

## 6. 저장 구조

| 항목 | 내용 |
|---|---|
| 저장소 | PostgreSQL 17 + pgvector (`regulations` DB). 설정은 `DB_설정.md`, 스키마는 `DB_스키마.md` |
| 컬렉션 | `regulations` (본 색인), `test_index` (샘플 200개, 확인용) |
| 문서 ID | 청크 `id` 그대로 (예: `23234_제5조_2항`) |
| 메타데이터 | `고유번호`, `문서명`, `위계`, `조항`, `개정표기`, `상태`, `출처URL`, `정정안내`(JSON 문자열), `cites`(JSON 문자열) |
| 어댑터 | `src/store/pgstore.py`의 `PgStore`. 검색과 적재 코드는 이 클래스의 메서드만 쓴다 |

**현재 상태 (2026.10.06 기준)**
- `regulations`: 재색인이 필요하다. 이전 실행에서 벡터 인덱스 파일이 생성되지 않아 읽을 수 없다. 색인 대상 개수도 이번 설계(4,465개)와 다르다.
- `test_index`: 200개, 읽기 가능.

---

## 7. 실행 순서

1. **샘플 확인**: `test_index`로 4,465개 중 일부(200개)를 색인하여 파이프라인을 확인한다.
2. **전체 색인**: 4,465개를 `regulations`에 넣는다. 예상 소요 약 25분.
3. **검증**
   - 저장 개수가 4,465와 같은지 확인한다.
   - 검증 질문 세트로 상위 결과를 확인한다.
   - 문서명이 들어간 질문과 항 번호가 들어간 질문을 따로 본다.
   - 상위 결과가 한 규정에 쏠리는지 본다.
4. **형제 항 확장** 구현과 테스트.
5. **하이브리드 검색**(BM25 + 벡터, RRF) 구현. 이후 단계.

---

## 8. 명령

```
uv run python -m src.index.build --limit 200 --collection test_index   # 샘플
uv run python -m src.index.build                                       # 전체 (regulations 재생성)
```

`src/index/build.py`는 부칙과 삭제 조문을 색인하지 않는다 (`is_indexed`가 `false`). 전체 실행은 `documents`와 `chunks`를 비운 뒤 다시 넣는다.
