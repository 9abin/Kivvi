# 팀 실행 안내 (2026.10.14)

검색·답변 추천 구성과, 팀이 같은 결과를 다시 내는 방법. 질문 하나가 처리되는 순서는 `질의_흐름.md`,
단계별 근거는 `검색_설계.md`·`답변_설계.md`.

## 1. 추천 구성

| 항목 | 값 | 설정 |
|---|---|---|
| 색인 | **팀 DB 항 단위** (청크 4,819개, 색인 4,595개). 이 PC에서는 사본 `regulations_team` | `PG_DATABASE` |
| 임베딩 | `BAAI/bge-m3` (GPU fp16) | `EMBED_MODEL` |
| 질문 바꿔쓰기 | **켬** (GPT, 원래 질문 검색과 동시에) | `USE_REWRITE` (기본 켬) |
| 후보 검색 | 벡터 50 + BM25 50, 바꿔 쓴 검색어로 한 번 더 | |
| 합치기 | 가중 RRF, 벡터 0.7 : 키워드 0.3, RRF_K 60 | `HYBRID_*_WEIGHT`, `RRF_K` |
| 리랭크 | 상위 30개, `BAAI/bge-reranker-v2-m3`, 입력 `[문서명 장 조항] 본문` | `RERANK_MODEL`, `RERANK_HEADER` |
| 근거 고르기 | **항으로 찾고 조 전체 넘기기**: 서로 다른 조 5개, 각 조의 모든 항 | `RETURN_ARTICLE` (기본 끔) |
| 강조 | 근거마다 역할(질문으로 찾은 조문 / 인용된 조문(참고)), 조를 올린 항에 ▶ | `HIGHLIGHT_HITS` (기본 끔) |
| 인용 | 1단계. 법 인용은 찾은 항이 직접 인용한 것만, 중복 인용 제거 | `LAW_CITES_FROM_HITS` (기본 끔) |
| 응답 시간 개선 | 바꿔쓰기·검색 동시, 충돌 확인·답변 동시, 근거 검사는 답 뒤에, 스트리밍 | `FAST_PIPELINE` (기본 켬) |
| 질문 나누기 / 동의어 사전 | 끔 / 끔 | `QUERY_PLAN`, `USE_SYNONYMS` |
| 답변 모델 / 채점 모델 | `gpt-5.6-luna` / `gpt-5.6-luna` | `OPENAI_MODEL`, `JUDGE_MODEL` |
| 근거 상한, 관련 없음 기준 | 8,000자, 리랭크 1위 < 0.001 | `CONTEXT_CHAR_BUDGET`, `ANSWER_NONE_BELOW` |

`RETURN_ARTICLE`·`HIGHLIGHT_HITS`·`LAW_CITES_FROM_HITS`는 조 단위 DB에서는 의미가 없어서 기본을 꺼 두었다. 팀 DB를 쓰기로 확정하면 기본값을 켬으로 바꾼다.

## 2. 성능 (100문항, `eval/answer_eval_100.jsonl`)

| 지표 | 값 |
|---|---|
| LLM 채점 (luna) | 정답 29, 부분 59, 오답 4, 답못함 8, 금지 위반 3 |
| RAGAS (luna) | 충실도 0.891, 관련성 0.958, 문맥 재현 0.702 |
| 검색 (93문항, 조 단위로 채점) | Hit@1 0.41, Hit@5 0.76, Hit@10 0.84, MRR 0.563, Recall@5 0.623 |
| 첫 글자 / 답 완성 / 근거 검사 끝 | 평균 8.0초 / 10.4초 / 15.3초 |

검색 지표는 항으로 찾은 결과를 조로 바꿔 센다(같은 조는 첫 번째만). 답변에 조 전체가 넘어가므로 맞는 조의 아무 항이나 찾으면 된다.

### 실험 기록 (같은 100문항, 답변·채점 luna)

| 구성 | 정답 | 부분 | 오답 | 답못함 | 금지 | 충실도 | 문맥 재현 | 답 완성 |
|---|---|---|---|---|---|---|---|---|
| 조 단위 색인 (나누기 끔) | 27 | 59 | 13 | 1 | 11 | 0.861 | 0.738 | 19.6초 |
| 팀 DB 항 → 조 | 27 | 60 | 5 | 8 | 4 | 0.865 | 0.726 | 16.4초 |
| + 강조·법 인용 정리 | 30 | 56 | 6 | 8 | 5 | 0.900 | 0.712 | (GPU 겹침) |
| + 응답 시간 개선, 바꿔쓰기 끔 | 29 | 52 | 8 | 11 | 6 | 0.899 | 0.674 | 8.7초 |
| **+ 응답 시간 개선, 바꿔쓰기 켬 (추천)** | **29** | **59** | **4** | **8** | **3** | 0.891 | 0.702 | **10.4초** |

- 같은 설정을 다시 돌려도 판정이 10문항 안팎 흔들린다 (질문 나누기 끔/켬 비교에서 좋아짐 15, 나빠짐 11). 작은 차이는 신호로만 본다.
- 조 단위 색인은 인용으로 따라오는 근거가 많아(평균 2.0개, 항→조는 0.8개) 핵심 조문이 묻히는 문제가 있었다. 그래서 강조와 법 인용 제한을 넣었다.

### 바꿔쓰기 측정 (조 단위 색인, 검색만, 93문항)

| 오타 질문, 바꿔쓰기 켬 / 끔 | 0.35 / 0.39 | 0.73 / 0.71 | **0.84 / 0.78** | 0.518 / 0.529 | **0.714 / 0.665** |

오타 질문(`eval/questions_100_typo.jsonl`, `scripts/make_typo_set.py`)은 질문마다 오타 2곳 + 30%는 띄어쓰기를 붙였다. 바꿔 쓴 검색어는 gpt-4o-mini로 만들었다(`eval/runs/multi-cache.jsonl`).

### 응답 시간 (추천 구성 검색 단계, 15문항 평균)

luna 바꿔쓰기 2.18초 (4o-mini면 0.96초), 리랭크 30개 0.95초, 벡터 0.05초, BM25 0.004초, 조 조립·인용 0.005초. 그 뒤 luna가 첫 글자를 내기까지 약 4.8초.
로컬 모델(`qwen3.5:9b`, RTX 4070 노트북 8GB)은 답변 작성 한 번에 첫 글자 22.5초, 완성 43.1초로 맞지 않았다.

## 3. 팀 DB를 이 PC로 받기

팀 DB(`.env`의 `TEAM_*`, 조회 전용 계정)에 접속되면 public 스키마를 이 PC의 Docker DB에 새 DB로 복사한다. 팀 DB는 읽기만 한다.

```powershell
uv run python -m scripts.copy_team_db            # → db-pg 컨테이너의 regulations_team
```

`chunks.section`(장) 칸이 팀 DB에 없어서 사본에만 빈 칸으로 추가한다. 이미 있으면 멈춘다.

## 4. 추천 구성으로 평가하기

PowerShell, 저장소 루트. GPU 8GB 기준이라 GPU를 쓰는 실행(답변 생성, 검색 평가)은 하나씩 돌린다.
두 개를 겹치면 메모리가 거의 다 차서(7.9GB) 둘 다 크게 느려진다. 채점·RAGAS는 GPU를 쓰지 않는다.

```powershell
$env:PYTHONIOENCODING = "utf-8"
$env:PG_DATABASE = "regulations_team"
$env:RETURN_ARTICLE = "1"; $env:HIGHLIGHT_HITS = "1"; $env:LAW_CITES_FROM_HITS = "1"

# 답변 100문항 (첫 글자·답 완성·검사 끝 시간을 문항마다 기록, 같은 --tag로 다시 돌리면 이어서 함)
.\.venv\Scripts\python.exe -m src.eval.run_answer_eval --tag my_run --questions eval/answer_eval_100.jsonl
# LLM 채점 (판정별 개수 출력) / RAGAS (이미 만든 답변에 매김)
.\.venv\Scripts\python.exe -m src.eval.judge_answers my_run --questions eval/answer_eval_100.jsonl
.\.venv\Scripts\python.exe -m src.eval.ragas_from_runs my_run
# 검색 지표 (Hit@k, MRR, Recall@k, 단계별 정답 순위, 리랭크 뒤 10위 밖 문항)
.\.venv\Scripts\python.exe -m src.eval.rank_trace --questions eval/questions_100_retrieval.jsonl --out my_trace.json
```

- 결과: `eval/answer_runs/<tag>/runs.jsonl`(답변·시간), `judged.jsonl`(판정), `ragas.jsonl`, `eval/runs/<out>`(검색).
- 끄고 켜며 비교: `USE_REWRITE=0`, `FAST_PIPELINE=0` 환경 변수. `run_answer_eval --plan`/`--no-plan`은 질문 나누기. `rank_trace --no-rewrite`/`--synonyms`/`--no-synonyms`/`--device cpu`.
- 답변 평가셋의 근거를 고치면 검색 정답을 다시 만든다:
  `uv run python -m scripts.build_190_retrieval --src eval/answer_eval_100.jsonl --dst eval/questions_100_retrieval.jsonl`

- 근거 하나가 별표 조각 여러 개에 걸치면 "정답묶음" 한 묶음이고, 그중 하나만 찾아도 그 근거는 찾은 것이다.

## 6. 남은 일과 알려진 문제

- **LLM 채점이 흔들린다**: 오답 4개 중 2~3개는 사람이 보면 오답이 아닐 수 있었다(두 규정을 다 적은 것을 틀렸다고 봄, 근거에 있는 문장을 지어냈다고 봄). "빠짐"으로 표시된 요지에는 "다르게 말함"도 섞여 있다. 중요한 판정은 사람이 다시 본다.
- **"부분" 59개**: 답변에 넘어가는 상위 5개 조 안에 필요한 근거를 모두 찾는 비율이 Recall@5 0.62다. 넘기는 조 수(5 → 7)와 RRF 가중치(0.7 : 0.3은 항 단위 시절 값)를 재 볼 것.
- **더 빠르게**: 바꿔쓰기만 gpt-4o-mini로(약 −1.2초, 바꿔쓰기 효과를 잰 검색어가 4o-mini 것), 바꿔쓰기를 기다리는 동안 원래 질문 후보를 먼저 리랭크(약 −0.6~0.9초, 결과 같음), 결론·불릿 모순 확인을 답 뒤로(약 −1~1.5초).
- **평가셋 원본 오류**: "예전엔 배우자 출산휴가가 5일…"의 근거에 복무규정 제1조(목적), "인사규정 별표에 직급이 1급부터 5급…"의 근거에 개인정보 지침 "1급 개인정보" 별표가 들어 있다. "팀장 전결…"은 근거가 번호 없는 "별표"라 검색 정답에서 빠졌다.
- **이름 없는 위임 조문 41개**: "출장여비는 별도로 정한 바에 따라 지급한다"처럼 대상 규정 이름이 없어 인용 따라가기가 안 된다. 사람이 대상을 정해 `cites`에 넣으면 해결된다.
- **끊긴 인용 75개**: 약칭을 못 푼 61개, 대상을 못 찾은 14개는 따라가지 않는다.
- **HNSW 상한**: `hnsw.ef_search` 기본 40 < 요청 50. 지금은 DB가 전체 비교라 문제없지만 데이터가 늘면 올린다.
- **화면**: Streamlit 앱은 `ask()`를 그냥 불러 근거 검사를 기다린다. 답을 먼저 보여 주려면 `ask(…, on_token=…, wait_checks=False)`와 `finish()`로 바꾼다.
