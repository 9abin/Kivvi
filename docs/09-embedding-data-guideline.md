# 09. 임베딩 튜닝: 학습 데이터 생성 가이드라인과 파인튜닝 설계 (우리 구조 반영)

작성 261014 (v2) · 목적: 규정 검색의 **후보 단계 재현율**(후보 30개 안에 정답 근거 81.4%)을 90%대로 올린다. 이 문서는 ① 우리 구조에서 출발한 사실, ② 학습 데이터를 어떻게 만들지, ③ 어떻게 파인튜닝하고 평가할지를 정한다.
근거: 가빈 검색 실험(`feature/rag-tuning-para`, 검색_실험_261014), 그래프 상한 분석(리포트 39), 평가셋 분석(리포트 36), 이 저장소의 공유 DB 통계.

## 1. 우리 구조에서 출발 (확인한 사실)
| 항목 | 값 | 의미 |
|---|---|---|
| 색인 단위 | 항 청크. 전체 4,819개 중 색인 4,595개 (항 3,565 · 조 전체 897 · 별표 133) | 학습 문서 = 이 청크 그대로 |
| **청크 길이** | **중앙값 87자**, 90%가 222자 이하, 최대 2,195자 | 대부분이 한두 문장이라 **무슨 규정·무슨 조의 말인지가 청크 안에 거의 없다** |
| 색인에서 빠진 것 | 부칙 89 · 별지 55 (비색인), 삭제 항 80 | 정답 근거의 약 4.5%(7건)가 어떤 설정으로도 못 잡힘 |
| 검색 흐름 | 질문 + 바꿔 쓴 검색어(Luna가 규정 용어 한 줄로) 각각 벡터 50·BM25 50 → 가중 RRF(0.7:0.3) → 상위 30 리랭크(`[문서명 조항] 본문`) → k=8 조 묶기 → 형제 항·인용 확장 | 질의가 **두 형태**(구어 원질문, 규정어 검색어)로 들어온다. 둘 다 학습해야 한다 |
| 평가 단위 | **조(·별표)**. 항 청크가 맞아도 같은 조면 정답으로 센다 | 학습 라벨도 조 단위(§6) |
| 약점 | 후보 30 상한 81.4%, 놓친 근거의 61%는 이미 찾은 근거와 **같은 규정**, 36%는 인용으로 안 이어진 **다른 규정**, BM25를 섞으면 Hit@1 하락 | §3의 구조 쌍·복합 질문, §10의 하이브리드 재조정 |
| 쓸 수 있는 관계 데이터 | 인용 edge 1,884(조 대상·정상 381, 그중 다른 규정 109), 같은 제목 조 그룹 90개(287조), 정의 항 약 200, 규정·지침 위임 edge 약 200, 인용 연결 청크(`cites`) 1,260 | LLM 없이 만드는 **구조 기반 쌍**(§3-B) |
| 가빈 청크 ID ↔ 우리 항 대응 | `amend.chunk_detail`(4,530 대응) | 우리 파서 데이터를 같은 ID로 연결 |

> **결과 (261014 밤, [리포트 42](reports/261014-2030-42-embed-ft-v1.md))**: 이 가이드라인대로 합성 질문 5,316개(조 1,000개분)와 어려운 오답으로 LoRA를 학습했으나 **성공 기준(후보 Recall@30 +5%p)을 넘지 못했다**(개발용 ±0, 시험용 −2~−5%p). 합성 질문 검증 MRR은 0.81→0.91로 올랐으나 실제 질문(간접 사례·정의 조항)에는 전이되지 않았다. 다시 시도한다면 §3-C 복합 질문과 전체 조 커버, 실제 놓치는 유형을 닮은 질문이 조건이다. 가이드라인의 규칙(누출 검사, 조 단위 라벨, false negative 방지)은 유효했다.

## 2. 원칙 (어기면 평가를 믿을 수 없다)
1. **평가 질문·정답을 학습에 쓰지 않는다.** 생성 입력은 조문 원문과 구조 관계뿐. 평가셋(190문항 전체, N-set 80, 우리 골든셋)은 입력에서 제외하고, 생성된 질문이 평가 질문과 닮았으면 버린다(§8).
2. **시험용은 끝까지 안 본다.** 개발용 = 평가 100문항, 최종 시험용 = 190문항 중 안 쓴 90 + N-set 80. 설정 선택은 개발용·튜닝 검증으로만.
3. **원문은 KVIC 저작물.** 학습 데이터는 `data/embedding/`(git 제외). 저장소에는 가이드·스크립트·통계만. 외부 모델(luna)은 공개된 ALIO 문장에만, 개발 중 「선생」으로만 쓴다.
4. **공유 DB를 바꾸지 않는다.** 튜닝 벡터는 우리 스키마(`amend.chunk_vec`)에 둔다(§10-7). `public.chunks`는 읽기만.
5. **성공 기준을 미리 정한다**(§11). 기준 미달이면 접고 다른 길(§10-9)로 간다.

## 3. 학습 데이터 세 층
### A. 합성 질문 ↔ 청크 (핵심, 약 12,000쌍)
| 청크 종류 | 수 | 청크당 질문 |
|---|---|---|
| 항 (색인) | 3,565 | 길이 ≤60자: 1~2개 / 60~250자: 3개 / >250자: 4~5개 |
| 조 전체 | 897 | 3~4개 (조 제목으로 묻는 질문 포함) |
| 별표 | 133 | 5개: **행·열을 특정**하는 질문(「과장 해외출장 숙박비 상한은?」) |
| 부칙·별지 | 144 (비색인) | 지금은 만들지 않는다. 색인 방침이 정해지면 같은 규칙으로 추가 |
| 삭제 항 | 80 | 만들지 않는다 |
- **질문 두 형태를 함께 만든다** (검색에 실제로 들어오는 형태):
  - 구어 원질문(40%): 「반반차도 쓸 수 있어요?」 · 상황형(25%): 「병원 예약이 애매하게 잡혀서 2시간만 쓰려는데요」
  - **규정어 검색어(25%)**: 바꿔쓰기 프롬프트(`REWRITE_PROMPT`)가 내는 「공식 용어 + 주제어 2~4개 한 줄」 형태 (예: 「반일 단위 연차 2시간 분할 사용」). 검색의 2번째 질의가 이 모양이다.
  - 격식 질문(10%): 「직위해제 사유는 무엇입니까?」
- 핵심어 중 적어도 하나는 조문과 **다른 말**로 바꿔 쓴다(속어·줄임말·풀어쓴 말). 조 번호·규정명 금지(규정명이 질문 일부인 것은 10%까지).
- 한 청크의 질문들은 말투·핵심어가 서로 달라야 하고, 그 청크만 읽고 답할 수 있어야 한다. 한 문장 80자 이내.
- 청크가 짧아 문맥이 없는 항(「전항에 따라…」)은 **조 제목·규정명을 모델에게 보여 주되** 질문에는 쓰지 못하게 한다.

### B. 구조 기반 자동 쌍 (LLM 없이, 약 3,000쌍) — 우리만 가진 데이터
| 쌍 | 만드는 법 | 규모 | 학습 효과 |
|---|---|---|---|
| B1 인용 문장 ↔ 대상 조 | 인용 표현을 `[인용]`으로 가린 문장(의미 검사 2단계의 질의와 같은 형태)과 설명구 「…에 따른 X」의 X → 대상 조. **정상 연결된 인용만**, 점검 결과 279건의 위치는 제외 | 381 (설명구 있는 것 약 85) | 사람이 쓴 문장이라 실제 말투. 「X」만 짧게 묻는 질의에 강해짐 |
| B2 조 제목 ↔ 조 본문 | 제목(「육아휴직」, 「직위해제」)을 질의로, 그 조 항 청크를 정답으로 | 2,052조 | 짧은 키워드 질의 |
| B3 용어 ↔ 정의 항 | 「“X”란 …을 말한다」의 X → 정의 항 | 약 200 | 용어 질문 |
| **B4 같은 주제 다른 규정** | 같은 제목의 조 그룹(인사규정 육아휴직 ↔ 취업규칙 육아휴직)을 **다중 정답**으로 묶어, 한 질문이 두 규정의 조를 모두 정답으로 | 90그룹·287조 | 놓친 근거의 36%인 **다른 규정 근거** 정면 겨냥 |
| B5 규정 ↔ 위임받은 지침 | 문서 인용·위임 edge | 약 200 | 규정 질문에서 지침 조 끌어오기 |
- 구조 쌍은 합성 질문보다 **정답 확실성이 높아** 학습 초반 안정화에 쓴다. 단, 점검에서 오류로 잡힌 인용(대상 불일치 125, 대상 없음 56 등)은 오답 라벨이 되므로 반드시 제외.

### C. 복합 질문 (다중 근거, 약 2,000쌍)
- 근거가 둘 이상인 질문(평가셋의 32%)을 겨냥해, **두 청크를 함께 보여 주고 둘 다 필요한 질문**을 쓰게 한다. 조합: ① 같은 규정 안 서로 다른 조(예: 본문 조 + 별표) ② B4의 같은 주제 다른 규정 쌍 ③ 같은 조의 서로 다른 항(조 묶기 효과를 임베딩이 배우도록).
- 두 청크 모두 정답으로 라벨(multi-positive). 한쪽만 답이 되는 질문이면 버린다.

### D. 운영 로그 (후속, 지금은 안 씀)
- 「도움이 됐어요/아니에요」(`web_feedback.jsonl`), 화면에서 열어 본 근거, **개정 담당자가 영향 카드를 수락·기각한 기록**(`amend.decision_log`)은 실제 사용자·담당자가 붙인 관련성 라벨이다. 양이 쌓이면 재튜닝 데이터로 쓴다(지금은 40건 수준이라 학습에 못 씀).

## 4. 청크 문서의 모양 (색인 입력과 같게, 그리고 비교 실험)
지금 색인 입력은 `[장·절 경로] + 보정 반영 본문`이고 **규정명은 넣지 않는다.** 청크 중앙값이 87자라 이 선택이 크게 작용할 수 있다. 학습 쌍의 문서 텍스트를 세 가지로 만들어 **같은 조건에서 비교**한다(모양을 바꾸면 재색인이 필요하므로 §10-7의 별도 벡터 표에 둔다).
| 모양 | 내용 | 비고 |
|---|---|---|
| v0 (현행) | `[장·절 경로] + 본문` | 가빈 색인과 동일 |
| v1 | `조 제목 + 본문` | 「제30조(육아휴직) 육아휴직 기간은…」 |
| v2 | `규정명 > 장 > 조 제목 + 본문` | contextual retrieval 방식 |
- 학습 입력은 **색인 입력과 같은 함수로** 만든다. 달라지면 검색 때 학습한 것과 다른 분포를 보게 된다.

## 5. 질문 품질 규칙 (생성 프롬프트)
- 모델: 개발 중 luna 또는 로컬 30B. 온도 0.7, 청크 하나에 1회 호출, JSON으로.
- 출력: `{"questions":[{"q","style":"구어|상황|검색어|격식|수치|예외","swapped":"질문 속 바꿔 쓴 말 → 조문 속 원래 말"}]}`
- 프롬프트에 넣을 것: 역할(「직원이 규정 도우미에게 묻는 질문」), 스타일 배분, 핵심어 바꿔쓰기, 길이, 조 번호·규정명 금지, 「청크만으로 답 가능」, 법령 내용·개인 사정 질문 금지.
- **넣지 않는 것:** 「~맞죠?」식 잘못된 전제 질문, 규정에 없음·개별사정 유형(정답 청크가 없음), 삭제 상태 확인 질문.

## 6. 라벨 단위와 어려운 오답 — 조 단위로
- **정답 = 그 항이 속한 조의 모든 항 청크.** 평가가 조 단위(같은 조 묶기)이므로 학습도 같게 한다. 같은 조의 다른 항은 오답으로 쓰지 않는다(정답 후보이므로 라벨 잡음).
- **배치 구성:** 한 배치에 같은 조의 청크가 둘 이상 들어가지 않게 한다(배치 내 오답 마스킹). 구조 쌍·복합 질문은 multi-positive 손실(정답 여러 개 중 하나라도 높으면 됨).
| 어려운 오답 | 만드는 법 | 비율 |
|---|---|---|
| 같은 규정의 다른 조 | 기본 모델로 질문 검색 상위 20 중 정답 조 제외 | 25% |
| **다른 규정의 같은 주제 조** | 상위 20 중 정답 규정이 아닌 것. 단 B4 같은 주제 쌍이 이 질문의 정답이면 제외 | 35% |
| 같은 낱말 다른 대상 | 「직원」 질문 vs 「임원」 조문 (답변 프롬프트 규칙 10의 함정) | 15% |
| **인용 관계로 이어졌지만 정답이 아닌 조** | 정답 조가 인용하거나 인용받는 조(관계 표)를 오답으로. 「제35조에 따른」을 물을 때 인용하는 쪽 조가 정답으로 끌려오는 경우를 가르침 | 15% |
| 무작위 | 배치 내 다른 청크 | 10% |
- **false negative 방지(핵심):** 오답 후보가 사실 질문의 답이 될 수 있으면 학습을 망친다. 기본 모델 점수가 정답보다 **높은** 후보는 쓰지 않고, 애매하면 luna에게 「이 질문에 이 조문이 답이 되는가」를 물어 「그렇다」면 버린다.

## 7. 품질 검사 (자동 → 사람)
1. 형식(JSON, 10~80자, 한 줄, 조 번호·규정명 미포함). 2. 핵심어 바꿔쓰기 확인(`swapped`가 조문에 없는 말인지). 3. **왕복 검사**: 기본 BGE-m3로 검색해 정답 조가 상위 100 밖이면 버림, 상위 3 안의 쉬운 질문이 70%를 넘으면 일부 덜어 냄(학습 신호는 상위 4~50에서 가장 많이 나온다). 4. 같은 청크 질문끼리 코사인 0.92 이상 중복 제거. 5. **평가셋 누출 검사**: 평가 질문 전체와 코사인 0.88 이상이거나 글자 3-gram 겹침 0.6 이상이면 버리고 수를 기록. 6. 사람이 무작위 100쌍 확인(「답이 된다 / 아니다 / 모호」 중 아니다+모호 10% 이하).

## 8. 저장
`data/embedding/pairs_v1.jsonl`(git 제외), 한 줄 한 쌍.
```json
{"id": "P00001", "src": "A|B1|B2|B3|B4|B5|C", "q": "…", "form": "구어|상황|검색어|격식",
 "pos": ["24024_제30조_1항", "24024_제30조_2항"], "negs": [{"chunk_id": "…", "kind": "다른 규정 같은 주제", "base_rank": 7}],
 "easy": false, "split": "train", "gen": {"model": "…", "seed": 1, "prompt": "v1"}}
```
분할은 **규정(문서) 단위**로 10%를 튜닝 검증으로 뗀다. 통계 `pairs_v1.stats.json`(커밋 가능): 층별·형태별·규정별 개수, 쉬운 질문 비율, 거른 수와 사유, 누출 검사 탈락 수.

## 9. 총량
합성 질문 약 12,000 + 구조 쌍 약 3,000 + 복합 약 2,000 = **약 17,000쌍**. 8GB GPU에서 LoRA로 1~2시간 안팎(청크가 짧아 빠름).

## 10. 파인튜닝 설계
**순서:** ① 기준선 재현 → ② 임베더 LoRA → ③ 리랭커 → ④ 하이브리드 재조정 → ⑤ 적용 방식 결정.
1. **기준선 4종:** BGE-m3(현행), BGE-m3-ko(이미 내려받아 있음), 현행+문서 모양 v1·v2(튜닝 없이 모양만 바꾼 것). **튜닝 전에 이 중 모양 바꾸기만으로 얼마나 오르는지부터 본다**(싸다).
2. **임베더:** LoRA(r 16~32, 주의 q·k·v·o + 출력 dense), 손실은 MultipleNegativesRanking의 캐시 방식(GradCache로 배치 128 이상을 8GB에서), hard negative, 최대 길이 256토큰(청크 90%가 222자), fp16, 학습률 1e-4(LoRA), 1~2 에폭. 질문 두 형태(구어·검색어)를 같은 모델이 학습. 에폭마다 튜닝 검증·개발용 후보 Recall로 확인. 현재 환경에 `peft`가 없어 설치가 필요하다.
3. **망각·과적합 방지:** WiSE-FT식 **가중치 보간**(기본 모델과 튜닝 모델을 α로 섞고 α를 검증 세트로 정함). 회귀 세트: 정확 조회형 질문(「인사규정 제30조」), 법령명 질문, 규정에 없는 질문(엉뚱한 근거가 올라오지 않는지).
4. **리랭커:** `bge-reranker-v2-m3`를 같은 쌍으로 LoRA 튜닝. 입력은 현행 그대로 `[문서명 조항] 본문`, hard negative는 **튜닝한 임베더가 상위 30에 올린 오답**. 목표는 Hit@1·Hit@3(상한 0.94 대비 현재 0.41·0.74). 임베더가 후보 상한을, 리랭커가 순서를 맡는다.
5. **하이브리드 재조정:** 튜닝 뒤 RRF 가중치를 다시 스윕(벡터 단독, 0.9:0.1, BM25는 리랭커 후보에만 보태기). 지금 BM25가 Hit@1을 낮춘 문제(0.51→0.40)가 튜닝 후 달라지는지 본다.
6. **질의 쪽:** 질문 나누기의 하위 질문(항목 하나만 묻는 짧은 질문)도 학습 형태에 넣는다. 질문 나누기가 꺼진 지금 구성에서도 무해.
7. **적용 방식(우리 구조에 맞게):** 튜닝 벡터를 `amend.chunk_vec(chunk_id, model, form, vec vector(1024), built_at)`에 적재하고 `public.chunks`는 건드리지 않는다. 가빈 검색은 설정으로 어느 벡터를 읽을지 고르면 된다(`embedding_model` 열의 이름·버전으로 구분). 규정이 개정되면 **바뀐 청크만 재임베딩**, 재튜닝은 개정이 누적됐을 때.
8. **우리 에이전트도 같은 모델을 쓴다:** 변경안 점검의 의미 유사 후보(`change_check`의 벡터), 의미 검사 1단계(`vector_check`), 법령 대조 카드의 관련 법조문 고르기(`web_law.related`, 지금은 글자 2-gram 코사인)를 튜닝 모델로 바꾸고 골든셋·과거 재현(정답 5/5)에서 효과·회귀를 본다.
9. **함께 비교할 대안(같은 합성 질문 사용):** (a) **doc2query**: 튜닝 없이 합성 질문을 청크 옆에 색인에 붙임 — 데이터 한 번으로 두 방식을 비교한다. (b) bge-m3의 sparse·multi-vector 모드 병행. (c) 전체 파인튜닝은 8GB에서 어려워 제외.

## 11. 평가 (튜닝 전후, 같은 조건)
| 지표 | 대상 | 세트 |
|---|---|---|
| 후보 Recall@30·50·100 (조·별표 단위 정답 근거 재현율) | 벡터 단독, RRF 합침 각각 | 개발용 → 최종 시험용 |
| 최종 근거 Recall (k=8, 16) | 리랭크·조 묶기 뒤 | 개발용 → 최종 시험용 |
| Hit@1·Hit@3·MRR | 순위 품질 | 개발용 → 최종 시험용 |
| 에이전트 쪽 회귀 | 과거 정답 5/5, 변경안 골든셋(NUMC·INS·CLEAN), 법령 대조 카드 | 우리 평가 |
- **성공 기준(미리):** 개발용과 최종 시험용 **둘 다**에서 후보 Recall@30 **+5%p 이상**이고, BGE-m3-ko보다 높을 것. 한쪽만 오르면 과적합. 회귀 세트에서 이미 맞던 질문이 틀어지면 α를 낮추거나 접는다.
- 문항 수가 적어(개발용 100문항, 근거 약 160개) 차이에 ±4%p 정도 잡음이 있다. 부트스트랩 신뢰구간을 같이 적고, 최종 판단은 시험용 170문항 합산으로 한다.

## 13. 위험과 대비
| 위험 | 대비 |
