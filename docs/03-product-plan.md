## 목적

폐쇄망에서는 법률 API를 쓸 수 없어 법령이 바뀌어도 규정이 따라가지 못하는 경우가 생긴다.
규정 개정이 쌓이면서 조문 번호, 인용, 명칭이 어긋나는 문제도 함께 찾는다.
규정 관리 담당자에게 잘못된 조항과 수정안을 제시한다.

| 항목 | 내용 |
|---|---|
| 사용자 | 규정 관리 담당 부서 |
| 입력 | 규정 전체, 반입된 법령 변경분 |
| 출력 | 영향받는 규정 조문, 개정된 법조문, 오류 유형, 신·구조문대비표 형태의 참고 수정안 |
| 핵심 데이터 | 법령·규정 RDB (폐쇄망 반입) |
| 최종 판단 | 담당자가 변경 단위로 수락·거절, 원문은 개정 절차로만 변경 |

## 범위

- 포함: 법령 개정 영향 분석, 규정 내부 점검(내부 참조, 규정 간 인용, 구 명칭, 용어 정의, 근거 소멸), 암묵적 관련 검토, 신·구조문대비표 형태의 참고 수정안, 검토 화면
- 다른 담당: 법령 RDB 구축과 반입 흐름(한석희), 챗봇형 RAG(김가빈)
- 제외: 원문 자동 수정(수정은 초안 사본에만), 법적 판단, 책임·권한 공백 점검(후속 과제)
- 형태: 챗봇이 아니라 사건 기반 점검 파이프라인 + 검토 화면

## 근거 사례 (1주차 검토, 담당 21건)

원문: `data/한국벤처투자_내부규정/최종_문제목록_노션용.md`, `검토결과_노션용.md`, `외부법령_참고_노션용.md`

| 분류 | ID | 대응 오류 유형 |
|---|---|---|
| 고칠 수 있음 | F1~F6 | 내부 참조 오류, 규정 간 인용 오류 (조문 번호 오인용) |
| | F7~F11 | 오타, 규정 명칭 불일치 |
| | F12~F13 | 구 명칭·용어 잔존 |
| 판단 가능 | J1~J7 | 규정 간 충돌 (양쪽 조문 표시) |
| 판단 불가 | X1~X7 | 수정안 없음, "담당 부서 확인 필요" |
| 법 개정 확인 | E1~E5 | 법령 개정 미반영·법령 내용 불일치 후보 |

## 운영 방식 (기관 도입 시 제안안)

근거: [261006-1414-06](reports/261006-1414-06-operation-poc.md). 반입 주기·우선순위·처리 기한은 기관이 정할 사항이며 아래는 가정이다.

| 계기 | 시점 | 에이전트 | 받는 쪽 |
|---|---|---|---|
| 법령 반입 | 정기(예: 주 1회) + 긴급 수동 | 바뀐 법조문 → 영향 조문 | 준법감시인, 업무담당부서 |
| 내규안 입안 | 초안 제출 시 (제20조) | 변경분 점검 → 새 이슈만 | 제21조 조정 협의 자료 |
| 개정 시행 | 시행일 (제23~24조) | 원문 DB 갱신, 재점검, 해소 이슈 자동 종료 | 내규담당부서 |
| 정기 정비 | 분기·반기 (제25조②) | 전수 점검, 기준선 갱신 | 내규담당부서 |

- 역할: 업무담당부서(소관 이슈 1차 검토, 내규안 입안), 내규담당부서(현황판, 배분, 해석 불분명 건, 직권 일괄 정비), 준법감시인(법령 관련 이슈), 에이전트(탐지·표시·참고 문안, 결정 안 함)
- 이슈 흐름: 신규 → 배분 → 검토 중 → 승인(→ 내규안 반영 → 시행 후 해소) / 기각 / 오탐(숨김) / 판단 불가(→ 확인 요청). 전환마다 검토자·일시·의견 기록
- 우선순위: 높음(법령 개정 미반영, 근거 소멸) / 중간(충돌, 용어 정의, 오인용) / 낮음(구 명칭, 명칭 불일치, 오타 → 직권 일괄 정비, 제20조③3호)

### 초기 도입 (설치 직후)
1. 준비: 원문 적재 검증, 규정별 소관 부서 매핑, 법령 기준일, 역할 지정
2. 보정: 결과 비공개로 표본 검토, 유형별 정밀도 측정, 기준 미달 유형은 비공개 후 규칙 조정
3. 묶음 정리: 같은 원인(번호 밀림), 같은 매핑(구 명칭), 같은 질문(판단 불가 질의서), 오탐 숨김
4. 단계적 배분: 우선순위 높음부터, 부서별 소관만
5. 기준선 고정: 이후 변경분만 보고, 기존 미해결은 따로 추적

## 수정 방식

에이전트가 초안 사본(changeset)에 신·구조문대비표를 만들고 사람이 변경 단위로 수락·거절한다. 원문은 개정 절차로만 바뀐다.
유형별 범위: 기계적 수정(오타·명칭·확실한 번호)만 문안, 법령 내용 변경은 나란히 표시만, 충돌·용어는 선택지별 문안(선택 안 함), 판단 불가는 질의서. 상세: [261006-1414-06](reports/261006-1414-06-operation-poc.md)

## 화면

| 화면 | 내용 |
|---|---|
| 현황판 (내규담당부서) | 규정별 미해결 수, 유형·우선순위 분포, 마지막 점검일, 최근 반입 |
| 이슈 목록 (업무담당부서) | 소관 규정만, 유형·상태 필터 |
| 이슈 상세 | 문제 조문, 인용 대상 조문·법조문 버전, 근거, 영향 범위 그래프, 신·구조문대비표, 수락·거절·의견 |
| 변경안 점검 | 초안 조문 입력 → 새 이슈 / 해소 이슈 |

대화 기능은 이슈 상세의 "왜 걸렸나" 설명(근거 범위 안)과 변경안 자연어 입력 두 곳만.
팀 시연은 앱 하나에 챗봇 탭(김가빈)과 점검 탭(박형건), 연결 장면은 "승인된 이슈가 챗봇 답변에 주석으로 표시".

## PoC 범위 (10.20 발표)

"설치 첫날" 시나리오 하나를 끝까지 동작시킨다.

| 구분 | 내용 |
|---|---|
| 반드시 | ① 담당 21건 기준선 점검 + 1주차 정답 대조(정밀도·재현율) ② 이슈 상세: 신·구조문대비표 + 수락·거절 ③ 법령 스냅샷 2개로 영향 조문 시나리오 1개 ④ 변경안 1건 → 새 이슈·해소 이슈 |
| 가능하면 | 90건 기준선, 오류 주입셋 재현율, 원인 묶음 표시 (건수 vs 묶음 수) |
| 그림으로만 | 역할별 화면 분리, 현황판, 개정 시행 재점검, 운영 절차, 초기 도입 단계 |

법률 DB가 늦으면 ③은 손으로 만든 법령 스냅샷으로 대체한다. UI는 Streamlit 수준.

## 평가 설계

- 정답 두 종류
  - **실제 사례:** 1주차 검토 결과 + 2020년 벤처투자법 시행으로 다른 법률에서 옮겨진 조항을 KVIC 규정이 아직 옛 법률로 인용하는지 확인한 결과
  - **주입 사례:** 법조문 버전을 바꿔 규정이 개정 전 조문을 인용하게 만들거나, 규정 조문의 인용 번호·금액·규정명을 바꿔 심은 오류. 주입 위치를 알고 있으므로 탐지율·오탐률을 정확히 계산
- 지표: 영향 조문 탐지 정밀도·재현율(명시적 인용과 암묵적 관련 분리), 오류 유형별 정밀도·재현율, 참고 수정안 채택률, 실제 사례 탐지 건수
- 비교 실험: RDB 조인 기반 영향 분석 vs 법령 전문 벡터 검색 + LLM vs LLM 단독(규정과 법령 전문 제공)
- 실제 오류 목록은 결과물로 보고하고, 성능 평가는 주입 오류로 따로 한다. LLM 채점을 쓰면 같은 입력 재채점 일치율을 함께 보고한다
- 결과는 오류 유형별로 바로 사용 가능한 유형과 법무·규정 담당자 확인이 필요한 유형으로 나눈다

## 미결 사항 (원본 기획 중 이 작업 관련)

- RDB 엔진 (SQLite / PostgreSQL) — 한석희와 합의
- 로컬 LLM 선정 (캐시된 후보: Qwen2.5-3B-Instruct). GPU는 RTX 4070 8GB 확인
- 규정 인용 법령 목록 추출과 대상 법령 범위 확정
- 벤처투자법 시행 전 법률을 인용한 규정 조문 잔존 여부
- ALIO 이전 개정본 확보 가능 여부
- 법령 데이터 이용 조건
- 수정안 승인 평가자 지정
- 두 방향(챗봇 / 수정 에이전트) 중 메인 결과물 선택
