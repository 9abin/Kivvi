## 요약
DB를 원문·관계(그래프)·의미·점검 4계층으로 나누고, 원본 기획의 `citation`·`reg_law_citation`을 `edge` 하나로 합쳤다.
새 조항이나 수정안은 전체를 탐색하지 않고 인덱스로 후보를 모은 뒤 후보에만 LLM을 쓴다.
기존 오류는 원문을 고치지 않고 기준선으로 쌓고, 이후에는 변경분만 보고한다.

## 주요 결정
| 결정 | 이유 | 대안 |
|---|---|---|
| 4계층: 원문 / 관계 / 의미 / 점검 | 원문은 공유·불변, 나머지는 에이전트 산출물. 갱신 주기와 담당이 다름 | 원본 기획의 평면 테이블 |
| `edge` 하나로 인용·위임·준용·정의·버전 대체·법 이관·명칭 변경 표현 | 다단계 영향과 NetworkX 적재가 한 질의로 끝남. 그래프 DB로 옮길 때도 형식 그대로 | 유형별 테이블 |
| `edge`에 적힌 대상과 의도 대상을 따로 둠 | 오인용(F1)을 원문대로만 연결하면 실제 대상 조문 개정 시 영향 범위에서 빠짐 | 원문대로만 연결 / 원문 수정 |
| `slot`(주제키·대상·속성·값) 테이블 | J1처럼 서로 인용하지 않는 충돌 조문을 키 조회로 묶음. 회계규정 제29조와 이사회규정 제3조②5호 사이에는 엣지가 없음을 확인 | 벡터 검색만 사용 |
| 수정안을 `article_version`에 초안 상태로 저장, `changeset`으로 묶음 | 원문을 건드리지 않고 "현행 + 초안" 상태를 시뮬레이션 | 별도 초안 테이블 |
| 변경 점검은 7개 경로로 후보 수집 → 후보에만 LLM | 전수 LLM 비교는 약 300만 쌍. SQL·벡터 전수는 싸지만 LLM이 병목 | 전수 비교 |
| finding에 발견 경로 기록 | 경로별 기여도와 후보 재현율 측정 | 기록 안 함 |
| 기준선 + 변경분 운영 | 원문 수정 권한은 회사(내규관리규정 제20~24조). 기존 이슈가 매번 다시 잡히는 소음 제거 | 원문 선수정 후 구축 |
| 별지는 `form`으로 본문과 분리 | 계약서형 서식이 자체 「제1조」를 가져 조문 분할·내부 참조 점검을 오염시킴 | 본문과 같은 단위 (이전 문구, 폐기) |
| 엔진은 PostgreSQL + pgvector 권장 | 역방향 인덱스, 재귀 질의, 벡터 검색, 법률 DB 조인을 한 곳에서 | SQLite + 벡터 확장 |
| 그래프 분석은 NetworkX, 그래프 DB 미도입 | 노드 약 2.5천, 엣지 수천. 그래프는 묶음 생성 역할이고 판정은 규칙·LLM | Neo4j, Apache AGE(예비안) |

## 초기 구축 순서
1. 원문 90건을 오류 포함 그대로 적재
2. `edge` 추출: 적힌 대상으로 연결, 해석 실패·의심 표시
3. 기준선 전수 점검 → 기존 이슈 목록
4. 선별 검토: 담당 21건은 1주차 정답과 대조(정밀도·재현율), 나머지 69건은 확실한 규칙 탐지부터
5. 승인 결과 → 의도 대상, `term`, 기존 이슈 목록에 반영 (원문 불변)
6. 이후 변경은 변경분만 점검

## 평가 관련
- 사람이 에이전트 결과를 검토하면 정밀도만 나온다. 재현율은 21건 정답과 주입셋으로만 잰다.
- 후보 수집의 재현율(실제 문제 조문이 후보에 들어왔는가)을 따로 잰다. 후보 수 대비 재현율이 비교 실험 항목이 된다.
- 명시 엣지만 vs 명시 + 유사 엣지의 충돌 탐지 재현율 비교로 그래프 접근의 효과를 보인다.
- 데모 시나리오: 기준선 N건 → 수정안 1건 입력 → 새 충돌 발견, 기존 이슈 해소 표시.
