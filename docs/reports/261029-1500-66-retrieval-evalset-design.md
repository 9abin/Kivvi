## 요약

## 1. 무엇을 주장하려는가 (범위)
| 주장 | 평가셋이 있어야 말할 수 있는가 |
|---|---|
| 온톨로지가 질문-조문 표현 차이를 메워 후보 recall을 올린다 | 예 (유형별 recall) |

충돌 점검의 효과는 이 평가셋으로 말하지 않는다. 그건 전문가 판정 데이터가 따로 필요하다.

## 2. 기존 세트(r3·v4)의 사실과 한계
받은 파일에서 확인한 것:
- 각 30문항 = **10작업 × 3변형**(Q-1~3). 세 변형은 같은 정답 세트를 공유한다. r3는 T01~T10, v4는 T11~T20. 유형은 r3가 규정내 9·규정간 9·개정법령 12, v4가 법령본문 9·상하위규정 9·조문개정이력 6·규정간병행 6.
- 필드: `id, q, 유형, 변형, 작업, 답가능여부, 근거[{규정, 조항, tier, 항?}], 출처, 확인필요`. 정답은 조 단위(`조항`: 제N조, 별표N)이고 항은 참고로만 붙는다.
- `tier`는 전부 `필수`(117, 105개)이고 `답가능여부`는 전부 `가능`이다. 보조 정답과 무정답 문항의 선례가 없다.
- **`법령근거` 필드가 없다.** v4 설명에 "법령 조문은 정답에 넣을 수 없다"고 적혀 있다. 검색 색인(`regulations`, 내부규정 90건)에 법령이 없고 법령 원문은 별도 SQLite에만 있어 측정 키(`문서명:제N조`)로 맞출 대상이 없기 때문이다.
- v4는 "기준선 결과를 보고 문항을 고르거나 고치지 않았다"고 명시했다. 다만 어느 세트도 온톨로지 설계와 독립이라고 할 수 없다.

한계:
- r3·v4는 기존 검색이 놓친 유형에서 스키마를 설계했다. 같은 문항으로 설계하고 평가한 셈이라 낙관적일 수 있다 (건강검진, 괴롭힘, 임금피크제, 업무 식사가 곧 T14, T12, T19, T20).
- **문항이 독립이 아니다.** 한 작업이 3문항이므로 파일당 유효 표본은 10작업이다. 한 작업이 10%포인트다 (이전 초안의 "한 문항 4~5%포인트"는 과소평가).
- **결정: r3·v4는 개발셋으로 내린다.** 설계·튜닝·오류 분석은 여기서 한다.

## 3. 세트 구성
| 세트 | 용도 | 크기 | 열람 |
|---|---|---|---|
| 개발셋 | 기존 r3·v4 (T01~T20) | 60문항 / 20작업 | 자유 |
| 검증셋 | 방식 선택(순위·예산 규칙, 소스별 ablation) | 30문항 / 10작업 | 자유, 봉인셋과 주제가 겹치지 않음 |
| **봉인셋** | 최종 보고 | 60문항 / 20작업 | 동결 후 **한 번만** 연다 |

**규정 전체가 아니라 조·주제 단위로 나눈다.** 병행 규정, 상위→하위 위임, 복수 제도 문항은 인사규정·취업규칙·복무규정·급여규정·여비규정처럼 다른 규정과 많이 엮인 핵심 규정이 끼어야 만들어진다. 규정째 빼면 쿼터를 못 채우거나 그래프에 불리하지 않은 쉬운 문항만 남는다.
- 모집단: 90개 규정, 2,052개 조 (`out/parsed` 실측).
- **조 단위 제외**: 개발셋 20개 작업의 정답 조와 그 조가 다루는 제도·주제(부록 A). 예를 들어 인사규정은 쓰되 정년·국외연수 복무의무기간 조는 뺀다. 휴가·휴직 파일럿 영역도 제외한다.
- **규정 단위 제외**: 개념 추출 프롬프트 예시로 쓰는 규정. 차량관리지침, 도서관리지침, 정보보안, 문서·기록물 관리 (예시 목록은 바뀔 수 있으니 확정 시점의 목록을 부록 B에 적는다).
- 남은 조에서 질문을 만든다. 검증용·봉인용은 **주제(제도) 단위**로 가르고(같은 제도가 양쪽에 걸리지 않게), 시드와 목록을 부록 B에 기록한다. 핵심 규정은 두 세트가 서로 다른 제도를 쓰는 식으로 나눠 가진다.
- 작업 형식은 기존과 같게 한다: 작업당 정답 조 3~5개, 질문 3변형이 같은 정답 세트, 질문당 묻는 내용 2~3개.
- 표본 수 근거: 봉인 20작업이면 한 작업이 5%포인트다. 차이가 작으면 단정하지 않는다(§7).

## 4. 작업 구성 (층화, 작업 단위)
| 형태 | 설명 | 봉인셋 목표(작업) |
|---|---|---|
| 병행 규정 | 같은 사항을 여러 규정이 나눠 정함 | 3 |
| 복수 제도 동시 적용 | 한 상황에 여러 제도가 걸림 | 2 |
| 정의 위임 | 정의를 법령·타 규정에 맡김 (아래 §5 참고) | 2 |
| 상위→하위 위임 | 상위 규정이 하위 지침에 위임 | 2 |
| 일상어·별칭 | 현업 말투·줄임말 질문 | 3 |
| 조건 조가 따로 있음 | 요건·절차·금액이 다른 조 | 2 |
| **통제** | 온톨로지 개념에 안 걸리는 단일 조 질문 | 4 |
| **무정답** | 규정에 없는 내용 | 2 |

- 합계 20작업 × 3변형 = 60문항.
- 통제 작업은 온톨로지가 노이즈로 입력을 밀어내는지 보는 용도다 (이번 "나머지 문항 1~2개 줄어듦"에 해당).
- 형태 태그를 남겨 형태별 결과를 본다. 소표본이면 참고로만 쓴다.
- 쿼터는 초안이며, 라벨링 중 어려우면 조정하되 변경 이력을 남긴다.

## 5. 만드는 절차
1. **질문 작성**: 작성자가 원문을 읽고 현업 상황으로 질문을 쓴다. 조문의 낱말을 그대로 복사하지 않는다(표현 차이가 평가 대상이다). 온톨로지·검색 출력은 보지 않는다.
2. **정답 라벨**: 라벨러 2명이 독립으로 "답하려면 읽어야 하는 조"를 정한다. 원문 전체와 키워드 검색은 허용, 시스템 후보는 비공개. 각 조에 등급을 붙인다: **필수**(없으면 답이 틀림), **보조**(있으면 좋음). 기존 세트는 필수만 쓰므로 보조는 쓰면 따로 집계한다.
3. **불일치 해소**: 협의로 정하고, 불일치율과 사유를 기록한다 (라벨 품질 지표).
4. **풀링 점검**: 시스템이 찾았는데 정답에 없던 조는 사람이 다시 보고, 정답 추가가 맞으면 `추가_후보`에 따로 기록한다(주지표에는 반영하지 않고 민감도로만 본다). 시스템이 찾은 것만 정답이 되는 편향을 막기 위해서다.
5. **동결**: 파일 해시를 기록하고, 이후 수정은 새 버전으로만 남긴다.

### 파일 형식 (`eval/ret_sealed_v1.jsonl` 등)
r3·v4와 같은 필드에 새 필드만 더한다.
```json
{"id": "S01-Q-1", "q": "...", "유형": "...", "변형": "Q-1", "작업": "S01", "답가능여부": "가능",
 "근거": [{"규정": "규정 정식 이름", "조항": "제21조", "tier": "필수", "항": [1]}],
 "출처": "...", "확인필요": [],
 "형태": "병행|복수제도|정의위임|위임|일상어|조건|통제|무정답",
 "라벨러": ["A", "B"], "불일치": false, "추가_후보": [], "법령참고": []}
```
- **정의 위임은 규정 측 조만 정답**으로 한다. 법령 조문은 색인에 없어 기존 채점 키로 맞출 수 없으므로 `근거`에 넣지 않고 비채점 필드 `법령참고`에 적는다 (v4 T11~T13 방식과 같음). 법령 조문까지 채점하려면 법령 색인과 채점 키 확장이 먼저 필요하며 이번 범위 밖이다.
- 무정답 문항은 `답가능여부`를 `불가`로 하고 `근거`를 빈 배열로 둔다. 채점 코드 확인 결과(`src/combo/metrics.py`, `src/combo/answer.py`):
  - 빈 `근거`는 오류 없이 처리된다. 정답 노드가 0개라 `ndcg`는 None, 부트스트랩은 전체 수 0인 질문을 건너뛴다. 즉 **검색 recall 지표에서는 무정답 문항이 조용히 빠진다.** 노이즈 영향은 recall이 아니라 "입력에 들어온 조 수"로 따로 봐야 한다.
  - 답 단계(`answer.py:112`)는 `답가능여부 == "불가"`를 거절 정확도(`refusal_accuracy`)로 이미 센다. 무정답 문항은 이 지표로 평가된다.
  - 규정 이름은 `title_to_doc`로 문서 id에 매핑되므로 `근거[].규정`은 색인의 정식 이름과 정확히 같아야 한다.
- 위 필드 구성은 받은 두 cases 파일에서 확인했다. `answer_eval_100_tiered_v2.jsonl`도 `근거[{규정, 조항, tier}]`를 쓴다.

## 6. 지표 (층별로 따로)
| 층 | 지표 | 의미 |
|---|---|---|
| 후보 | 필수 정답 조 recall, 전부 찾은 작업 수 | 확장이 닿는가 |
| 입력 | LLM 입력에 든 필수 조 recall, 질문당 추가 조 수, 입력 슬롯 중 정답 비율 | 예산 경쟁을 이겼는가 |
| 통제 | 통제 작업의 입력 recall 변화 | 노이즈 피해 |
| 답(선택) | 사람 또는 평가 LLM의 정답 여부 | 최종 효과. 비용이 크니 봉인셋 한 번만 |

비교 조건: ① 기존 검색 ② +구조 그래프 ③ +온톨로지 ④ 소스별 ablation(개념·별칭·위임 규칙·계층 확장). 같은 문항에 쌍 비교한다.

## 7. 보고 규칙
- 작업별 표(어느 작업이 +/−)와 이긴·진 작업 수를 같이 낸다. 합계만 내지 않는다.
- **같은 작업의 3변형은 같은 정답을 공유하므로 작업 단위로 묶어 센다.** 부트스트랩도 작업 단위로 다시 뽑는다. 문항을 독립 표본으로 세면 구간이 실제보다 좁게 나온다.
- 현재 `bootstrap`·`paired_diff`(`src/combo/metrics.py:79,93`)는 **질문 단위로 복원 추출**한다. 이대로 쓰면 구간이 과소평가되므로, 작업(`작업` 필드) 단위로 묶어 뽑는 변형이 필요하다. 이것이 비교 스크립트의 첫 수정 지점이다.
- 쌍 비교의 부트스트랩 구간 또는 부호 검정을 붙인다. 구간이 0을 포함하면 "차이 확인 안 됨"이라고 쓴다.
- 입력 층에서 이득이 없으면 후보 층 결과만으로 효과를 말하지 않는다.

## 8. 누수 방지
- 봉인셋은 동결 전에 개발·튜닝 코드에서 읽지 않는다. 한 번 열어 결과가 나쁘면 그대로 보고하고, 같은 셋으로 재튜닝하지 않는다. 다시 만들 때는 새 봉인셋을 쓴다.
- 질문 작성자와 온톨로지 구축자를 가능하면 분리한다. 같은 사람이면 그 사실을 보고서에 적는다.
- 추출·정규화 프롬프트의 예시는 평가 규정 밖에서만 고른다.
- 놓친 조를 보고 개념·관계를 손으로 넣지 않는다.
