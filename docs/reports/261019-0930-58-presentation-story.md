## 요약
발표 이야기를 「규정 챗봇(RAG)을 만들다 문서 문제를 발견 → RAG로는 문서끼리의 모순을 못 푼다 → 챗봇 안에 개정 지원 도구를 넣었다」로 정했다.
웹 화면도 이 이야기에 맞췄다. 담당자 · 승인권자는 「개정 업무」 첫 화면(흐름 · 시작하는 곳 · 할 일)에서 시작하고, 개정 요청은 전용 대화로 연다.
답변 · 개정안 작성 모델은 API(gpt-5.6-luna)로 바꿨다. 폐쇄망 운영은 환경변수로 로컬 모델로 되돌린다.

## 발표 스토리

1. **배경**: KVIC는 업스테이지와 외부 사용자 대상 AI 서비스를 준비 중이다(기사). 첫걸음으로 직원용 **내부 규정 챗봇(RAG)**을 만들었다.
2. **발견**: 데이터를 확인해 보니 규정끼리 맞지 않는 곳이 있었다.
   - 예: 육아휴직 분할 — 취업규칙 제43조② 「3회, 휴직 단위 총 4회」 대 인사규정 제30조② 「최대 2회, 휴직 단위 총 3회」. 챗봇 답에 두 규정이 함께 나온다.
   - 틀린 조 번호 인용, 옛 법령명도 있다.
   - 꾸준히 개정돼 왔는데도 남아 있었고, ALIO 공시 다른 공공기관(창업진흥원 · 기술보증기금) 규정에서도 같은 유형이 보였다(건수 비교는 안 함).
   - **실측 근거 (리포트 59, Q072)**: 같은 질문에 로컬 30B는 「최대 3회」와 「최대 2회」를 섞어 썼고, luna는 「두 규정이 서로 다르게 규정되어 있다」고 정확히 답했다. 그래도 둘 다 오답 판정 — 정답지가 한쪽만 요구한다. **규정끼리 다르면 어떤 모델도 정답을 낼 수 없다.**
3. **원인 추측**: 규정을 소홀히 해서가 아니라 구조가 복잡해서다. 90건이지만 본문 조 인용만 376곳이 얽혀 있어, 한 조를 고치면 인용하는 곳 · 같은 제목 조 · 현행 법령까지 봐야 한다. 사람이 읽을 수는 있지만 시간이 많이 든다. 가설: 다른 업무가 많은 담당자가 개정 한 번에 연쇄 영향까지 다 챙기기 어렵다.
   - RAG는 「문서에 뭐라고 써 있나」에는 답하지만 「문서끼리 맞나」는 풀지 못한다. 답의 품질은 문서 품질을 넘지 못한다 → 문서를 고쳐야 한다.
4. **해결**: 별도 시스템이 아니라 **같은 대화창에 개정 지원 도구 하나**를 넣었다. 목표는 「고치면 어디에 영향이 있는지 확인 · 판단하는 시간」을 줄이는 것.
   - 질문은 RAG가, 개정 담당자의 「○○규정 제△조를 이렇게 바꿔줘」는 개정 도구가 맡는다.
   - 도구: 고칠 조문 찾기 → 개정문 · 신구대비표 → 깨지는 인용 연쇄 수정 → 영향 카드(인용받는 곳 · 같은 제목/비슷한 내용 · 법령 대조).
   - 업무: 담당자 카드 결정 · 제출 → 승인권자 승인 · 반려 → 공포 → 함께 고칠 규정은 새 초안. 법령이 바뀌면 변경 감시에서 시작.
5. **원칙**: 법적 판단을 하지 않는다. 개정문은 참고 문안이고 자동 반영하지 않는다. 충돌은 판정하지 않고 양쪽 조문을 보여 준다. 업무 판단이 필요한 부분은 **현업 검수(UAT) · 향후 과제**로 둔다.
6. **근거 수치**
   - 자연어 개정 요청 120건, 의도에 맞게 쓴 건수: 로컬 7B 93 · 로컬 30B 108 · API(luna) 116 ([57](261018-2000-57-llm-citation-review.md))
   - LLM 인용 검토(KVIC 전체): 확인 후보 76건, 정답 원장의 인용 오류 13/15 포함, 원장에 없던 오류 후보 12~15건 ([57](261018-2000-57-llm-citation-review.md))
   - 답변 시간: luna 약 10초 · 로컬 9B 약 82초 (261018 화면 실측, 질문 1~2개)
   - RAG 조합 실험 (리포트 59, 99문항): 검색은 임베딩이 정한다(bge-m3 → Qwen3-4B 최종@10 0.810 → 0.889), 병목은 답변(필수 근거 전부 확보 87문항인데 로컬 30B 정답 47 · luna 60, 오답 34 → 6). luna 점수는 채점도 luna라 상한선 참고치
7. **모델 계획**: 시연은 API(luna). 실제 후보는 업스테이지 **Solar**(1번 배경과 연결). 폐쇄망은 `CHAT_MODEL` · `DRAFT_MODEL`을 로컬 모델로 바꾼다. 검색 · 임베딩 · 리랭커는 이미 로컬이다.
8. **시연 순서**
   1. 일반 직원: 「육아휴직은 몇 번까지 나눠 쓸 수 있나요?」 → 두 규정이 다르게 나온다(2번 장면).
   2. 개정 담당자: 「개정 업무」 화면에서 흐름을 보여 준다.
   3. 「개정 요청 쓰기」 → 「인사규정 제30조 육아휴직 분할 사용 횟수를 3회로 늘려줘」 → 초안 · 영향 카드.
   4. 카드 결정 → 제출 → 승인권자로 바꿔 승인.

## 주요 결정
| 결정 | 이유 | 대안 |
|---|---|---|
| 「챗봇 + 도구 하나」로 설명 | 에이전트를 따로 내세우면 챗봇과의 관계가 애매하다. 같은 대화창에서 질문 · 개정이 나뉘는 게 업무 흐름에 맞다 | 독립 개정 에이전트 시스템으로 소개 (버림) |
| 도구 고르기는 규칙(담당자 역할 + 개정 말투, 개정 요청 대화는 전부 도구) | 잘못 고르면 「질문으로 답 받기」로 되돌릴 수 있고 예측 가능하다 | 모델이 도구를 직접 고르기 — 상위 모델에서 가능, 향후 과제 |
| 답변 · 개정안 작성 모델을 API(luna)로 | 개정 120건 의도 맞음 116 대 7B 93, 답변 시간 약 10초 대 82초. 보내는 것은 공개 규정(ALIO) 조문과 질문 · 요청뿐 | 로컬 9B · 7B 유지 — 폐쇄망 운영 시 환경변수로 되돌림 |
| 담당자 · 승인권자 첫 화면을 「개정 업무」로 | 결과 화면만 있어 어디서 어떻게 시작할지 안 보였다(사용자 지적) | 개정안 검토 화면 안에 안내만 추가 (부족) |
| 검토 요약 숫자 4칸 → 「결정할 카드 N건 중 M건 남음」 + 깨지는 인용 한 줄 + 종류별 거르기 | 이름만으로 뜻을 알기 어렵고 할 일(카드 결정)과 연결되지 않았다 | 숫자 칸 유지 + 설명만 추가 |
| 접속 정보 · 모델 이름 · 점수 같은 개발용 글자를 화면에서 뺌 | 서비스 화면에는 필요 없다. 오류는 콘솔, 모델 · 시간은 의견 기록에 남긴다 | 그대로 둠 |

- 멀티턴 고침(`app/web_chat.standalone`): 이어 묻는 질문 13건 중 다시 쓰기 4건만 되던 것 → 이어 묻기 9건 모두 다시 쓰고 새 주제 4건은 그대로.
  원인 둘 — ① 말투 규칙(그럼 · 그건 · ~는요?)으로 먼저 골라내서 「남자 직원도 쓸 수 있어?」 같은 이어 묻기를 놓침 → 이전 대화가 있으면 늘 모델에 묻는다(질문당 약 1초 더).
  ② 「이전 질문의 말을 가져왔나」 검사가 낱말을 그대로 비교해 조사(특별휴가 / 특별휴가는) 때문에 맞게 고친 것도 버림 → 앞 두 글자로 비교.
  답변 모델은 여전히 다시 쓴 질문 하나만 받는다(이전 답은 넘기지 않음 — 숫자 섞임 방지).
- 영향 카드 → 「이 조도 함께 개정」(261019): 내용으로 맞물린 다른 조(같은 제목 · 의미 유사 · 정의 용어 · 충돌 해소 등)는 AI가 문안을 정하지 않으므로, 카드에서 개정 요청 대화를 열고 「<그 조>도 함께 맞춰줘 — 원 개정안 W…: <원 요청 내용>」을 미리 채운다(원 요청의 규정 이름 · 조 번호는 빼서 고칠 조를 잘못 찾지 않게). 담당자가 고쳐 보내면 새 초안. 원 개정안과 묶어 함께 승인하는 것은 발표 후 과제(DB 연결 칸 필요).
  - 연쇄 수정 정리: ① 같은 규정 깨진 인용 = 자동(최대 4라운드), ② 다른 규정의 조 번호 인용 = 함께 개정(수락 → 공포 시 F 초안 자동), ③ 내용 연쇄 = 이 버튼(사람이 판단), ④ 여러 조를 한 요청에 = 미지원.
- 시연 전 정리: 시험 개정안 7건(W261019-*)을 기각(기록 남김, 「초안」으로 되돌릴 수 있음), W261018-210626만 초안으로 남김.
- 오타 검사 · 주제 추론 · 카드 설명 모델도 luna로(`SPELL_MODEL` · `HYPO_MODEL`). 화면의 「에이전트」 문구는 「AI」로.
- 카드 이유 문구에서 「(법률 DB 연결 후)」 삭제(`change_check.py`, 이미 저장된 카드는 `web_server.readable`에서 지움).
