## 요약
"수정 에이전트로 문서를 고치면 DB가 업데이트되고 챗봇이 그걸로 돈다"는 가정을 내규관리규정 원문으로 확인했다.
승인된 수정안은 아직 개정이 아니다. 개정은 입안 → 조정 → 결재·이사회 → 등록·공지 → 시행을 거친다.
그래서 **규정 원문 DB는 공유하고**, 각자의 산출물(챗봇 색인, 에이전트 finding)은 분리하는 것을 제안한다. 김가빈과 합의 필요.

## 근거: 내규관리규정의 개정 절차
| 조문 | 내용 | 시스템에 주는 의미 |
|---|---|---|
| 제20조 | 업무담당부서장이 내규안 입안 | 에이전트 수정안은 내규안의 **초안 자료**일 뿐 |
| 제21조①1호 | 내규담당부서장·준법감시인과 「법령등과의 저촉 또는 중복 여부」 협의·조정 | 에이전트가 정확히 돕는 단계 |
| 제22조 | 대표이사 결재로 확정, 일부는 이사회 의결, 필요하면 정부 승인 | 승인 ≠ 확정 |
| 제23조 | 사내망 게시판 등록·공지 (내규명, 개정일, 시행일) | 챗봇 DB 갱신의 실제 출처 |
| 제24조 | 확정일부터 시행, 부칙이 따로 정하면 그 날 | 시행일 전에는 옛 조문이 유효 |
| 제25조③ | 폐지·개정된 구내규도 이력 보존 | 조문 버전 관리 필요 |
| 제8조③ | 부서·기관명 변경은 개정 전까지 새 이름으로 해석 | 구 명칭은 개정 전에도 챗봇이 보정 안내 가능 |

## 판단
| 질문 | 결론 |
|---|---|
| 수정안 승인 시 챗봇 DB가 바뀌어야 하나 | **아니다.** 확정·시행 전 문안으로 답하면 틀린 안내가 된다 |
| 그럼 챗봇 DB는 언제 바뀌나 | 공지된 개정본이 들어와 **시행일이 된 때.** 에이전트도 같은 시점에 다시 점검해 finding 해소를 확인 |
| 같은 DB를 써야 하나 | **규정 원문 계층(규정·조문·조문 ID·버전)은 공유.** 조문 ID가 다르면 finding과 챗봇 인용이 같은 조문을 가리키는지 알 수 없고, 파서가 두 개면 결과가 갈라진다 |
| 무엇을 분리하나 | 챗봇 검색 색인(BM25·벡터), 에이전트의 `finding`·법령 연결. 서로 쓰지 않는다 |
| 챗봇이 에이전트 결과를 쓰나 | 선택 사항. **승인된 finding만** 원문 옆 주석으로 표시 (기획서의 "오인용·충돌 보정 매핑"). 원문을 대체하지 않고, 개정본이 들어와 해소되면 사라진다 |

## 제안 흐름
```
            ┌───────────── 규정 원문 DB (공유, 버전 관리) ─────────────┐
            │  regulation · article(시행일·종료일) · amendment         │
            └─────▲──────────────────┬────────────────────┬──────────┘
   공지된 개정본 적재│                  │읽기                 │읽기
 (제23조, 시행일 기준)│        챗봇 색인 (김가빈)      수정 에이전트 (박형건) ← 법률 DB (한석희)
            │                  ▲                     │
            │                  └── 승인 finding 주석 ──┤ (선택, 읽기 전용)
            │                                        ▼
         [사람] 내규안 입안·조정·결재·공지 ◀── 참고 수정안 · 담당자 승인
```

## 주요 결정 (제안, 합의 전)
| 결정 | 이유 | 대안 |
|---|---|---|
| 규정 원문 DB와 조문 ID 체계 공유 | 같은 조문을 가리켜야 연결 가능, 파서 이중화 방지 | 각자 DB (ID 매핑 필요) |
| 산출물 저장소는 분리 | 챗봇은 원문만, 에이전트 결과는 승인 전까지 미확정 | 한 테이블에 합침 |
| 챗봇 DB 갱신 트리거는 개정본 시행일 | 제22~24조 | finding 승인 시점 |
| `article`에 시행일·종료일 추가 | 시행 예정 개정, 구내규 이력(제25조③) | 최신본만 보관 |
