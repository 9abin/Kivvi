## 요약

「어떤 조를 고쳤을 때 영향받는 조」를 정답으로 둔 평가셋을 새로 만든다. 문항 하나는 가상의 수정 하나다. 정답은 라벨러가 규정 원문만 읽고 만들고(시스템 출력을 보지 않음), 정답마다 닿는 방식(명시 · 개념 · 암묵)을 **정답이 확정된 뒤** 코드로 분류한다. 그래서 인용 그래프, 개념 묶음, RAG가 각각 얼마나 찾는지와 RAG가 더하는 몫을 따로 잴 수 있다. AI 설명은 별도 기준표로 잰다. 전문가 검수(UAT)는 하지 않았고, 정답은 라벨러가 정한 것이다.

## 1. 왜 새로 만드는가

| 기존 자산 | 쓸 수 없는 이유 |
|---|---|
| `eval/scenarios` S01~S03 | 3건뿐이고 정답이 인용 표에서 나왔다(S03은 출처가 「인용받음 13건」). 시스템이 쓰는 표로 정답을 만들었으므로 재현율이 자명하게 높다 |
| 과거 개정 동시 변경(개정 표지) | 「같이 바뀐 조」이지 「영향받은 조」가 아니다. 인용 도달률 0.8~4%로 낮게 나왔고, 그것은 탐지 실패가 아니라 정답이 부적합해서다 |
| 이동 · 삭제 반영 분석 | 표지 있는 이동 44건, 현재 인용이 남은 것 5건. 사후 점검 사례로만 쓴다 |
| 검색용 평가셋(66) | 질문에 답하는 검색용이라 「고친 조 → 영향받는 조」 구조가 아니다 |

## 2. 구성

문항 24개. 영향 있는 수정 20개와 영향 없는 수정(통제) 4개.

| 분할 | 문항 | 쓰임 |
|---|---|---|
| 개발 | 8 (영향 6, 통제 2) | 규칙 · 설정 조정. S01~S03을 정답만 다시 만들어 포함 |
| 봉인 | 16 (영향 14, 통제 2) | 한 번만 실행. 개발 규정 · 주제를 피한 별도 규정에서 작성 |

수정 종류(영향 있는 20개 기준):

| 종류 | 개수 | 예 |
|---|---|---|
| 값 변경 | 6 | 기한 · 횟수 · 금액 숫자 변경 |
| 삭제 | 4 | 조 삭제 |
| 번호 이동 · 신설 삽입 | 4 | 조 신설로 뒤 조 번호가 밀림 |
| 정의 변경 | 3 | 용어 정의 수정 |
| 위임 · 법령 변경 | 3 | 위임받은 조 변경, 인용 법령 개정 |

통제 4개는 영향이 없다고 라벨러 둘이 합의한 수정(표현만 바꿈, 고립된 조의 문구 수정 등)이다. 후보를 쏟아내는 시스템이 점수를 올리지 못하게 하는 장치다.

## 3. 문항 형식 (`eval/impact_cases_YYYYMMDD.jsonl`)

한 줄에 문항 하나.

```json
{"id":"I01","분할":"개발","수정":{"규정":"인사규정","조":"제30조","항":2,"종류":"값 변경","개정문":"제30조제2항 중 \"최대 2회\"를 \"최대 3회\"로 한다."},
 "영향":[{"규정":"취업규칙","조":"제43조","항":2,"이유":"같은 육아휴직 분할 횟수를 다르게 정함","라벨러":["A","B"]}],
 "무영향_확인":[{"규정":"인사규정","조":"제31조"}],
 "형태":"영향있음","추가_후보":[],"불일치":false,"확인필요":"라벨러 합의"}
```

- `영향[].규정` 이름은 색인된 이름과 정확히 같아야 한다(`metrics.node_key` 규칙).
- 정답 단위는 **조**. 항은 설명용이다.
- `유형`(명시 · 개념 · 암묵)은 문항 파일에 **사람이 쓰지 않는다**. 정답이 확정된 뒤 실행 코드가 붙인다(5절).
- 통제 문항은 `형태: "무영향"`, `영향: []`.

## 4. 작성 절차

1. **개정문 작성자**(A)가 수정 24개를 만든다. 규정 원문과 개정문만 쓴다. 시스템 결과 · 인용 표 · 규정문 파일은 보지 않는다.
2. **라벨러 둘**(B, C)이 각자 독립으로 영향받는 조를 적는다. 규정 원문을 읽고 필요하면 검색해도 되지만 시스템 출력은 보지 않는다. 영향마다 이유 한 줄.
3. 두 사람의 합집합을 후보로 하고, 한 사람만 낸 것은 **불일치**로 표시해 A가 아닌 제3자가 결정한다. 불일치 비율을 보고한다.
4. 통제 문항은 B, C가 모두 「영향 없음」이라고 한 것만 쓴다.
5. 해시를 고정하고 계획서를 실행 전에 커밋한다(검색 팀 봉인셋과 같은 방식).
6. **풀링**: 시스템들이 낸 후보 중 정답에 없는 것을 B, C가 출처를 모른 채 다시 판정한다. 정답으로 인정된 것은 `추가_후보`에 넣고, 보고서는 추가 전후 두 숫자를 모두 낸다.

## 5. 정답 유형 분류 (코드, 정답 확정 후)

각 정답 조에 대해 수정된 조에서 다음 순서로 확인한다.

| 유형 | 판정 |
|---|---|
| 명시 | `impact_range`(역방향 인용 · 위임 · 법령, 2단계 이내)로 닿음 |
| 개념 | 명시가 아니고, 규정문의 (개념, 면)이 수정된 조의 규정문과 같음 |
| 암묵 | 위 둘 다 아님 |

유형은 시스템이 설계된 방식에 따른 사후 층 분류이고, 정답의 속성이 아니다. 인용 표나 규정문이 바뀌면 같은 정답의 유형도 바뀐다. 보고할 때 이 사실을 적는다.

## 6. 지표

| 층 | 지표 |
|---|---|
| 그래프 | 명시 · 개념 유형별 재현율, 전체 재현율 |
| RAG | RAG만의 재현율, **추가 기여 = (그래프 ∪ RAG) 재현율 − 그래프 재현율** (특히 암묵 유형) |
| 부담 | 문항당 후보 수, 후보 중 정답 비율(정밀도), 통제 문항에서 나온 후보 수 |
| 공정성 | 후보 상한을 문항당 N개(권장 20)로 고정해 같은 상한에서 비교. 상한 없는 결과는 참고 |
| AI 설명 | 아래 7절 |

- 단위는 문항(수정 하나). 구간은 문항 단위 부트스트랩(`paired_diff_cluster`), 이긴 · 진 문항 수 병기.
- 층별 정답 수를 항상 함께 적는다. 암묵 유형이 5개 미만이면 숫자 대신 사례 목록으로 보고하고 「탐색적」이라고 적는다.

## 7. AI 설명 평가

시스템이 후보마다 쓴 설명을 정답 조에 대해서만 채점한다.

| 항목 | 방법 |
|---|---|
| 근거 인용 정확성 | 인용한 문장이 원문에 실제로 있는지 코드로 검사(부분 문자열) |
| 영향 유형 일치 | 라벨러가 적은 이유와 설명의 영향 종류가 맞는지 (맞음 · 부분 · 틀림) |
| 확인할 것의 쓸모 | 담당자가 다음에 할 일을 알 수 있는지 (예 · 아니오) |
| 지어낸 내용 | 원문에 없는 사실 · 번호를 말했는지 (있음 · 없음) |

- 사람이 표본 30%를 채점하고, 나머지를 LLM 채점으로 보조한다면 사람 표본에서 LLM 채점의 일치율을 보고한다.
- 설명은 수정안 품질이 아니다. 참고 문안(개정 초안)의 평가는 별도다.

## 8. 보고 규칙

- 한 표에 층별 정답 수 · 재현율 · 구간 · 이긴/진 문항을 함께 쓴다.
- 쓸 수 있는 말: 「이 24개 문항에서 인용 · 개념 층이 정답 영향 조의 X%를 후보로 올렸고, RAG가 Y개를 더했다」.
- 쓸 수 없는 말: 충돌 탐지 성능, 정밀도의 일반화, 「누락 없이」.
- 정답은 라벨러가 정한 것이다. 법적 확정은 현업 검수(UAT)이며 향후 과제다.
- 개발셋 숫자는 설계를 고른 데이터라 낙관적이다. 결론은 봉인 숫자로 쓴다.

## 9. 누수 방지

- 개정문 작성자와 라벨러는 시스템 출력 · 인용 표 · 규정문 파일을 보지 않는다.
- 봉인 문항의 규정 · 주제를 규칙 설계에 쓰지 않는다. 개발 규정과 겹치면 봉인에서 제외한다.
- 봉인 실행은 한 번이다. 결과를 보고 규칙을 고치면 새 봉인셋이 필요하다.
- 규정문 추출 프롬프트에 평가 문항을 넣지 않는다.
