## 요약
개정 담당자 화면에 「변경 감시」를 추가했다. 반입된 법률 DB 판을 고르고 「탐색 시작」을 누르면, 점검을 다시 돌려 직전 탐색과 비교한 뒤 새로 생김 / 해결됨 / 그대로로 나눈다. 탐색 한 번은 약 1.3초 걸린다.
시험: 261007판(법령 232개)을 기준으로 기록하고 현재 판(284개)을 탐색하면 새로 생김이 5건 나온다. 그중 「특정범죄신고자 등 보호법」 제9조(2026.10.02 시행)를 인용하는 신고 처리 지침 3곳, 「지방계약법 시행령」 제25조 1곳, 법령명 오기 1곳이다. 해결됨은 0건, 그대로는 268건이다. 같은 판으로 다시 탐색하면 새로 생김은 0건이다.

## 주요 결정
| 결정 | 이유 | 대안 |
|---|---|---|
| 비교 열쇠는 `review_key`(규정·단위·조·항·문구·유형 해시) | 실행마다 바뀌는 fid와 달리 같은 문제는 같은 키라서, 사람이 이미 본 결과와 새 결과를 가를 수 있다 | fid 비교 (실행마다 달라 쓸 수 없음) |
| 탐색 결과는 `amend.scan`·`scan_item`에 따로 쌓고, `amend.finding`(기준선)은 바꾸지 않는다 | 화면(editor 역할)이 기준선 표를 고칠 수 없게 한다. 기준선 교체는 지금처럼 `amend_load.py`(amend_builder)로 | 탐색할 때마다 finding 교체 (화면에 넓은 쓰기 권한이 필요) |
| 비교 기준은 직전 탐색(새로 생김 + 그대로). 처음이면 기준선 적재본 | 「지난번 이후 무엇이 바뀌었나」가 담당자가 실제로 묻는 것 | 항상 기준선과 비교 (한 번 본 결과가 매번 「새로」 나옴) |
| 「기준으로만 기록」 버튼 (비교 없이 그 판의 결과를 기준으로) | 설치 첫날 기준을 잡거나, 시연에서 옛 판 → 새 판 순서를 보여 주려면 필요 | 없음 (첫 탐색이 늘 기준선과 비교됨) |
| 반입 판 목록은 `data/law_rag*.sqlite3` 파일 | 폐쇄망 반입 = 파일 반입. 파일 이름은 정규식으로만 받아 경로 조작을 막는다 | 업로드 화면 (반입 절차는 석희 쪽 합의 뒤) |
| 탐색 결과도 판정이 아니라 「다시 볼 곳」 목록 | AGENTS §3. 법령이 바뀌어도 내규를 고칠 필요가 없을 수 있다 | — |

## 변경 사항
- `regcheck.watch`: `scan(law_db)`는 build_findings와 같은 단계로 법률 DB만 바꿔 실행한다. `diff`는 review_key로 비교하고, 같은 키는 한 건으로 센다. `snapshots`도 여기 있다.
- `amend.scan`(탐색 한 번)과 `amend.scan_item`(항목, change = new·resolved·kept)을 만들었다. editor에는 INSERT 권한만 준다.
- API
  - `GET /api/scan/snapshots`: 판 목록, 지금 서버가 쓰는 판, 마지막 탐색
  - `POST /api/scan/start {law, rebase}`: 탐색 실행
  - `GET /api/scan?id=`: 결과(새로 생김·해결됨)와 탐색 기록 10건
- 화면: GNB에 「변경 감시」(개정 담당자만)를 추가했다.
  - 판 선택, 탐색 시작, 기준으로만 기록
  - 요약 3칸(새로 생김·해결됨·그대로), 새로 생김·해결됨 카드
  - 「조문 열기」를 누르면 질의응답 화면에 그 조와 개정 정보(법령 대조 카드)가 열린다
  - 오른쪽에 탐색 기록
- 테스트 2개를 추가했다. 전체 211개 통과.
- 시험 탐색 기록은 지웠다 (`amend.scan` 비움).
