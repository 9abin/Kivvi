# 261030-1830 영향 라벨링 키트 (평가셋 68의 작성 도구)

- 관련: [68 영향 점검 평가셋 설계](261030-1800-68-impact-evalset-design.md)
- 변경 범위: `eval/impact_label_kit/` 새로 만듦(미커밋). 코드 변경 없음

## 요약

평가셋 68의 문항 작성과 정답 라벨링을 외부 에이전트(Codex 등)에게 맡기기 위한 폴더다. 규정 전문만 들어 있고 인용 표 · 규정문 · 시스템 결과 · 프로젝트 문서는 넣지 않았다. 지시서도 어떤 시스템을 평가하는지 말하지 않는다. 그래야 정답이 시스템에 끌려가지 않는다(68의 4절).

## 구성 (`eval/impact_label_kit/`)

| 파일 | 내용 |
|---|---|
| `규정/*.txt` (90개) | `out/parsed`에서 뽑은 규정 전문(조문 · 부칙 · 별표). 간선 · 관계 정보는 없음 |
| `규정목록.tsv` | 규정 이름과 조 수 |
| `지시서.md` | 공통 규칙, 역할 A(가상 개정 24건 작성), 역할 B(영향 라벨링), 역할 C(불일치 결정) |
| `validate.py` | 산출물 형식 검사(규정 · 조 존재, 근거문장의 원문 일치, 라벨 누락) |
| `산출/` | 결과를 쓰는 빈 폴더 |

## 실행 순서

각 단계는 **새 세션**으로 한다. 같은 대화에서 역할을 바꾸면 안 된다. 작업 폴더는 `eval/impact_label_kit`이고, 상위 폴더가 보이지 않는 환경이 가장 안전하다(폴더를 따로 복사해 가도 된다).

1. 역할 A: 「`지시서.md`를 읽고 역할 A를 수행하라. 산출물은 `산출/changes.jsonl`」 → `python validate.py changes 산출/changes.jsonl`
2. 역할 B1, B2: 서로 다른 두 세션(가능하면 서로 다른 모델)에서 「역할 B, 라벨러 B1(또는 B2)」 → `산출/labels_B1.jsonl`, `labels_B2.jsonl`
3. 역할 C: B1, B2가 끝난 뒤 새 세션에서 → `산출/labels_final.jsonl`
4. 사람이 `labels_final.jsonl`의 제외 목록과 확신 「낮음」 항목을 훑어 본다.
5. 정답으로 확정한 `labels_final.jsonl`을 `eval/impact_cases_YYYYMMDD.jsonl` 형식(68의 3절)으로 옮기고 해시를 고정한다.

## 주의

- 지시서의 미리 정해진 개정 3건(I01~I03)은 기존 시나리오 S01~S03에서 가져온 개정문이다. 정답은 가져오지 않았다.
- 개정문 작성자(A), 라벨러(B1, B2), 결정자(C)는 서로 다른 세션이어야 한다. 같은 모델을 쓰면 편향이 같을 수 있으므로 한계로 적는다.
- 정답은 라벨러가 정한 것이고 법적 확정이 아니다(68의 8절). 전문가 확인은 별도 과제다.
- A가 조를 난수로 고르게 한 것은 인용이 많은 조를 고르는 선택 편향을 줄이기 위해서다.
- 라벨러가 규정 90개를 모두 검색해야 하므로 시간이 걸린다. 개정 24건 × 2명이면 한 세션에서 끝나지 않을 수 있다. 중간 저장이 되도록 개정을 나눠 진행해도 된다(`산출/`에 id 범위를 나눠 쓰고 합치는 방식).
- `eval/impact_label_kit/`은 git에 올리기 전에 용량과 공개 가능 여부를 확인한다. 규정 원문은 KVIC 저작물이라 외부 공유 시 ALIO 링크를 쓰는 규칙(작업 규칙 §4)이 있다. 외부 서비스에 보내는 것이면 규정 전문을 업로드하는 것이므로 먼저 확인한다.
