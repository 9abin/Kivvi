# 99. 웹 편집 화면을 평가한 파이프라인으로 통합

작성 261113. 관련: [리포트 96](261112-2000-96-codex-cross-review.md)(지적 3: 평가와 앱 설정이 다름), [98](261112-2330-98-impact-ontology-domain-graph.md). 가빈 UI 작업(`feature/merge-regulation-review-ui`, 304acaf) 위에 얹었다.

## 왜
웹 편집 화면(`app/web_edit.py`)은 웹 전용 후보 찾기(벡터 + BM25 순위 합치기, 상위 10개만 luna)를 썼다. 평가셋(웹이 돌릴 수 있는 문항)에서 luna 입력까지 재현율이 개발 0.679 · 시험 0.694로, 같은 문항에서 우리 파이프라인(0.974 · 0.944)보다 크게 낮았다. 순위 전체(약 100개)에는 0.936 · 0.972가 있었으나 10개로 자르며 빠졌다. 보고 숫자(최종 0.900)가 웹 화면 성능이 아니었다.

## 바꾼 것
- 웹 화면이 `run_pipeline`을 쓴다: 개정 영향 온톨로지 경로 · 개정문 낱말 일치(판단 모델로 거름) + 의미 검색(luna가 고름, 입력 50) → 첫 화면 10개 + 「더 보기」. 화면에 출처 묶음 · 찾은 경로 · 서버 알림 표시. 웹 전용 검색 함수는 지웠다.
- 판단 모델 호출을 `regcheck.decide_runner.subprocess_scorer`로 옮겨 리뷰 앱과 같이 쓴다. GPU 작업은 한 번에 하나(잠금). 판단 모델 환경: `IMPACT_DECIDE_PYTHON` · `IMPACT_DECIDE_MODEL`(예: `C:\Users\Admin\kanana_decide\venv\Scripts\python.exe`, `…\kanana_decide\model`, torch 2.10.0 · transformers 5.5.3, 저장 점수와 차이 0). 없으면 규칙 후보를 거르지 않고 알림.
- 조 전체 교체 개정문(웹 편집기는 항상 「제N조를 다음과 같이 한다」): ① `change_query`가 옛 조문에서 바뀐 말을 감싼 문구를 되살려 `old_phrases`로 넣는다(따옴표 안 전체 · 괄호가 닫힐 때까지 · 짧으면 앞 낱말까지) → 낱말 일치 경로 작동 ② 판단 모델 입력 앞에 「바뀌는 부분: 「옛 문구」 → 새 말」 요약(`impact_pipeline.decide_amendment`). 평가셋에는 이 형태가 0문항이라 보고 숫자 영향 없음.
- 속도: 판단 모델이 있으면 의미 검색 모델을 CPU로(`IMPACT_EMB_DEVICE`로 바꿀 수 있음). 8GB GPU를 나눠 쓰면 230초, 나누지 않으면 66초. luna 제한 14 → 60초, 판단 모델 90초, 브라우저 300초.
- Codex 코드 리뷰 반영: 그래프에 없는 검색 id(`…:전문` 등)로 요청 전체가 실패하던 것, 서버 알림이 화면에 안 보이던 것, 서버 · 브라우저 제한 불일치, GPU 동시 적재.

## 확인
개인정보 보호 및 관리지침 제38조 「제36조(개인정보의 파기)」 → 「제37조(…)」(시험 T030과 같은 개정)를 웹 함수로 끝까지 실행: 66초, luna 입력 46, 첫 화면 10 · 더 보기 2. 옛 번호를 인용하는 제13 · 35 · 36조가 규칙 후보로 들어옴. 제24조는 판단 모델이 거름(T030과 같은 주제 치우침). 테스트 494개 통과.

## 남은 것
- 웹 화면 성능을 평가셋으로 다시 잰 것은 아니다(리뷰 앱과 같은 파이프라인이라 같다고 본다. 단 조 삭제 개정은 웹 편집기가 다루지 않음).
- 판단 모델을 요청마다 띄운다(약 15~20초). 상시 띄워 두는 방식은 이후 과제.
