# 95. 판단 모델 거르기 문턱 다시 보기 — 0.7 유지

작성 261112. 관련: [리포트 92](261110-1552-92-final-selection.md)(문턱 0.5), [리포트 93](261111-1500-93-candidate-state-pipeline.md)(0.7 · USES_TERM 예외), [리포트 94](261111-2100-94-eval-metrics.md)(시험 100), [리포트 96](261112-2000-96-codex-cross-review.md)(Codex 교차검증). 코드: `src/regcheck/impact_pipeline.py` `DECIDE_TH` · `_decide_bypass` (바꾸지 않음).

## 왜 봤나
시험 100 최종 재현율 0.860(개발 0.934). 판단 모델이 거른 시험 정답이 3개(T030 · T073 · T076)라서 문턱 0.7이 개발셋에 맞춰진 값인지 확인했다.

## 확인한 것
**문턱의 내력.** 리포트 92는 미리 정한 규칙(개발 규칙 정답 90% 이상 유지하는 가장 높은 값, 후보 0.5 · 1.0 · 1.5)으로 **0.5**를 골랐다. 리포트 93에서 val 30을 보고 목록을 줄이려고(3.9 → 3.3개) **0.7**로 올렸다. 시험을 보고 정한 값은 아니지만, 개발에서 「정답을 안 잃는 구간」(0~0.7)의 끝을 고른 값이다.

**판단 모델 자체는 두 세트에서 같다** (판단 대상 규칙 후보, 확정급 · 점수 없음 제외).

| | 개발 100 | 시험 100 |
|---|---|---|
| 후보 (정답) | 792 (38) | 806 (24) |
| AUC (`lv`) / (`p`) | 0.872 / 0.818 | 0.881 / 0.721 |
| 0.7 아래로 빠지는 오답 / 정답 | 71% / 11% | 70% / 12% |

개발에서 0.7 아래 정답 4개(B010 3 · B051 1)는 모두 정의 변경 · `USES_TERM`이라 예외(`_decide_bypass`)로 살았다. 시험의 3개는 값 변경 · 삭제라 예외에 안 걸려 지워졌다. 시험 3개 중 둘은 `lv`가 낮고 `p`(예/아니오 확률)가 0.92였다(T073 · T076). T073은 별표 5,369자에서 근거 문장이 1,792자 위치라 입력(앞 700자)에 없었다.

**`p`는 거르기에 시험한 적이 없다.** 리포트 92는 `p`를 순서 매기기에만 써 보고(시험 −10쌍) 버렸고, 거르기 후보에서도 함께 빠졌다.

## 개발셋만으로 다시 최적화 (시험은 마지막에 한 번)
미리 정한 규칙: 후보 = `lv` 문턱 {0.1 … 1.0} × `p` 문턱 {없음, 0.8, 0.85, 0.9, 0.95, 0.99}의 「또는」 66개. 기준 = 개발 정답 손실 최소, 같으면 목록이 짧은 것.

| 기준 | 개발 | 시험 (한 번) |
|---|---|---|
| 전부 보인 것으로 셈, USES_TERM 예외 끔 → `lv` ≥ 0.1 선택 | 0.912 (7.8개) | 0.900 (7.8개) |
| 같은 셈, 지금 0.7 (예외 끔) | 0.890 (5.2개) | 0.860 (5.3개) |
| **10개 화면(Recall@10), 예외 켬** → 지금 설정이 최적 | **0.901** | — |

- `p`는 개발셋에서 효과가 없다(개발에서 `lv`가 낮은 정답은 `p`도 낮음). `lv` ≥ 0.5 또는 `p` ≥ 0.9(시험 0.920)는 시험을 보고서만 나오는 기준이다.
- 10개만 보이면 문턱을 낮출수록 목록이 길어져 정답이 11위 밖으로 밀린다(개발 R@10: 0.1 → 0.868, 0.5 → 0.890, 0.7 → 0.901, 1.2 → 0.857).
- 합치는 순서(번갈아 · 확정급 먼저 · 규칙 앞 k개 등)도 개발 R@10에서 규칙 먼저(0.901)를 넘지 못했다.

**구간.** 개발 정답 91개 · 재현율 0.9면 ±6%p(정답 1개 = 1.1%p). 설정 간 차이는 정답 1~4개라 구분되지 않는다. 같은 200문항에서 짝지은 차이도 지금 vs `lv` ≥ 0.5 또는 `p` ≥ 0.9가 R@10 0.000 [−0.035, +0.034]. luna도 같은 프롬프트로 실행마다 결과가 달랐다(놓친 4문항 다시 돌리니 2개를 고름).

## 결정
- **문턱 0.7 · USES_TERM 예외 · 규칙 먼저를 그대로 둔다.** 10개 화면 기준 개발 최적이고, 다른 설정과의 차이는 구간 안이다.
- 설정은 짝지은 차이 구간이 0을 넘을 때만 바꾼다. 비교는 여러 번 반복 실행(luna 흔들림)으로 하고, 판단 모델 같은 부품은 후보 단위(AUC)로 본다.
- 문항 단위로 가르려면 정답 400개 이상이 필요하다 → 실제 개정 이력으로 큰 세트.

## 버린 대안
- **「판단 필요」 칸**: 문턱 아래 규칙 후보를 지우지 않고 아래 칸에 점수 순으로(상위 3 먼저) 보이기. 개발 0.934(6.9개) · 시험 0.900(6.8개)였으나 사용자가 거르기를 원해 코드를 되돌렸다. 시험 실패를 보고 나온 설계라 시험 숫자는 독립 수치가 아니다.
- 문턱 0.3 · 0.35(개발 손실 없는 구간의 가운데): 시험 0.900(6.2~6.3개). 10개 화면 기준 개발에서 0.7보다 낮다(0.890).
- `lv` ≥ 0.5 또는 `p` ≥ 0.9: 시험을 보고 고른 기준, 개발 근거 없음.
- 판단 모델에서 떨어진 규칙 후보 중 RAG도 찾은 것을 luna에 다시 넘기기(Codex 지적): 리포트 96.

## 남은 것
- 판단 모델 입력: 긴 조문은 앞 700자 대신 바뀌는 말이 든 문장 주변(T073 유형). 큰 세트가 생기면 확인.
- luna 프롬프트 너그럽게(놓친 개발 4문항에서 4개 모두 고름, 목록 1~7 → 7~14개): 큰 세트 · 반복 실행으로 확인.
