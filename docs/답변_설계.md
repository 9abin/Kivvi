# 답변 설계 (④ 단계)

검색된 근거로 질문에 답하는 단계를 정리한다.
근거를 찾는 과정은 `검색_설계.md`, 화면과 실행 방법은 아래 6절을 본다.

**기준일: 2026.10.06**
**상태: 1차 구현 완료, 검증 전**

---

## 1. 흐름

```
질문 → Searcher.search() → Searcher.assemble() → 근거 번호 부여 → OpenAI 모델 → 인용 검사 → 답변
```

- `src/answer/pipeline.py`의 `Assistant.ask()`가 전체를 묶습니다.
- 근거가 0개면 모델을 부르지 않고 고정 문구로 답합니다.

---

## 2. 모델

| 항목 | 값 |
|---|---|
| 모델 | `gpt-4o-mini` (`config.py`의 `OPENAI_MODEL`) |
| API | OpenAI Responses API (`client.responses.create`) |
| 키 | 프로젝트 상위 폴더의 `.env` (`OPENAI_API_KEY`). Git에서 무시됨 |

모델을 바꾸려면 `OPENAI_MODEL`만 고칩니다. 이전에는 `gpt-5.1`로 확인했고, 품질 비교는 골든셋 이후입니다.

---

## 3. 근거 형식

모델에는 근거를 번호와 함께 넘깁니다.

```
[1] 급여규정 제17조 제1항 | 조문상태: 현행 | 개정: 2025년도 ...
(본문)
정정안내: ... (있을 때만)
```

- 번호는 답변의 `[n]` 인용과 같습니다.
- 근거 순서는 검색 결과(정확 조회 → 검색) → 인용 대상 → 형제 항입니다. 세부 규칙은 `검색_설계.md` 0.3절을 봅니다.

---

## 4. 답변 규칙

시스템 지시(`SYSTEM_PROMPT`)로 요청한 규칙입니다.

| 규칙 | 내용 | 강제 여부 |
|---|---|---|
| 근거 한정 | 제공된 근거에 있는 내용만 쓴다 | 지시만 (보장 안 됨) |
| 없음 | 근거가 질문에 답하지 못하면 "제공된 규정에서 확인되지 않습니다"라고 쓰고 담당 부서 확인을 안내한다 | 지시만. 검사 코드 없음 |
| 인용 | 문장마다 `[n]`을 붙인다 | 인용 번호 검사만 함 |
| 부칙 | "현행 기준이 아님"으로 밝힌다 | 지시만 |
| 삭제 | "삭제된 조항입니다"로 밝히고, 현행 기준으로 말하지 않는다 | 지시만 |
| 정정안내 | 근거에 있으면 답변 끝에 "※ 정정 안내"로 붙인다 | 지시만 |
| 충돌 | 근거끼리 다르면 둘 다 보여주고 판정하지 않는다 | 지시만. 판정 로직 없음 |
| 외부 법령 | 근거가 아니다 | 지시만 |

### 4.1 자동으로 검사하는 것
- 답변이 근거 범위 밖의 번호(`[9]`처럼 없는 번호)를 쓰면 경고합니다.
- 답변에 인용이 하나도 없는데 "확인되지 않습니다"도 없으면 경고합니다.

### 4.2 구현됨 (점수 구간, 충돌 표시)
- **점수 구간** (`config.py`, 임시값): 1위 리랭커 점수가 0.3 미만이면 `none`, 0.3~0.6이면 `partial`, 0.6 이상이면 `answer`.
- **충돌**: 근거가 2개 이상이면 모델에게 "서로 다른 내용을 말하는 조문 쌍"만 JSON으로 찾게 합니다. 찾은 쌍은 화면에서 위계와 개정일과 함께 나란히 보여줍니다. 판정은 하지 않습니다.
- **정확 조회**: 조문이 확정된 경우에는 점수 구간을 적용하지 않습니다.

### 4.3 아직 없는 것
- **충돌의 자동 판정 (위계 우선, 개정일 우선)**: 보류. 판정 기준은 사용자가 정해야 하고, 지금은 표시만 합니다.
- **인용 내용 검사**: 답변 문장이 인용한 조문의 내용과 맞는지 확인하는 기능.
- **임계값 조정**: 평가셋 이후 (7절).

## 7. 점수 구간과 출력 형식

### 7.1 구간 (2026.10.10 재보정, 최초 2026.10.07)

| 1위 리랭커 점수 | 모드 | 답변 방식 | 모델 호출 |
|---|---|---|---|
| 0.001 미만 | `none` | "이 질문과 관련된 내용을 찾을 수 없습니다. 담당 부서에 확인해 주세요." | 안 함 |
| 0.001 이상 | `answer` | 모델이 근거 범위 안에서 답변 | 함 |
| (정확 조회 포함) | `answer` | 기준을 적용하지 않음 | 함 |

- 임계값은 `config.py`의 `ANSWER_NONE_BELOW`(0.001), `ANSWER_PARTIAL_BELOW`(0.001, `NONE_BELOW`와 같은 값)에 있습니다. 두 값을 같게 둬서 `partial`(점수만 보고 고정 문구로 답하던 중간 구간)이 사실상 비활성화됩니다. 코드(`decide_mode`)는 그대로 두고 값만 바꿨습니다.
- **2026.10.10 추가 재보정(0.05 → 0.001)**: 평가셋 190문항의 검색 점수로 보니, 0.05라는 기준이 **정답 조문이 상위 5개 안에 있는 질문의 26%(33/125)를 막고 있었습니다.** 0.001로 낮추면 1%(1/125)만 막힙니다. 임계값을 0으로 두고 "없음" 28문항 + 막혔던 정답 33문항을 실제로 답변까지 생성해 본 결과, "없음" 28개 중 지어낸 답은 1개뿐이었고 그 1개는 점수가 0.64라 애초에 어느 임계값을 써도 걸러지지 않았습니다. 그래서 점수 기반 차단은 거의 포기하고, 대신 아래 12절의 **코드 검사(guard.py)**로 사후에 걸러내는 쪽으로 무게를 옮겼습니다.

**바꾼 이유**: 처음 정한 0.3/0.6은 질문 35개(대부분 정답을 보고 만든 질문)로 잡은 값이었습니다. 이후 진짜 블라인드 질문(v3)으로 실제 점수 분포를 보니, **"답 있음"과 "답 없음" 질문의 점수가 0.03~0.6 구간에서 크게 겹쳐서 점수 하나로는 못 가른다**는 것을 확인했습니다 (예: "없음" 질문이 0.602, "있음" 질문이 0.015인 경우도 있었음). 그래서 확실히 아무것도 없는 구간(0.05 미만)만 막고, 그 위는 모델 판단(`SYSTEM_PROMPT`의 "답할 수 없으면 찾을 수 없었다고 써라" 규칙)과 사후 검사(10절 `verify()`)에 맡기기로 했습니다. 자세한 점수 분포와 검색_설계.md의 측정 과정은 PR #2를 참고합니다.

**효과 (v3, 질문 16개 "답 있음" 기준, 재보정 전 → 후)**

| 지표 | 전(0.3/0.6) | 후(0.05) |
|---|---|---|
| answer 모드로 실제 답한 질문 | 10/16 | **16/16** |
| LLM-judge 평균 정확성 | 2.31/5 | **3.38/5** |
| LLM-judge 근거충실 위반 | 10/16 | **6/16** |
| context_recall (RAGAS 스타일) | 0.17 | **0.40** |

**남은 위험**: "답 없음" 질문(v3_edge, 19개) 중 점수로 자동 차단되는 것이 6개로 줄었습니다(전에는 더 많았음). 나머지 13개는 이제 모델이 답을 시도합니다. 직접 확인해 보니 그중 일부는 **제가 "없음"으로 잘못 라벨링했던 것**(예: "휴가 신청 며칠 전"은 실제로 복무규정 제20조에 있었음)이었지만, **"명절 상품권"처럼 완전히 다른 주제의 조문(대외 접대 금지 규정)을 갖다 붙여 오답을 만든 진짜 문제 사례**도 있었습니다. 13개를 전부 검토하지는 못했습니다 — 다음 작업 후보입니다.

### 7.2 출력 형식 (`SYSTEM_PROMPT`)

모델은 `세부:` → `결론:` → (규칙 5일 때만) `관련 조문:` 구역을 이 순서로 쓴다. 불릿을 먼저 쓰게 한 이유는 결론이 불릿과 모순되지 않게 하려는 것이다. 화면에는 코드(`assemble_sections`)가 **결론을 맨 위로 옮겨** 결론 → 세부 불릿 → 관련 조문 순으로 보여 준다.

1. 세부: 근거에서 질문과 관련된 내용만 불릿으로. 최대 5개 (여러 항목을 물은 질문은 항목당 1개 이상, 전체 8개까지), 각 불릿 끝에 [n]
2. 결론: 한두 문장. 불릿과 모순되지 않게 쓴다 (모순이면 한 번 다시 쓴다, 8.5절)
3. 결론 끝에 붙는 "확인되지 않습니다. 담당 부서에 확인해 주세요" 문구는 결론 **전체**가 그 문구일 때만 남기고, 답을 쓴 뒤 끝에 덧붙은 건 코드가 뗀다
4. 부칙이나 삭제 조문을 썼으면 코드가 "※ 참고: [n]은 부칙(현행 기준 아님)입니다" 또는 "※ 참고: [n]은 삭제된 조항입니다"를 붙인다
5. 정정안내가 있으면 코드가 "※ 정정 안내: …"를 붙인다
6. 길이: 기본 3~5문장

### 7.3 충돌 표시

- 근거가 2개 이상이면 모델에게 충돌 쌍만 JSON으로 묻습니다 (`CONFLICT_PROMPT`).
- 쌍이 있으면 화면에 "⚠ 같은 주제의 조문이 서로 다른 내용을 말합니다"와 두 조문을 나란히 보여줍니다. 위계와 개정일은 문서에 적힌 사실이라서 함께 보여줍니다.
- **확인되지 않은 것**: 충돌 탐지가 실제로 충돌을 찾는지 아직 검증하지 않았습니다. 이사회 질문에서는 쌍이 찾아지지 않았는데, 충돌이 없는 것인지 놓친 것인지는 평가셋에서 확인합니다.

### 7.4 근거 순서와 참고 문구 (구현 완료)

- **근거 순서**: 현행 조문을 먼저 모델에게 넘기고, 부칙·삭제는 뒤로 보냅니다. 번호도 이 순서를 따릅니다.
- **참고 문구는 코드가 만듭니다**: 부칙·삭제 근거를 인용했을 때 "※ 참고: [n]은 …"을 답변 끝에 붙입니다. 모델이 번호를 잘못 붙이는 일을 막기 위해서입니다. 정정 안내도 같은 방식입니다.
- **모델에게 주지 않는 정보**: 문서의 개정표기는 모델에게 넘기지 않습니다. 모델이 개정일을 조문의 삭제일로 잘못 읽은 적이 있어서입니다. 화면에는 그대로 보여줍니다.
- **지시 강화**: 근거에 없는 일반 조언을 붙이지 않고, 날짜는 근거 본문에 적힌 것만 쓰고, "결론:" 같은 머리말을 쓰지 않습니다.
- **남은 문제**: 근거 밖 문장을 완전히 막지는 못합니다. 예: "포인트 관련 규정은 직위해제와 관련이 없습니다" 같은 판단을 모델이 덧붙이는 경우가 있습니다. 평가셋에서 확인합니다.

## 8. 프롬프트 (코드와 같은 내용)

프롬프트는 `src/answer/generate.py`에 있습니다. 이 절은 **현재 프롬프트 전문**입니다. 프롬프트를 고치면 코드와 이 절을 같이 고칩니다.

### 8.1 답변 프롬프트 (`SYSTEM_PROMPT`)

```
너는 한국벤처투자 내부규정을 설명하는 도우미다. 아래 규칙과 출력 형식을 반드시 지킨다.

[규칙]
1. 제공된 근거([1], [2] …)에 적힌 내용만 사용한다. 근거에 없는 내용은 추측하지 않는다.
2. 문장마다 근거 번호를 [1]처럼 붙인다. 여러 근거면 [1][2]처럼 붙인다.
3. 근거의 규정 이름, 조, 항은 표기를 그대로 쓴다. 새로 만들지 않는다.
4. 근거끼리 내용이 달라도 어느 쪽이 맞는지 판정하지 않는다. 각 근거의 내용을 번호와 함께 적는다.
5. 근거 어디에도 질문의 핵심(가능 여부, 수치, 기준, 절차)에 답하는 내용이 없을 때만 "제공된 규정에서 확인되지 않습니다. 담당 부서에 확인해 주세요."라고 쓴다.
   - 핵심에 답하는 내용이 하나라도 있으면 이 문장을 쓰지 않는다. 일부만 확인되면 확인된 부분만 쓰고, 빠진 부분은 "~는 근거에 없습니다"처럼 그 내용만 짚는다.
   - 이 문장은 결론에만 쓴다. 세부 불릿에는 쓰지 않는다.
   - 질문과 가장 가까운 근거가 있으면 이어서 "관련 조문:" 한 줄로 [n]과 규정명·조·항, 그 조문이 무엇을 정하는지 한 문장을 알려 준다. 그 조문이 질문에 답하는 것처럼 쓰지 않는다.
   - "찾을 수 없었습니다" 한 줄만 쓰고 끝내지 않는다.
6. 근거에 없는 일반 조언이나 예측을 덧붙이지 않는다. 예: "논의가 필요합니다", "달라질 수 있습니다" 같은 문장은 근거에 적혀 있을 때만 쓴다.
7. 근거는 번호순으로 현행 조문이 먼저 나온다. 현행 근거로 먼저 답하고, 부칙이나 삭제 근거는 현행 기준의 근거로 쓰지 않는다.
   - 조문상태가 '삭제'인 근거는 "그 항이 삭제되었다"는 사실의 근거로는 인용할 수 있다. 예: "○○에 관한 제N조 제M항은 삭제되었습니다 [n]." 삭제 날짜는 본문의 <삭제 날짜>에 적힌 것만 쓴다.
   - 삭제된 항의 원래 내용은 알 수 없다. 삭제 표기만으로 과거 내용을 추측하지 않고, 삭제됐다는 이유로 "현재 기준이 없다"고 결론짓지 않는다. 다른 근거에 현행 기준이 없으면 "확인되지 않는다"고 쓴다.
8. 부칙·삭제 여부와 정정 안내는 답변에 쓰지 않아도 된다. 시스템이 따로 붙인다. 단, 질문이 어떤 기준이 아직 있는지·삭제됐는지를 묻는다면 삭제 사실을 쓴다.
9. 날짜는 근거 본문에 적힌 날짜만 쓴다. "개정" 표기는 문서 전체의 개정일이지 조문의 시행일이나 삭제일이 아니다.
10. 근거를 쓰기 전에, 그 근거가 질문과 **같은 대상·같은 상황**을 다루는지 먼저 확인한다.
   - 단어가 같아도 대상이 다르면(예: 질문은 "직원"인데 근거는 "임원"·"단시간근로자"·"외부 기관" 대상, 또는 질문은 "직원에게 지급"인데 근거는 "외부에 제공 금지") 그 근거로 질문에 답하지 않는다.
   - 단어가 같아도 다루는 행위·절차가 다르면(예: 질문은 "징계 기준"인데 근거는 "근무평정(인사평가) 기준") 그 근거로 결론을 내리지 않는다.
   - 대상·상황이 맞는 근거가 없으면, 그 근거를 "관련은 있지만 질문에 직접 답하지는 않는다"고만 언급하고, 핵심 결론은 "제공된 규정에서 확인되지 않습니다"로 쓴다(규칙 5).
   - 다른 대상에 대한 규정만 있을 때, 그걸 일반화해서 "~는 금지됩니다/~는 보장됩니다"처럼 질문 대상 전체에 대한 결론으로 쓰지 않는다.
   - 반대로 근거가 질문과 같은 대상·상황을 다루면 이 규칙을 이유로 거절하지 않는다(규칙 11).
11. 근거 중 하나라도 질문에 직접 답하는 내용(수치, 기준, 가능 여부, 절차)이 있으면 반드시 그 내용으로 답한다. 이 경우 "확인되지 않습니다"로 끝내지 않는다.
   - 질문에 이미 들어 있는 말(연도, 선배·동료가 한 말, 옛 제도에 대한 기억)이 근거와 다르면 거절하지 말고 근거 기준으로 바로잡는다. 예: "근거에는 ~로 되어 있어 말씀하신 내용과 다릅니다 [n]."
   - 시행 시점이 근거에 없어 확인할 수 없으면, 현행 규정 내용은 답하고 시행 시점만 확인되지 않는다고 쓴다.
12. 표(별표)가 근거일 때는 질문의 대상(직급, 상황)에 해당하는 행만 골라 값과 단위를 그대로 쓴다. 표의 열 구분이 불분명해 값을 확정할 수 없으면 그 값을 단정하지 않고 확인되지 않는다고 쓴다.
13. 질문하는 사람이 어떤 집단(예: 신입, 수습 중인 직원)에 속하는지 먼저 생각한다. 근거에 그 집단이 다른 집단에 "포함된다/산입된다/준용한다"고 적혀 있으면, 그 다른 집단에 대한 근거의 기준(일수, 금액, 조건)을 질문한 사람에게도 그대로 적용한다. 이어서 쓴 두 근거는 번호를 모두 단다.
14. 질문이 "~는 안 되는 거 맞죠?", "~없다던데 진짜예요?"처럼 어떤 상태를 단정하면, 근거의 기준을 먼저 적고 그 기준에 비추어 단정이 맞는지 결론에 쓴다. 단정이 근거의 기준과 다르면 질문이 틀렸다고 쓰고 근거의 기준을 알려 준다. 이때 "규정에서 확인되지 않는다"고 쓰지 않는다.
15. 질문에 단정이 둘 이상 들어 있으면("~인 거 맞죠? 그럼 ~인 건가요?") 각 단정을 따로 근거의 기준에 비추어 본다. 첫 단정이 틀렸으면 그 위에 세운 다음 단정도 틀린 것이다. 결론은 "맞지 않습니다"로 시작해 근거의 기준(일수, 금액, 조건)을 먼저 쓰고, 질문자가 깔고 있던 상태를 그대로 되풀이하지 않는다.
16. 질문이 여러 항목을 동시에 물었으면(예: "월급이랑 복지포인트, 출산축하금은 각각 어떻게 되나요") 근거에 있는 항목을 하나도 빠뜨리지 않고 전부 답한다. 한 항목만 자세히 답하고 나머지 항목을 통째로 빼놓지 않는다.
17. 근거에 적힌 수치나 결론에 적용 조건·한도·예외(예: "1회로 한정", "구간별로 다름", "~인 경우에만")가 붙어 있으면, 그 수치만 떼어서 쓰지 않고 조건도 같이 쓴다. 조건을 빼면 다른 뜻이 된다.

[출력 형식] 아래 구역을 이 순서와 이 머리말 그대로 쓴다. 화면에는 시스템이 결론을 맨 위로 옮겨 보여 준다.
세부:
- 질문의 표현은 무시하고, 근거에서 질문과 관련된 내용만 불릿으로 쓴다. 최대 5개. 질문이 여러 항목을 물었으면(규칙 16) 항목당 최소 1개씩 쓰고 전체는 8개까지 쓸 수 있다. 각 불릿 끝에 [n]. 근거에 적힌 그대로 쓴다. 쓸 내용이 없으면 "없음"만 쓴다.
결론: 한두 문장. 반드시 위 세부 불릿을 다 쓴 다음에, 불릿과 모순되지 않게 쓴다.
   - 질문이 "~맞죠?"처럼 어떤 주장의 확인을 구하면, 첫머리에서 불릿에 비추어 "맞습니다/맞지 않습니다/근거로는 확인되지 않습니다" 중 하나를 밝히고 그 이유를 [n]으로 단다.
   - 질문이 기대하는 답이더라도 세부 불릿과 다르면 불릿을 따른다. 질문에 맞장구치지 않는다.
   - 결론이 근거로 질문에 답했다면 "확인되지 않습니다. 담당 부서에 확인해 주세요" 문구를 덧붙이지 않는다. 그 문구는 규칙 5의 경우에만, 결론 전체를 대신해서 쓴다.
관련 조문: 규칙 5에서 요구할 때만 쓴다. 아니면 이 구역을 쓰지 않는다.
- 길이: 기본 3~5문장. 조문 원문을 길게 옮기지 않는다.
```

### 8.2 충돌 확인 프롬프트 (`CONFLICT_PROMPT`)

```
아래 근거 중에서, 같은 질문에 대해 서로 다른 답(수치, 기준, 결론)을 주는 조문 쌍만 찾는다.

충돌이 아닌 경우 (찾지 않는다):
- 같은 단어(예: "감사")를 쓰지만 서로 다른 것을 규정하는 조문. 예: 하나는 감사의 "종류"를 나열하고, 다른 하나는 감사의 "직무"나 "업무"를 나열하면 충돌이 아니다. 둘 다 "감사"에 관한 것일 뿐, 같은 질문에 다른 답을 주는 것이 아니다.
- 한쪽이 다른 쪽을 보충하거나 구체화하는 경우.
- 적용 대상이나 상황이 다른 경우 (예: 하나는 정규직, 하나는 계약직 기준).

충돌인 경우 (찾는다):
- "지급률은 70%다"와 "지급률은 80%다"처럼 같은 항목에 다른 수치나 기준을 말하는 경우.

- 출력은 JSON 배열만 쓴다. 예: [[1, 3]]
- 확신이 없으면 넣지 않는다. 쌍이 없으면 []만 쓴다.
- 설명은 쓰지 않는다.
```

### 8.3 모델에게 넘기는 근거 형식

```
[1] 급여규정 제17조 제1항 | 조문상태: 현행 | 위계: 규정
(본문)
정정안내: ... (있을 때만)
```

- 개정표기는 넘기지 않습니다. 모델이 문서 개정일을 조문 날짜로 잘못 읽은 적이 있어서입니다.
- 근거 순서는 현행 먼저, 부칙·삭제는 뒤입니다.

### 8.4 코드가 붙이는 문구 (모델이 쓰지 않음)

- 부칙 근거를 인용했을 때: `※ 참고: [n]은 부칙 조항이라 현행 기준이 아닙니다.`
- 삭제 근거를 인용했을 때: `※ 참고: [n]은 삭제된 조항입니다.`
- 정정안내가 있는 근거를 인용했을 때: `※ 정정 안내 [n]: …`
- 애매함 구간과 없음 구간의 문구는 `pipeline.py`의 `partial_answer()`와 `NONE_MESSAGE`에 있습니다 (7절).

### 8.5 모순 확인 프롬프트 (`CONSISTENCY_PROMPT`)

답변의 결론 문장이 세부 불릿과 모순되는지만 묻는다 (`Generator.contradicts`). 모순이면 결론을 한 번 다시 쓰게 하고, 다시 써도 경고에 "결론이 세부 내용과 모순되어 한 번 다시 작성함"을 남긴다.

```
질문과 답변이 주어진다. 답변은 '결론 문장'과 '세부 불릿'으로 되어 있다.
결론 문장이 세부 불릿의 내용과 모순되는지 판정한다.

모순인 경우:
- 불릿은 "수습기간은 계속근로기간에 산입된다"인데 결론은 "수습 중에는 연차가 발생하지 않는다"처럼 결론이 불릿과 반대인 경우.
- 결론은 질문의 전제를 "맞다"고 하는데 불릿은 그 전제가 틀렸음을 보여 주는 경우, 또는 그 반대.
- 결론이 "임원도 팀장도 가능"인데 불릿은 "팀장 이하는 불가"처럼 결론이 불릿의 일부를 부정하는 경우.

모순이 아닌 경우:
- 결론이 불릿을 요약하거나 좁혀서 쓴 경우.
- 근거로는 확인되지 않는다고 밝히고, 불릿이 관련 내용만 나열하는 경우.

출력은 JSON 한 줄만 쓴다: {"모순": true} 또는 {"모순": false}. 설명은 쓰지 않는다.
```

### 8.6 문장 단위 근거 검사 프롬프트 (`VERIFY_PROMPT`)

답변의 각 불릿이 인용한 근거 본문에 실제로 있는 내용인지 확인한다 (`Generator.verify`, 10절). 결과는 답을 막지 않고 경고로만 붙인다.

```
질문에 대한 답변과, 답변이 사용한 근거가 주어진다. 답변의 불릿을 하나씩 보고,
그 불릿이 인용한 근거 번호의 본문에 실제로 있는 내용인지 확인한다.

- 근거 본문에 없는 내용(추측, 일반론, 과장)을 담은 불릿이 있으면, 그 불릿 문장을 그대로 JSON 배열에 담는다.
- 근거와 의미가 반대인 문장도 포함한다. 특히 근거가 "~해서는 아니 된다/금지한다"인데 답변이 "~할 수 있다/허용된다"로 바뀌었거나, 근거의 조건("다만", "한하여", 금액 상한, 예외)을 빼서 범위를 넓힌 문장이 그렇다.
- 답변의 숫자(금액, 일수, 비율, 기간)와 단위가 근거 본문과 정확히 같은지 본다. 근거의 표에서 다른 직급·등급 행의 값을 가져왔거나, 근거에 없는 단위(원, 달러 등)를 붙인 문장도 포함한다.
- 결론 문장도 같은 기준으로 본다.
- "~는 제공된 규정에서 확인되지 않는다/근거에 없다"고 말하는 문장은 근거에 없는 내용을 지어낸 것이 아니므로 포함하지 않는다. 단, 근거에 실제로 그 내용이 있는데 없다고 쓴 문장은 포함한다.
- 근거와 맞으면 포함하지 않는다. 모두 맞으면 []만 출력한다.
- 설명은 쓰지 않는다.
```

### 8.7 질문 바꿔쓰기 프롬프트 (`REWRITE_PROMPT`)

구어체 질문을 규정 용어로 바꾼 검색어 한 줄을 만든다 (`Generator.rewrite_query`). 후보를 찾는 단계에만 더해지고 리랭킹은 원래 질문으로 한다 (검색_설계.md 9.2절).
**기본은 이 프롬프트다(`config.QUERY_PLAN = False`, 2026.10.13 결정).** 아래 8.8 질문 나누기는 켰을 때만 쓰인다.

```
직원이 사내 규정 검색창에 구어체로 쓴 질문을, 규정 문서에 실제로 쓰이는 공식 용어로 바꿔 검색어 한 줄로 만든다.
- 줄임말, 속어, 외래어, 일상어를 규정에서 쓰는 정식 용어로 바꾼다.
- 질문의 상황이 규정에서 어떤 주제(제도, 절차, 금지·허용 사항)로 다뤄질지 떠올려, 그 주제어 2~4개를 덧붙인다.
- 질문에 없는 사실이나 수치를 만들어 넣지 않는다. 답을 쓰지 않는다.
- 출력은 검색어 한 줄만 쓴다. 설명, 따옴표, 번호를 쓰지 않는다.
```

### 8.8 질문 나누기 프롬프트 (`PLAN_PROMPT`, 2026.10.13)

질문을 하위 질문 최대 3개로 나누고, 하위 질문마다 8.7과 같은 규칙으로 검색어를 만든다 (`Generator.plan_queries`, `parse_plan`). 8.7 호출을 대신하므로 질문 하나당 모델 호출 수는 그대로다. 하위 질문별 검색과 합치기는 검색_설계.md 9.5절, 전체 흐름은 `질의_흐름.md`.

- 응답이 하위 질문 1개면 원래 질문 글자로 바꿔 둔다 — 나누지 않는 질문은 리랭킹까지 나누기 전과 같게 검색된다.
- JSON을 해석하지 못하면 원래 질문 하나(검색어 없음)로 검색한다.
- "나누지 않는다" 세 가지는 190문항 검색 비교(2026.10.13)에서 GPT가 상황 설명("애가 둘인데")이나 덧붙인 물음을 따로 떼어 내거나 "A 아니면 B"를 둘로 나눠 정답을 놓친 사례에서 넣었다.
- **예시는 평가셋에 없는 주제(사원증, 회의실, 사무용품, 노트북)로만 쓴다.** 평가 질문이나 그 주제를 예시로 넣으면 같은 평가셋으로 잰 점수가 부풀려진다. 예시를 바꿀 때는 `eval/` 파일에 그 말이 없는지 확인한다.
- 답변 결과의 `plan`에 하위 질문 목록이 남는다. 답변 프롬프트는 원래 질문을 받으며, 여러 항목을 빠짐없이 답하라는 규칙 16이 그대로 적용된다.
- 기본 끔(`config.QUERY_PLAN = False`). 켜려면 `True`로 바꾼다. `run_answer_eval --no-plan`은 설정과 상관없이 끈다.

```
직원이 사내 규정 검색창에 쓴 질문을 검색 계획으로 바꾼다.

1. 질문이 서로 다른 것을 두 가지 이상 묻는지 본다 (예: "사원증 재발급은 어디서 하고, 회의실 예약은 어떻게 하나요").
   - 그렇다면 묻는 것마다 하위 질문을 하나씩 만든다. 최대 3개.
   - 하위 질문마다 원래 질문의 대상과 상황을 모두 넣어서, 혼자 읽어도 같은 뜻이 되게 쓴다.
   - 한 가지만 묻는다면 하위 질문은 1개다. 나눌지 애매하면 나누지 않는다.
   - 다음은 나누지 않는다:
     · 한 제도의 여러 면 (예: "사원증 재발급은 며칠 걸리고 비용이 드나요")
     · 상황 설명이나 덧붙인 말 (예: "사원증 재발급 돼요? 어제 잃어버렸는데", "사무용품 개인 돈으로 사도 되나요? 나중에 청구해야 해요?")
     · 둘 중 하나를 고르는 질문 (예: "노트북 교체는 부서에서 신청해요 아니면 제가 직접 해요?")
2. 하위 질문마다 "검색어"를 만든다: 줄임말·속어·외래어·일상어를 규정에서 쓰는 정식 용어로 바꾸고,
   규정에서 어떤 주제(제도, 절차, 금지·허용 사항)로 다뤄질지 떠올려 그 주제어 2~4개를 덧붙인 한 줄.
3. 질문에 규정 이름(예: "복무규정", "여비규정")이 적혀 있으면 그 이름을 해당 하위 질문에도 그대로 남긴다.
- 질문에 없는 사실이나 수치를 만들어 넣지 않는다. 답을 쓰지 않는다.
- 출력은 JSON 배열만 쓴다. 설명을 쓰지 않는다.
  예: [{"질문": "사원증 재발급은 어디서 하나요?", "검색어": "출입증 재발급 신청 절차 분실"}]
```

### 8.9 근거 역할 표시와 강조 (`HIT_NOTE`, `ROLE_LABEL`, 2026.10.14)

`config.HIGHLIGHT_HITS`일 때만 쓴다 (항으로 찾고 조 전체 넘기기와 함께, 검색_설계.md 9.6절). 기본 프롬프트(`SYSTEM_PROMPT`)는 그대로 두고 두 가지를 더한다.

- **근거 머리에 역할**(`format_context`): `[1] 급여규정 제17조 | 조문상태: 현행 | 위계: 규정 | 역할: 질문으로 찾은 조문`.
  인용으로 따라온 근거는 `역할: 인용된 조문(참고) ('제34조 제4항'이 가리킴)`, 형제 항은 `같은 조 다른 항`.
- **본문 안 ▶**: 조 전체 중 그 조를 상위로 올린 항 하나에 `▶ `를 붙인다(`search.HIT_MARK`).
- **질문 뒤 안내**(`HIT_NOTE`):

```
[참고] 근거마다 '역할'이 적혀 있다. '질문으로 찾은 조문'을 먼저 보고 답한다. 그 본문에서 ▶로 시작하는 항이
검색이 질문과 가장 가깝다고 찾은 항이다. 같은 조의 다른 항(조건, 예외, 단서)도 함께 확인한다.
'인용된 조문(참고)'은 찾은 조문이 가리키는 다른 조문이다. 찾은 조문을 보충하거나 그 조문이 '~에 따른다'고
넘긴 내용을 확인할 때만 쓰고, 질문에 직접 답하는 근거로 먼저 쓰지 않는다. ▶ 표시는 답변에 옮겨 쓰지 않는다.
```

- **왜**: 인용으로 따라온 조문이 검색으로 찾은 조문과 같은 모양이라, 인용이 많으면 GPT가 엉뚱한 인용 조문으로 답했다.
- **측정** (팀 DB 항→조, 100문항): 넣기 전 정답 27 / 충실도 0.865 → 넣은 뒤 정답 30 / 충실도 0.900 (흔들림 범위 안이지만 같은 방향).

## 10. 문장 단위 근거 검사 (구현 완료, 평가 전)

답변의 각 불릿이 인용한 근거 본문과 실제로 맞는지, 별도 모델 호출로 다시 확인합니다 (`Generator.verify`, `VERIFY_PROMPT`).

- 입력: 질문, 모델이 쓴 답변 전체, 근거 전문
- 출력: 근거에 없는 내용을 담은 불릿 문장 목록 (JSON 배열). 모두 맞으면 `[]`
- 결과는 답변을 고치지 않고 **경고로만** 붙입니다 (`result["warnings"]`, `result["unsupported"]`). 화면에서 경고로 보여줍니다.
- 확인된 사례: "직위해제된 직원은 매월 15일을 기준으로 월할 계산이 이루어질 수 있습니다"라는 문장을 근거 밖이라고 정확히 잡았습니다.
- **한계**: 모델 호출이 하나 더 늘어서 비용과 시간이 늘어납니다. 검사 자체도 모델이 하므로 완벽하지 않습니다. 놓치거나 과하게 잡을 수 있습니다.
- **측정 전**: 골든셋이 없어서 이 검사가 실제로 얼마나 정확한지는 아직 모릅니다. 골든셋에 "근거 밖 문장이 포함된 질문"을 넣어서 확인해야 합니다.

### 10.1 충돌 탐지 보완

같은 문서의 같은 조에 속한 서로 다른 항은 충돌 후보에서 미리 제외합니다 (`pipeline.py`의 `_same_article`). 같은 조의 항들은 서로 보완하는 내용이지 충돌이 아니기 때문입니다.

또한 `CONFLICT_PROMPT`에 "같은 단어를 쓰지만 다른 것을 규정하면 충돌이 아니다"를 구체적인 예시와 함께 넣었습니다. 처음에는 "감사의 종류"(감사규정 제5조)와 "감사의 직무"(직제규정 제5조, 정관 제30조)를 충돌로 잘못 잡았습니다. 둘 다 "감사"라는 같은 단어를 쓰지만 다른 질문(종류 vs 직무)에 대한 답이라서 충돌이 아닙니다. 지시를 구체적인 예시로 고친 뒤에는 잡히지 않았습니다.

## 11. 답변 품질 평가: LLM-as-a-Judge, RAGAS 스타일 지표 (구현 완료, 2026.10.07, PR #2)

검색 품질(Hit@k, MRR)과 별개로, **최종 답변의 품질**(정확한가, 질문에 실제로 답했는가, 근거 밖 얘기를 안 했는가)을 재는 두 가지 평가를 추가했습니다. 둘 다 "모델이 답을 채점하는" LLM-as-a-Judge 방식입니다.

### 11.1 평가셋에 대한 중요한 전제

세 가지 질문 세트가 있고, 성격이 다릅니다.

| 세트 | 개수 | 만든 방법 | 신뢰도 |
|---|---|---|---|
| v1 (`questions.jsonl`) | 277 | **조문 원문을 보면서** 만듦 | 검색 성능 측정엔 유용하지만 점수가 쉽게 나옴 (천장 효과) |
| v2 (`questions_v2.jsonl`) | 12 | 제가(Claude, 같은 세션) 만듦. 원문을 다시 읽진 않았지만, 이미 이 저장소를 많이 읽은 상태라 **완전한 블라인드가 아님** | 참고용 보조 세트 |
| v3 (`questions_v3.jsonl` + `questions_v3_edge.jsonl`) | 16(답 있음) + 19(답 없음/부분) | **원본 규정 파일을 전혀 열어본 적 없는 별도 세션**이 만듦 | **진짜 블라인드. 이 절의 기준 세트** |

처음에는 v2와 v3를 "블라인드 세트"로 합쳐서 측정했는데, v2가 진짜 블라인드가 아니라는 게 확인되어 **v3만으로 다시 측정**했습니다. 아래 수치는 모두 v3 기준입니다. v2는 섞지 않습니다.

### 11.2 LLM-as-a-Judge (`src/eval/judge.py`)

**측정 항목 (질문당)**
- **정확성 (0~5)**: 답변이 정답 근거(정답으로 라벨링된 조문 + 같은 조의 다른 항)의 내용과 실제로 맞는지. 모델에게 질문·답변·정답 근거를 주고 점수와 이유를 JSON으로 받습니다.
- **근거충실 위반 (true/false)**: 답변이 **실제로 검색되어 쓰인 근거**에 없는 내용을 말했는지. `Generator.verify()`(10절)와 역할이 비슷하지만, judge는 평가 파이프라인에서 독립적으로 다시 채점합니다.

**정답 근거를 넓힌 이유**: 처음엔 라벨링된 조문 하나만 정답 근거로 썼는데, 시스템이 **같은 조의 다른 항**(형제 항)을 같이 인용하면 "근거충실 위반"으로 잘못 잡혔습니다. 예를 들어 질문의 정답이 제5조 제1항인데 시스템이 제5조 제2항도 같이 썼다면, 이건 위반이 아니라 정상적인 확장입니다. 그래서 `judge.py`는 정답 조문의 **형제 항까지 포함**해 정답 근거를 구성합니다 (`store.siblings()` 사용).

**결과 (v3, 질문 16개 "답 있음" 기준)**

| 시점 | 평균 정확성 | 근거충실 위반 |
|---|---|---|
| v2+v3 섞어서 측정 (방법 오류, 폐기) | 3.29/5 | - |
| v3만, 임계값 재보정 전(0.3/0.6) | 2.31/5 | 10/16 |
| v3만, 임계값 재보정 후(0.05) | **3.38/5** | **6/16** |
| v3만, 프롬프트 규칙 10 추가 후(주제 혼동 방지) | 3.31/5 | 8/16 |

마지막 줄(프롬프트 규칙 추가 후)이 재보정 직후보다 살짝 낮아진 것은, 표본이 16개뿐이라 **개별 질문 1~2개가 바뀌면 평균이 흔들리는 노이즈 범위**입니다. 통계적으로 유의한 개선이라고 주장하지 않습니다. 다만 "겸직" 질문처럼 **다른 대상(임원 vs 직원)의 규정을 섞어 쓰던 자기모순 사례**는 개별적으로 확인했을 때 고쳐졌습니다.

**재보정 전(0.3/0.6) "근거충실 위반 10/16"의 실제 내용**: 10건 전부가 할루시네이션(지어낸 근거)은 아니었습니다. 그중 **9건은 "원래 답이 있는 질문인데 점수 임계값에 걸려 `none`(모름) 모드로 빠져서 근거 자체가 아예 없었던 경우"**였고, 진짜로 틀린 근거를 지어낸 경우는 1~2건(예: "인수인계 기간을 2일"이라고 사실과 다르게 말함)뿐이었습니다. 이 구분이 재보정(7.1절)의 직접적인 근거였습니다 — 문제의 대부분이 "모델이 틀리게 답한 것"이 아니라 "답할 수 있는데 못하게 막아둔 것"이었기 때문입니다.

**Hit@10(0.81)과 평균 정확성(2.31/5, 재보정 전)이 왜 이렇게 다른가**: Hit@10은 "검색이 정답을 찾았는가"만 봅니다. 정확성은 "최종 답변이 좋은가"를 봅니다. 검색은 찾았어도 리랭커 점수가 임계값보다 낮으면 모델이 그 근거를 쓰지도 못하고 "모르겠다"고 답했기 때문에, 검색 지표와 답변 품질 지표 사이에 큰 차이가 생겼습니다. 이 간극이 바로 7.1절 재보정의 동기입니다.

- 재현: `uv run python -m src.eval.judge`

### 11.3 RAGAS 스타일 지표 (`src/eval/ragas_style.py`)

실제 `ragas` 패키지는 쓰지 않았습니다. `ragas>=0.2`는 `langchain-core<1.0`을 요구하는데, 이 프로젝트는 이미 `langchain-core>=1.6.7`로 전환되어 있어(PR #1) 직접 충돌합니다(설치 시도로 확인). 구버전(`ragas==0.0.22`)은 설치는 되지만 `langchain.callbacks` 모듈이 최신 LangChain에서 제거되어 임포트 시 바로 깨집니다. 그래서 **지표 정의만 가져와서** 우리 데이터·프롬프트로 가볍게 구현했습니다.

**측정 항목 (0~1, 모두 LLM 채점)**
- **충실도 (faithfulness)**: 답변의 문장(또는 불릿) 중 몇 개가 실제로 쓰인 근거에서 나왔는지의 비율. `judge.py`의 근거충실과 비슷하지만 true/false가 아니라 비율로 봅니다.
- **관련성 (answer_relevancy)**: 답변이 질문의 요지를 실제로 다뤘는지. 내용이 맞는지는 안 보고, "동문서답인지"만 봅니다. "모른다"고 솔직히 답한 경우도 회피가 아니므로 관련성은 높게(0.8~1.0) 줍니다.
- **문맥재현 (context_recall)**: 정답 근거(조문 전체)의 핵심 내용이 **검색 단계에서 가져온 근거** 안에 들어 있었는지. 답변에 그 내용을 썼는지는 안 보고, 검색이 그 내용을 찾아왔는지만 봅니다.

**결과 (v3, 질문 16개 "답 있음" 기준)**

| 시점 | 충실도 | 관련성 | 문맥재현 |
|---|---|---|---|
| v2+v3 섞어서 측정 (방법 오류, 폐기) | - | - | 0.29 |
| v3만, 임계값 재보정 전(0.3/0.6) | 0.84 (n=5) | 0.86 (n=16) | 0.17 (n=9) |
| v3만, 임계값 재보정 후(0.05) | - | - | **0.40** |
| v3만, 프롬프트 규칙 10 추가 후 | - | - | 0.00 (n=3) |

`n`은 그 지표를 실제로 계산할 수 있었던 질문 수입니다. 충실도·문맥재현은 답변이 `answer` 모드로 근거를 쓴 경우에만 계산되므로, 재보정 전에는 16개 중 5~9개만 해당됐습니다(나머지는 `none`/`partial` 모드라 "근거"가 없어서 측정 대상에서 빠짐). 관련성은 모드와 관계없이 모든 질문(질문에 답을 시도했든, "모르겠다"고 했든)에 대해 계산되므로 n=16입니다. 마지막 줄(프롬프트 규칙 추가 후)은 n=3이라 대표성이 없어 참고 수치로만 남깁니다.

**해석**: 관련성은 꾸준히 높고(모델이 "모른다"고 솔직히 답함), 문맥재현은 낮습니다(0.17~0.40). 이 조합이 의미하는 것은 — **모델이 거짓으로 답을 지어내지는 않지만, 검색이 정답 근거를 충분히 못 찾아오고 있다**는 것입니다. 답변 프롬프트를 더 고쳐도 한계가 있고, **검색 단계(Hit@10이 16개 중 3개를 놓침, 검색_설계.md 0.1절 v3 표)** 개선이 더 중요한 다음 단계입니다.

- 재현: `uv run python -m src.eval.ragas_style`

### 11.4 두 평가의 공통 한계

- **표본이 작습니다 (16개).** 개별 질문 1~2개의 결과가 평균을 크게 흔듭니다. 추세("재보정 후 나아졌다")는 믿을 수 있지만, 소수점 둘째 자리까지의 차이를 근거로 삼지 않습니다.
- **채점자도 LLM입니다.** `judge.py`, `ragas_style.py` 모두 `gpt-4o-mini`로 채점하므로, 채점 자체의 오차가 있습니다. 사람 검증은 하지 않았습니다.
- **다음 작업 후보**: 더 많은 블라인드 질문 확보(다른 팀원에게 받기), 검색 단계에서 놓친 3개 질문(출장비, 성과급, 의무교육) 원인 분석.

## 12. 코드 검사 (`src/answer/guard.py`, 구현 완료, 2026.10.12)

11절의 결론(모델이 솔직하긴 한데 틀린 숫자·범위를 섞어 쓰는 사례가 있음)을 받아서, **모델을 다시 부르지 않고 코드로만** 잡는 검사 4종을 추가했다. 전부 `pipeline.py`의 `ask()` 안에서 실행된다.

### 12.1 숫자 바꿔치기 검사 (`unsupported_numbers`)

**사례(Q054)**: 근거 표에는 국외 일비가 "40"(외화 단위)인데, 답이 "40,000원"이라고 썼다 — 숫자는 같은데 다른 표(국내 일비, 원화)의 값이 섞여 들어간 것이다.

- 답의 각 줄에서 숫자를 뽑아, 그 줄이 인용한 근거(`[n]`)의 본문에 그 숫자가 있는지 본다. 인용이 없는 줄은 근거 전체와 비교한다.
- 질문에 이미 있던 숫자, 조·항·별표 번호, 정정 안내 줄(※)은 비교에서 뺀다.
- 근거의 비율 표현(예: "50% 가산")에서 나오는 배수(1.5배 등)는 허용한다(`_multipliers`).
- **정밀도 트레이드오프**: 근거 전체와 비교하도록 느슨하게 풀면 틀린 숫자도 통과하는 경우가 있었다(국내여비 별표1에 우연히 같은 숫자가 있어서 Q054의 틀린 "40,000원"이 통과). 인용 번호만 잘못 쓴 정상 답변 약 3건/190건이 억울하게 걸리는 건 감수한다 — **틀린 숫자가 나가는 쪽이 더 나쁘다고 판단**했다.
- 걸리면: 답을 버리고 관련 조문만 보여주고(`partial` 모드로 전환), 원래 답은 화면에 안 보이는 `withheld`에 남긴다.

### 12.2 표 범위 필터 (`filter_tables_by_scope`)

같은 규정 안에 적용 대상이 다른 별표가 여러 개 있다(여비규정: 국내 별표1, 국외 별표5, 파견 별표1의2, 외국인 초청 별표6). 이 표들이 한 근거 묶음에 섞이면 모델이 값을 섞어 쓴다(Q054가 바로 이 경우).

- 질문에서 국내/국외 출장 여부가 **확실할 때만**(`question_scope`, 국내·국외 지명 키워드로 판단, 비교 질문이거나 둘 다/둘 다 아니면 `None`) 작동한다.
- 별표 첫머리 140자에서 그 표의 적용 대상(`table_scope`)을 읽어, 질문의 범위와 다른 별표는 근거에서 뺀다. 조문(별표가 아닌 일반 조항)은 안 건드린다.
- 파견·외국인 초청처럼 질문이 그 맥락을 직접 언급하면(`_SPECIAL_MENTION`) 범위가 달라도 빼지 않는다.
- `Assistant(scope_filter=True)`로 끄고 켤 수 있다(전후 비교용). 기본은 켬.
- 뺀 내용은 `scope_excluded`에 담겨 답변에 경고로 붙는다.

### 12.3 표 비고 모순 검사 (`contradicted_distinctions`)

**사례(Q054)**: 근거 표 비고에 "일비는 등급 구분 없이 직급당 한 값"이라고 적혀 있는데, 답이 "나등급이라 일비는 40"이라고 등급으로 나눠서 설명했다 — 근거와 답이 모순이다.

- 근거 본문에서 "S는 D 구분 없이/무관" 패턴(`_NO_DISTINCTION`)을 찾아 (S, D) 쌍을 모은다.
- 답의 한 줄에 S와 D가 같이 나오는데 그 줄 자체가 "구분 없음"을 다시 말하는 게 아니면 모순으로 본다.
- 걸리면 12.1과 같은 처리(답 버리고 관련 조문만 보여줌, `withheld`에 원래 답 보관).

### 12.4 주제 바뀜 경고 (`missing_terms`)

**사례(Q073)**: 질문은 "계약보증금"인데 근거에는 사택 "임차보증금"만 있었고, 답이 "계약보증금은 임차보증금의 10%…"로 서로 다른 제도를 섞어 답했다.

- Kiwi로 질문에서 붙어 있는 명사 덩어리(3글자 이상, 예: "계약"+"보증금" → "계약보증금")를 뽑는다.
- 그 명사 덩어리가 근거 본문 어디에도 없는데 답에는 쓰였으면 의심 신호로 본다.
- **차단하지 않고 경고만** 붙인다(`질문의 "{t}"이(가) 근거 본문에 없음: 비슷한 다른 항목으로 답했을 수 있음`) — "병가"/"인병휴가"처럼 진짜 동의어도 같은 패턴으로 걸릴 수 있어서, 확정 판단이 아니라 "다시 봐야 할 신호"로만 쓴다.

### 12.5 실행 순서 (`pipeline.py`의 `ask()`)

1. 표 범위 필터(12.2) → 용어집 수치 근거 제외(검색_설계.md 9.3절, 조 본문을 항으로 나눠 걸린 항만 지움) → 근거 확정
2. 모델 답변 생성 (충돌 확인은 `FAST_PIPELINE`이면 이와 동시에 시작)
3. 문장 단위 근거 검사(10절 `verify()`) — `FAST_PIPELINE`이면 뒤에서 돌린다 (12.7)
4. **숫자 바꿔치기(12.1) + 표 비고 모순(12.3)** — 하나라도 걸리면 답을 버리고 `partial`로 전환, `withheld`에 원래 답 보관
5. 주제 바뀜 경고(12.4), 용어집·표 범위 제외 경고를 화면에 붙임

### 12.7 응답 시간 개선 (`config.FAST_PIPELINE`, 기본 켬, 2026.10.14)

호출 순서만 바꿔서 답변 내용은 같다. 끄면(`FAST_PIPELINE=0`) 예전처럼 하나씩 차례로 한다.

| 바꾼 것 | 이유 | 줄어든 시간 |
|---|---|---|
| 질문 바꿔쓰기(GPT)를 기다리는 동안 원래 질문의 벡터·BM25를 먼저 한다 (`Searcher.search(rewritten_future=…)`) | 원래 질문 검색에는 바꿔 쓴 검색어가 필요 없다 | 바꿔쓰기와 겹친 만큼 |
| 충돌 확인을 답변 작성과 동시에 | 근거만 보고 답변은 안 본다 | 약 2초 |
| 문장 근거 검사를 답을 돌려준 뒤 뒤에서 | 경고만 붙이고 답을 막지 않는다 | 약 5초 (체감) |
| 스트리밍 (`ask(…, on_token=함수)`) | 글이 생기는 대로 보여 준다 | 첫 글자까지 |

- **쓰는 법**: `r = assistant.ask(질문, on_token=화면에_붙이기, wait_checks=False)`로 답을 먼저 받고, `assistant.finish(r)`로 근거 검사 경고를 붙인다. `ask()`를 그냥 부르면(`wait_checks=True`, 기본) 예전처럼 경고까지 다 붙여 돌려준다 — Streamlit 앱과 예전 채점 스크립트는 이 방식이라 바꾸지 않아도 된다.
- **시간 기록**: 결과의 `timing`에 질문부터 첫 글자(`first_token`), 답 완성(`answer`), 검사 끝(`checks`)까지 초가 들어간다. `run_answer_eval`이 문항마다 `t_first_token`, `t_answer`, `t_checks`로 저장한다.
- **스트리밍의 한계**: 결론이 불릿과 모순이어서 다시 쓴 답(`retried`)은 스트리밍되지 않는다. 화면은 마지막에 `answer`로 바꿔 보여 줘야 한다 (100문항 중 0~2번).
- **측정** (팀 DB 항→조 + 강조, 바꿔쓰기 켬, 100문항): 첫 글자 평균 8.0초, 답 완성 10.4초, 검사 끝 15.3초. 하나씩 차례로 하던 때 답 완성 16~20초.

### 12.6 왜 "다시 쓰게" 하지 않고 "버리고 관련 조문만 보여주는" 쪽을 택했나

처음엔 검사에 걸리면 모델에게 다시 쓰게 하는 것도 검토했지만, 실측에서 **정상 답변 29건 중 22건이 억울하게 막혔다** — 검사 모델이 "맞습니다. …" 같은 결론 문장이나 실제로 맞는 문장까지 근거 밖으로 자주 표시해서(정밀도가 낮음) 재작성이 오히려 품질을 떨어뜨렸다. 그래서 10절(문장 검사)은 경고만 붙이는 쪽으로 되돌렸고, 12.1·12.3(코드 검사, 정밀도가 훨씬 높음)만 답을 실제로 막는 데 쓴다.
