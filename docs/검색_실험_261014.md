# 검색 설정 비교 실험 (2026.10.14)

항 단위 색인(팀 DB)에서 "정답 근거를 더 가져오는" 설정을 골랐다. 검색 설정은 LLM 답변 없이 Recall로 먼저 걸러내고, 채택 후보만 Luna로 100문항 답변 평가를 돌렸다.

## 1. 조건

| 항목 | 값 |
|---|---|
| 색인 | 팀 DB(항 단위, 청크 4,819개, 색인 4,595개). 읽기 전용으로만 접속 |
| 평가셋 | `eval/answer_eval_100.jsonl` (190문항에서 유형·난이도·답가능여부 비율을 유지해 뽑고 정답을 교차 검증한 100문항) |
| 답변·채점 모델 | `gpt-5.6-luna` (채점은 `src/eval/judge_answers.py`) |
| 공통 설정 | BGE-m3, 가중 RRF(벡터 0.7·키워드 0.3), BGE-reranker-v2-m3(상위 30개), 질문 나누기·동의어 사전 끔 |
| 바꿔 쓴 검색어 | 질문마다 Luna로 한 번만 만들어 모든 설정이 같은 검색어를 씀 (`eval/runs/rewrite-cache.json`) |

## 2. 검색 설정 비교 (LLM 없이 Recall)

`scripts/exp_retrieval_variants.py`. 정답 근거 (규정, 조) 중 최종 근거에 들어온 비율. 후보 계산(검색·리랭크)은 질문마다 한 번만 하고 설정별로 재사용한다. 답변 후 필터(표 범위·용어집 후처리)는 거치지 않은 근거 단계의 값이다.

| 설정 | Recall | 색인 대상만 | 전부 확보 문항 | 평균 컨텍스트 |
|---|---|---|---|---|
| A 기준 (k=5) | 0.564 | 0.591 | 49/100 | 2,756자 |
| B 조 전체 인용 복구 | 0.564 | 0.591 | 49 | 2,820자 |
| **C k=8** | **0.660** | 0.691 | **57** | 3,923자 |
| D 같은 조 묶기 | 0.583 | 0.611 | 51 | 2,917자 |
| E 동의어 사전 | 0.564 | 0.591 | 49 | 2,725자 |
| F 원질문 벡터 상위 10 보호 | 0.571 | 0.597 | 49 | 2,728자 |
| G 글자 상한 해제(진단) | 0.564 | 0.591 | 49 | 3,803자 |
| C+D | 0.686 | 0.718 | 59 | 4,276자 |
| B+C+D | 0.686 | 0.718 | 59 | 4,338자 |
| B+C+D+E | 0.692 | 0.725 | 59 | 4,281자 |
| B+C+D+F | 0.692 | 0.725 | 59 | 4,259자 |

"색인 대상만"은 색인에 없는 부칙·별지 근거를 뺀 값이다.

- **효과가 있었던 것**: k를 5에서 8로, 같은 조 묶기. 합치면 Recall +12.2%p, 정답 근거를 전부 가져온 문항 49 → 59.
- **효과가 없었던 것**: 조 전체 인용 복구(이 100문항의 정답 근거와 무관), 동의어 사전(Recall 변화 없음), 원질문 벡터 보호(1문항), 글자 상한 해제(3,000자·8,000자 한도는 병목이 아님).
- 인용 복구는 버려지던 인용(연결된 인용 2,041건 중 항으로 쪼개진 조를 가리키는 323건)을 살리는 정확성 수정이라 코드는 남긴다.

## 3. 답변 평가 (Luna, 100문항)

| 지표 | k=5 | k=8 + 조 묶기 + 인용 복구 |
|---|---|---|
| 정답 / 부분 / 오답 / 답못함 | 26 / 61 / 7 / 6 | **34 / 57 / 3 / 6** |
| 최종 근거 Recall | 0.56 | **0.67** |
| 정답 근거를 전부 확보한 문항 | 50 | 59 |
| RAGAS 충실도 | 0.89 | 0.92 |
| RAGAS 관련성 | 0.96 | 0.96 |
| RAGAS 문맥재현 | 0.69 | 0.77 |
| 평균 응답시간 | 18.5초 | 18.4초 |

문항별로는 등급이 같은 74개, 좋아진 18개, 나빠진 8개다. 근거를 더 가져온 16문항에서는 좋아진 7개·나빠진 1개로 뚜렷하다. 근거에 변화가 없는 84문항에서도 좋아진 11개·나빠진 7개가 나왔는데, 이것이 같은 입력의 결과가 흔들리는 잡음의 크기다. 그래서 정답 +8건 전부가 방법의 효과는 아니고 실제 효과는 약 +6건 정도로 본다.

근거 청크 수는 평균 13개에서 24.5개로 거의 두 배가 됐는데 응답시간은 그대로다. 시간은 입력 길이가 아니라 모델의 생각 시간이 정한다.

## 4. 이 PR의 변경

- `config.TOP_K = 8` 추가. `Assistant.ask`와 `run_answer_eval`의 기본값이 이 값을 쓴다.
- `search.GROUP_BY_ARTICLE`(같은 조 묶기), `search.CITE_WHOLE_ARTICLE`(조 전체 인용 복구). 둘 다 끌 수 있는 스위치다. 조 단위 색인에서는 효과가 없어서 안전하다.
- `PgStore`: `chunks.section`이 없는 색인(항 단위 팀 DB)에서도 읽기 쿼리가 돌게 했다.
- 평가 도구: `run_answer_eval`·`judge_answers`에 `--questions`, `run_answer_eval`에 `--k`, 합친 보고서 `src/eval/report_100.py`, 설정 비교 `scripts/exp_retrieval_variants.py`.

## 5. 한계

- 각 설정은 한 번씩만 돌렸다. 같은 입력도 문항의 약 25%가 달라지는 잡음이 있어 작은 차이는 판단하지 않았다.
- 답변과 채점이 같은 모델(Luna)이다. 채점이 후할 수 있다.
- 같은 100문항으로 여러 설정을 시험해 고른 것이라 이 문항에 맞춰졌을 수 있다. 채택 설정은 아직 보지 않은 평가셋(N-set)으로 확인해야 한다.
- 팀 DB의 한 시점(2026.10.13 05:44 색인)을 기준으로 했다.
- 부칙 근거 7건은 색인에 없어서 어떤 설정으로도 잡히지 않는다. 부칙 색인은 정책 결정이 필요해 이번에 다루지 않았다.
- 못 가져오는 근거가 아직 남아 있다(Recall 0.67, 색인 대상만 보면 0.72). 리랭커나 임베딩 쪽 개선이 필요하다.

## 6. 재현

```powershell
# 팀 DB를 가리키도록 PG_HOST, PG_DATABASE 등을 설정한 뒤 (색인 DB에 쓰지 않는다)
$env:PYTHONIOENCODING = "utf-8"

# 설정 비교 (LLM 호출은 바꿔 쓴 검색어 100개뿐, 10분 안팎)
.\.venv\Scripts\python.exe scripts\exp_retrieval_variants.py --out exp_variants_100.json

# 답변 평가 (k=8 기본, 질문 파일 지정)
.\.venv\Scripts\python.exe -m src.eval.run_answer_eval --tag k8grp_luna_100 --no-plan --questions eval\answer_eval_100.jsonl
.\.venv\Scripts\python.exe -m src.eval.judge_answers k8grp_luna_100 --questions eval\answer_eval_100.jsonl
.\.venv\Scripts\python.exe -m src.eval.report_100 --tag k8grp_luna_100 --trace rank_trace_100_para.json
```
