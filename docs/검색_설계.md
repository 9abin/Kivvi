# 검색 설계 (③ 단계)

질문을 받아 근거가 될 청크를 찾는 단계를 정리한다.
색인 구조는 `DB_스키마.md`, 색인 방식은 `재색인_설계.md`, 평가 질문은 `eval/questions.jsonl`을 본다.

**기준일: 2026.10.06**

---

## 0. 정확 조회 (구현 완료)

질문에 규정 이름과 조·항 번호가 확정되면 검색을 거치지 않고 그 조문을 직접 가져옵니다. 자동 문서 필터 가점 방식은 이 경로로 대체했습니다.

- 규칙 (`src/search/exact.py`)
  1. 질문에 규정 이름이 **하나** 있다. 공백은 무시하고, 다른 이름 안에 들어가는 짧은 이름은 긴 이름을 쓴다.
  2. 질문에 "제N조" 또는 "제N조의M"이 **한 번** 있다.
  3. 항 번호("제N항" 또는 ①~⑳)는 있으면 그 항만, 없으면 조 전체를 가져온다.
- 그 밖의 경우(규정 여러 개, 조항 여러 개, 규정 이름 없음)는 기존 검색을 쓴다.
- 정확 조회 결과는 검색 결과의 **맨 앞**에 두고, 나머지 자리는 기존 검색으로 채운다. 결과의 `match`는 "정확조회"로 표시한다.

확인: 질문 파서 시험 10개 중 9개가 기대대로 동작했다. "감사규정 제3조와 제5조 차이"(조항 두 개)와 "제2조 제2항은"(규정 이름 없음)은 None으로 정확히 걸러졌다.
주의: 항번호 질문 6개는 파서를 만들 때 보던 질문이라, 그 6개의 결과는 일반화 성능이 아니다.

## 0.1 구성 요소별 측정 (`uv run python -m src.eval.run`, 질문 277개, 2026.10.07)

| 방식 | 내용 Hit@10 | 문서명 Hit@10 | 항번호 Hit@10 | 전체 Hit@3 | 전체 Hit@10 | 전체 MRR | 놓친 질문 | 쏠림 |
|---|---|---|---|---|---|---|---|---|
| 벡터 | 0.98 | 0.96 | 0.91 | 0.93 | 0.97 | 0.88 | 2 | 0.60 |
| BM25 | 0.93 | 0.84 | 0.71 | 0.80 | 0.88 | 0.74 | 5 | 0.61 |
| RRF (0.7:0.3) | 0.98 | 0.97 | 0.88 | 0.91 | 0.97 | 0.85 | 1 | 0.65 |

질문 31개로 측정했던 이전 결과(아래 "이전 측정(참고, 질문 31개)")는 리랭킹이 오히려 해가 되는 것처럼 보였지만, 질문을 277개로 늘리자 **리랭킹이 뚜렷하게 도움이 되는 것으로 뒤집혔다** (RRF Hit@10 0.97 → RRF+리랭킹 0.99, MRR 0.85 → 0.97). 31개는 표본이 작아서 리랭킹 효과를 제대로 보여주지 못했다는 뜻이다.

읽는 법:
- 벡터 단독이 BM25 단독보다 전반적으로 강하지만, 항번호 질문(제N조 제M항처럼 숫자가 중요한 질문)에서는 둘 다 약하다(Hit@10 0.91, 0.71). 그래서 정확 조회가 필요했다.
- RRF는 벡터와 BM25를 합쳐서 벡터 단독보다 전체 MRR이 조금 낮지만(0.88→0.85), 놓친 질문은 줄었다(2→1). 리랭킹을 거치면 이 차이는 사라진다(아래 3.2절, 가중치 스윕 참고).
- 전체 검색(정확 조회+RRF+리랭킹)이 277개 중 **놓친 질문 0개**다.

### v3 재확인 (진짜 블라인드, 질문 16개, 2026.10.07, PR #2)

277개(v1)는 **조문 원문을 보면서 만든 질문**이라 점수가 비정상적으로 좋게 나왔다는 것이 이후 확인됐다(0.1절 각주, 답변_설계.md 11절). 그래서 **다른 세션이 실제 규정 파일을 전혀 열어보지 않고 쓴 질문 16개(v3, `eval/questions_v3.jsonl`)** 로 같은 비교를 다시 했다.

| 방식 | Hit@3 | Hit@10 | MRR | 쏠림 |
|---|---|---|---|---|
| 벡터 단독 | 0.69 | 0.81 | 0.59 | 0.53 |
| 키워드(BM25) 단독 | 0.50 | 0.56 | 0.35 | 0.43 |
| 하이브리드(RRF) | 0.69 | 0.81 | 0.59 | 0.55 |
| 하이브리드+리랭킹 | 0.62 | 0.81 | 0.62 | 0.53 |
| 전체 검색 | 0.62 | 0.81 | 0.62 | 0.53 |

**지표 설명**
- **Hit@3 / Hit@10**: 정답 조문이 상위 3개 / 10개 안에 들어온 질문의 비율. Hit@10 0.81이면 16개 중 13개는 찾고 **3개는 10위 안에도 없었다**(출장비 정산 시기, 성과급 기준, 의무교육 질문).
- **MRR**: 정답이 1위면 1점, 2위면 0.5점… 식으로 순위에 반비례해 평균 낸 값. "찾았는지"뿐 아니라 "몇 등이었는지"까지 반영한다.
- **쏠림**: 상위 10개 중 한 규정이 차지한 비율. 0.53이면 상위 결과 절반이 같은 규정이라는 뜻이고, 이 정도는 정상 범위다.

**읽는 법**
- 하이브리드가 벡터 단독과 Hit@10이 같다(0.81). 리랭킹도 Hit@10을 못 올렸다. v1(277개)에서는 리랭킹이 확실히 도움이 됐는데, 여기선 16개뿐이라 그 효과가 안 보이는 것일 수도 있고 실제로 어려운 질문에서 효과가 작을 수도 있다 — **이 표본으로는 단정할 수 없다.**
- v1과 비교하면 전체적으로 점수가 많이 낮다(Hit@10 0.97~1.00 → 0.81). **v1 수치를 "검색이 잘 된다"는 근거로 쓰면 안 되고, v3가 더 현실적인 기준이다.**

## 0.2 결과 형식 (구현 완료)

답변 단계가 쓰는 결과 한 줄의 구조입니다.

| 필드 | 내용 |
|---|---|
| `chunk_id`, `doc_id`, `article` | 청크 식별자, 고유번호, 조항 |
| `문서명`, `위계`, `개정표기`, `출처URL` | 출처 정보 (documents에서 가져옴) |
| `조문상태` | `현행`, `부칙`, `삭제` 중 하나. 부칙과 삭제는 현행 근거로 쓰지 않도록 표시 |
| `body` | 원문 표기 (답변 인용용) |
| `정정안내` | 확정 오탈자·참조 정정 안내 (없으면 null) |
| `score`, `rerank`, `match` | RRF 점수, 리랭커 점수, 올라온 경로 (`벡터+키워드`, `정확조회` 등) |
| `siblings` | 같은 조의 다른 항. 같은 형식 |
| `cited` | 인용 1단계 대상. 같은 형식 + `인용원문`, `연결상태` |

## 0.3 근거 조립 (구현 완료, `Searcher.assemble()`)

검색 결과를 답변 입력으로 바꾸는 단계입니다.

- 순서: 검색 결과(또는 정확 조회) → 인용 대상 → 형제 항
- 중복 제거: 청크 ID 기준으로 한 번만 넣습니다.
- 글자 예산: `config.py`의 `CONTEXT_CHAR_BUDGET` (임시 8,000자). 넘는 항목은 건너뜁니다. 답변 단계에서 실제 사용량을 보고 조정합니다.
- 묶기: (문서, 조) 단위로 묶고, 묶음 안은 항 번호 순서(숫자 기준)로 정렬합니다. 묶음 순서는 가장 높은 검색 순위를 따릅니다.
- 각 항목에 `역할`(정확조회, 검색, 인용, 형제항)을 붙입니다.

## 0.4 운영 점검 (구현 완료)

- **색인 버전**: 색인 대상 청크 수와 가장 최근 색인 시각(`index_version()`)을 기준으로 봅니다. 검색을 부를 때마다 확인하고, 바뀌었으면 BM25 역색인과 문서·청크 목록을 다시 읽습니다 (`_refresh_if_stale()`). 재시작 없이 재색인을 반영합니다.
  - 확인: 한 청크의 색인 시각을 바꾸자 다음 검색에서 버전이 바뀌어 다시 읽었고, 원래 값으로 되돌리자 버전도 원래대로 돌아왔습니다.
- **문서 필터 후보 부족**: 90개 문서 전부에 대해 문서 하나로 거르고 10개를 요청했을 때, 청크가 있는 문서는 모두 정답 수만큼 돌려줬습니다 (무작위 질의 3개). 작은 문서에서 결과가 줄어드는 문제는 이번 데이터에서는 나타나지 않았습니다. 데이터가 바뀌면 다시 확인합니다.

## 2. 키워드 검색과 BM25

### 2.1 이전 방식의 문제 (`ts_rank`, 교체 완료)
- `ts_rank`는 흔한 단어를 충분히 낮추지 못했습니다.
- "제", "조", "항"처럼 거의 모든 청크에 나오는 단어가 점수를 올려서, 정답이 상위 10개 밖으로 밀립니다. 측정에서 항번호 질문이 0점인 원인입니다.

### 2.2 결정과 구현: BM25로 순위를 매긴다 (완료)
- 방식: BM25 (`k1 = 1.5`, `b = 0.75`, 표준값, `config.py`의 `BM25_K1`, `BM25_B`)
- 토큰: Kiwi 형태소 (`chunks.body_tokens`, 색인 때 저장)
- 구현: 4,465개 청크라서 시작할 때 토큰을 메모리로 읽어 역색인을 만든다. 별도 확장 설치가 필요 없다.
- 흔한 단어의 점수는 자동으로 낮아진다 (IDF).

### 2.3 확인할 것
- 한국어 BM25 파라미터는 표준값으로 시작하고, 측정 후에만 바꾼다.
- 질의 토큰에서 "제", "조", "항"을 빼야 할지는 BM25 적용 후 측정으로 정한다. 미리 빼지 않는다.

## 3. RRF 결합과 가중치

### 3.1 방식
각 방식의 순위로 점수를 매기고 더한다.

```
점수(청크) = w_벡터 / (60 + 벡터순위) + w_키워드 / (60 + 키워드순위)
```

- `60`: RRF 상수 (표준값)
- `w_벡터`, `w_키워드`: 방식별 가중치

### 3.2 가중치

**적용: 벡터 0.7, 키워드 0.3** (`config.py`의 `HYBRID_VECTOR_WEIGHT`, `HYBRID_KEYWORD_WEIGHT`). 측정 완료, 바꿀 근거 없음.

#### 측정 방법 (2026.10.07, `src/eval/sweep_weights.py`, 질문 277개)

과적합을 피하려고 학습용/검증용으로 나눴다.

1. 질문을 유형(내용/문서명/항번호) 비율을 유지하며 **학습용 221개 / 검증용 56개**로 나눴다 (고정 시드 42). 검증용은 가중치를 고르는 동안 보지 않았다.
2. 질문마다 벡터·BM25 상위 50개를 한 번만 계산해 캐시하고, 후보 8개(벡터:키워드 = 1.0:0.0 ~ 0.0:1.0)를 **학습용 세트로, 리랭킹 없이 RRF만** 비교했다. 벡터·BM25를 후보마다 다시 돌리지 않아서 빠르다.
3. 가장 좋았던 후보와 현재 기본값을, **검증용 세트로 딱 한 번**, 정확 조회·RRF·리랭킹을 모두 포함한 실제 `search()`로 비교했다.

| 0.8:0.2 (1단계 1위) | 1.00 | 1.00 | 0.99 | 0.66 |

#### 결론

**리랭킹을 포함하면 두 값의 차이가 사라졌다.** 1단계에서 보인 차이는 RRF 단계만의 차이였고, 리랭커가 그 차이를 거의 다 메꿨다. 검증용 세트에서 두 값이 완전히 같은 점수(사실상 만점)를 받아서, **0.8:0.2로 바꿀 근거가 없다.** 그래서 **0.7:0.3을 그대로 유지한다.**

다만 검증용 56개가 전부 거의 만점이라는 것은 **이 측정으로는 두 값을 구분할 수 없다는 뜻이기도 하다** (천장 효과). 질문이 조문 원문을 보고 만들어져 실제 사용자 질문보다 쉬울 수 있다는 한계와 같은 맥락이다(0.1절). 가중치가 실제로 중요해지는 것은 벡터·키워드가 서로 다른 조문을 가리키는 더 어려운 질문에서일 가능성이 크고, 지금 세트로는 그런 경우가 거의 없었다.

확실하게 말할 수 있는 것은 **키워드만 쓰면(0.0:1.0) 뚜렷하게 나쁘다**는 것이다. 벡터를 빼면 안 된다.

#### v3(진짜 블라인드, 16개)로 재검증 (2026.10.07, PR #2)

277개(v1)는 조문을 보고 만든 질문이라 점수가 천장에 붙어 있었다(위 결론 참고). v3 16개로도 같은 방식(학습 12/검증 4, 유형 비율 유지, 시드 42)으로 다시 돌렸다.

| 가중치 | Hit@3 | Hit@10 | MRR |
|---|---|---|---|
| 0.7:0.3 (현재) | 0.50 | 1.00 | 0.45 |
| 0.9:0.1 (학습 1위) | 0.50 | 1.00 | 0.46 |

검증 질문이 **4개뿐**이라 둘의 차이(MRR 0.45 vs 0.46)는 노이즈 범위다. 이 결과만으로 가중치를 바꿀 근거는 없고, 기존 결론(0.7:0.3 유지, 키워드 단독은 쓰지 않음)이 뒤집히지도 않았다. v3는 "277개짜리 결론이 더 어려운 질문에서도 깨지지 않는지" 확인하는 용도로 쓴 것이고, 가중치를 다시 정하려면 훨씬 더 많은 블라인드 질문이 필요하다.

- 재현: `uv run python -m src.eval.sweep_weights`
- 설정 위치: `config.py`에 둔다. 코드를 고치지 않고 바꿀 수 있게 한다.

## 4. 메타데이터 필터

메타데이터 필터는 **검색 대상 문서의 범위를 먼저 좁히는 조건**입니다. 벡터나 키워드 점수를 계산하기 전이나 후에 적용합니다.

| 필터 | 예 | 용도 |
|---|---|---|
| 위계 (`documents.tier`) | "지침만", "규정만" | 질문이 규정 종류를 가리킬 때 |
| 문서 (`chunks.doc_id`) | 고유번호 23234 | 질문에 규정 이름이 있을 때 |
| 개정일 (`documents.revision`) | 2025년 이후 | 최신 개정본만 볼 때 |
| 상태 (`chunks.status`) | 정상 | 삭제 조문 제외 (색인 단계에서 이미 적용) |

- **구현**: `Searcher.search(filters=...)`에서 `tier`(위계), `doc_ids`(문서), `min_year`(개정연도)를 받는다. 필터는 벡터 검색과 BM25 모두에 적용된다.
- **미구현**: 질문에 규정 이름이 있을 때 `doc_ids`를 자동으로 채우는 규칙. 지금은 호출하는 쪽이 넘긴다.
- **자동 추출은 나중**: 질문에서 위계나 문서를 알아내는 것은 규칙 또는 별도 판정으로 한다. 지금은 호출하는 쪽이 인자로 넘긴다.

## 5. 리랭킹

- 역할: 결합으로 뽑은 상위 후보(예: 50개)를 질문과 쌍으로 다시 채점해서 상위 k개를 고른다.
- 모델: `BAAI/bge-reranker-v2-m3` (다국어, 로컬, GPU fp16). 질문과 `[문서명 장 조항] body_search`를 쌍으로 채점한다 (`config.RERANK_HEADER`, 기본 켬). 장은 2026.10.13 추가했고, 문서명은 색인에 넣지 않고 여기서만 붙인다.
- 머리말을 붙이는 이유 (2026-10-07 평가): 머리말 없이 채점하면 본문만으로 어느 규정인지 알 수 없는 청크가 밀린다. 예: 업무추진비 지침 제7조 ②("법정공휴일 또는 일요일에는 집행할 수 없으며…", 주어는 ①항에만 있음)는 리랭커 11위, 윤리헌장 2번째 항목("하나, 우리는 고객 의견을 존중하고…", 헌장 이름 없음)은 19위였다. 두 청크 모두 RRF 상위 30개 안에 있었으므로 리랭커 입력만 바꿨다. 임베딩·BM25 색인에는 머리말을 붙이지 않는다 (재색인 불필요, `재색인_설계.md` 3절).
- 효과 (질문 277개, `uv run python -m src.eval.run --rerank-header off|on`): 실제 검색(`search`) 기준 Hit@3 0.98→0.99, Hit@10 0.99→1.00, MRR 0.94→0.97, 놓친 질문 2→0. 머리말 때문에 걱정한 쏠림(내용 질문 상위 10개 중 한 규정이 차지한 비율 평균)은 0.63→0.65로 거의 그대로다.
- 적용 위치: RRF 상위 30개를 리랭커로 다시 채점하고, 그 결과로 최종 순위를 정한다.
- 이 수치는 평가셋을 만든 사람이 원문을 보며 쓴 질문 기준이라 실제 사용자 질문보다 쉬울 수 있다. 가중치·상위 개수 조정에는 질문 일부를 검증용으로 떼어 두고 쓴다.

## 9. 질문 재작성·동의어·용어집 신호 (구현 완료, 2026.10.12)

구어체 질문과 규정 용어 사이의 간극을 메우는 세 가지 장치다. 셋 다 **후보를 찾는 단계(1단계)에만** 검색어를 더하고, 리랭킹은 원래 질문으로 한다(`Searcher.search()`의 `hint`, `search.py:250-257`).

### 9.1 동의어 사전 (`data/manual/synonyms.json`, `src/search/synonyms.py`)

직원이 "법카", "사표", "코인"처럼 구어체로 쓰는 말을 규정 용어("법인카드", "사직", "가상자산")로 바꿔 검색어에 더한다. 사전에는 **규정 원문에 거의 안 나오는 구어체 말(청크 8개 이하)만** 담고, 목표어는 전부 규정 원문에 실제로 있는 말이다. 새 항목은 실제로 검색에 실패한 질문을 모아 채워 넣는다.

**끈다 (2026.10.13 결정, `config.USE_SYNONYMS = False`). 효과는 아직 재지 못했다.** 190문항 중 73문항에서 작동하는데, "입사 동기" → "이해충돌", "점심시간" → "업무추진비"처럼 엉뚱하게 붙는 경우가 있다. 실패한 평가 질문을 보고 채운 항목이 있다면 같은 평가셋으로 잰 점수가 부풀려질 수 있다. 켬/끔 비교 방법은 `팀_실행_안내.md` 2.1. 벡터 검색만으로도 구어체 질문의 정답을 50위 안에 153/160 찾으므로 사전의 몫은 순위를 조금 끌어올리는 정도로 본다.

### 9.2 질문 바꿔쓰기 (`rewrite_query`, `src/answer/generate.py`)

모델에게 질문을 규정 문서에 실제로 쓰이는 공식 용어로 한 줄 바꿔 쓰게 한다(`REWRITE_PROMPT`). `Searcher.search(rewritten=...)` 인자로 넘어가 `hint`에 합쳐진다.
**답변 파이프라인의 기본은 이 방식이다 (`config.QUERY_PLAN = False`, 2026.10.13 결정).** 질문 나누기(9.5절)를 켜면 이 호출 대신 하위 질문마다 같은 규칙으로 검색어를 만든다.

**켜 둔다 (`config.USE_REWRITE`, 기본 켬, 2026.10.14 측정).** 끄면 GPT 호출 하나가 빠지지만 아래처럼 오타 질문과 답변 품질에서 손해다.

| 측정 | 바꿔쓰기 켬 | 끔 |
|---|---|---|
| 깨끗한 질문 검색 (조 단위 93문항) Hit@5 / Hit@10 | 0.77 / 0.89 | 0.80 / 0.89 |
| 오타 질문 검색 (`eval/questions_100_typo.jsonl`) Hit@10 / Recall@10 | **0.84 / 0.714** | 0.78 / 0.665 |
| 답변 100문항 (팀 DB 항→조 + 강조 + 시간 개선) 오답 / 답못함 / 금지 위반 | **4 / 8 / 3** | 8 / 11 / 6 |
| 답 완성까지 | 10.4초 | 8.7초 |

- 깨끗한 질문에서는 벡터 검색이 구어체를 이미 잘 찾아서 차이가 없다. 오타가 있으면 GPT가 고친 검색어가 놓친 조문을 6~10위로 다시 올린다.
- 검색 측정의 바꿔 쓴 검색어는 gpt-4o-mini로 만든 것(`eval/runs/multi-cache.jsonl`), 답변 실행은 luna가 바꿔 썼다. 바꿔쓰기만 4o-mini로 하면 0.96초(luna 2.18초)라 약 1.2초 빨라진다.
- `FAST_PIPELINE`이면 바꿔쓰기를 기다리는 동안 원래 질문의 벡터·BM25를 먼저 한다(`Searcher.search(rewritten_future=…)`). 결과는 같다.

### 9.3 용어집 (`data/manual/glossary.json`, `src/search/glossary.py`)

"확인된 다른 제도" 쌍과 "보증금"처럼 같은 말머리를 쓰는 제도 묶음(family)을 담는다. 역할이 두 가지로 나뉜다.

- **검색 신호(`signal_terms`)**: 관계가 아직 미확정이거나, 질문에 특정 신호 단어가 있으면 관련 용어를 검색어에 더한다. 이건 차단이 아니라 후보를 넓히는 용도라 항상 켜져 있다.
- **수치 근거 제외(`filter_candidates`, `filter_by_glossary`)**: **"서로 다른 개념"으로 확인된 쌍에서만** 작동한다. 질문이 한쪽 용어만 말하는데, 후보 근거가 반대쪽 용어만 담고 있고 그 안에 수치·기간·비율(`has_quantity`, 정규식으로 "5만원", "30%", "10일" 등 인식)이 있으면 그 항을 후보/근거에서 뺀다. 절차나 보완 설명처럼 수치가 없는 항은 안 뺀다. 빼는 건 **리랭킹 뒤**와 **형제 항 확장 뒤** 두 군데다. 다 빼게 되면(남는 근거가 하나도 없으면) 아무것도 안 뺀다(안전장치).
- **항 단위 판정 (2026.10.13, 조 단위 청크에 맞춤)**: 청크가 조 하나라서, 본문을 ①, ② …로 나눠(`paragraphs`) 항마다 위 규칙을 적용한다. 걸린 항만 본문에서 지우고, **모든 항이 걸린 조만 통째로 뺀다**(빈자리는 다음 후보가 채운다). 조 전체를 한 덩어리로 판정하면 다른 개념의 항 하나 때문에 수치 없는 절차 항까지 빠지고, 한 조의 다른 항에 두 용어가 함께 있으면 다른 개념의 수치 항이 그대로 남기 때문이다. 경고에는 `제28조 제2항`처럼 지운 항을 적는다. 항 표시가 없는 조(한 항짜리, 별표)는 조 전체를 한 덩어리로 판정한다.
- **끔/켬 전환**: `Searcher.glossary_filter`(기본 켬)로 수치 근거 제외만 끌 수 있다. 검색 신호는 이 플래그와 무관하게 항상 작동한다 — 그래서 끔/켬 비교 실험에서도 "검색 확장"은 양쪽에서 똑같이 일어날 수 있다.
- **원칙**: 용어가 같은 개념이어도 적용 기준(직원/임원별 일수 등)이 다르면 동의어로 묶어서 기준을 합치지 않는다.

### 9.4 끔/켬 실험 (N-set, `eval/n_set/`, 진행 중)

용어집의 수치 근거 제외 효과를 "개발에 쓰지 않은 질문"으로 측정하는 평가셋. 80문항을 끔/켬 양쪽으로 돌려 비교한다. 1차 결과와 방법은 `eval/n_set/README.md`, 결론은 사람 검토가 끝난 뒤 PR에 남긴다 (아직 진행 중, 이 문서에는 반영하지 않음 — 1차 LLM 판정만으로는 신뢰할 수 없다고 확인됨).

### 9.5 질문 나누기 (`plan_queries`, `Searcher.search_plan`, 2026.10.13) — 기본 끔

**결정: 끈다.** 두세 가지를 묻는 39문항에서는 좋아졌지만(36 → 39, 단 프롬프트 예시가 평가셋과 겹쳐 부풀려졌을 수 있음), 실제 질문에 가까운 190문항 검색에서는 좋아진 3 / 나빠진 4로 차이가 없었고 리랭킹 GPU 시간이 2~3배다. 코드는 남겨 두고 `config.QUERY_PLAN`으로 켤 수 있다.

"출장여비는 어떻게 주고, 법인카드 한도는 얼마인가요"처럼 서로 다른 것을 함께 묻는 질문을 하위 질문으로 나눠 따로 검색한다. Azure AI Search의 agentic retrieval(질문 계획 → 하위 질문 병렬 검색 → 결과 합치기)과 같은 방식이다. 전체 흐름은 `질의_흐름.md`.

- **나누기**: 모델이 하위 질문 최대 3개와 하위 질문별 검색어(9.2절과 같은 규칙)를 JSON으로 돌려준다(`PLAN_PROMPT`, `parse_plan`). 바꿔쓰기 호출을 대신하므로 모델 호출 수는 같다. 한 가지만 묻는 질문은 하위 질문 1개이고 원래 질문 글자를 그대로 쓴다. 해석에 실패하면 원래 질문 하나로 검색한다.
- **검색**: 하위 질문마다 `search()`를 따로 부른다. **리랭킹도 하위 질문으로 한다.** 원래 질문 전체로 리랭킹하면 B를 찾는 조문이 질문의 절반과만 맞아서 밀린다.
- **규정 이름으로 점수를 깎는 기능은 뺐다(2026.10.13).** 원래 `_demote_unrouted`(규정 밖 후보 리랭크 점수 × 0.3)가 있었지만 넘겨줄 규정 목록을 만드는 코드가 없어 한 번도 실행되지 않았고, 효과도 잰 적이 없었다. 규정 이름은 정확 조회("규정명 + 제N조")와 리랭커 입력의 `[문서명 …]` 머리말로 이미 쓰인다.
- **합치기(`interleave`)**: 하위 질문별 결과를 1위끼리, 2위끼리 번갈아 담고 같은 청크는 한 번만 담는다. 하위 질문이 2개 이상이면 받는 개수를 `max(k, 3 × 하위 질문 수)`로 늘린다(답변 k=5 → 2개면 6, 3개면 9).
- **비용**: 리랭킹이 하위 질문 수만큼 돈다(GPU 시간 2~3배). 모델 호출은 그대로.
- **측정**: 두세 가지를 묻는 39문항(`eval/questions_multi.jsonl` 20, `eval/questions_multi_hard.jsonl` 19)에서 정답 조를 상위 6개 안에 모두 찾은 문항 36 → 39. 비슷한 주제를 함께 묻는 질문(전문계약직 채용 vs 직원 채용)과 세 가지를 묻는 질문에서 좋아졌다. 실행: `uv run python -m src.eval.run_multi --questions <파일>`.
- **2번 방식(A를 읽어야 B를 찾음)은 하지 않는다.** 이름으로 가리키는 인용은 `cites` 메타데이터로 이미 따라간다(5절). 남는 것은 "별도로 정한 바에 따라"처럼 대상 규정 이름이 없는 위임 조문(41개)이고, 사람이 대상을 정해 `cites`에 넣는 편이 싸고 확실하다.

### 9.6 항으로 찾고 조 전체 넘기기 (`Searcher._as_articles`, 2026.10.14) — 추천, 기본 끔

항 단위 색인(팀 DB, 이 PC 사본 `regulations_team`)에서 검색·리랭크하고, 답변에는 조 전체를 넘긴다(small-to-big). 조 단위 색인에서는 효과가 없어 기본은 끄고 환경 변수로 켠다 (`RETURN_ARTICLE=1`).

- **합치기**: 같은 조의 항은 가장 앞선 순위 하나로 합쳐 서로 다른 조 k개를 고르고, 각 조의 모든 항을 항 순서대로 이어 붙인다. 점수·조문 상태는 가장 앞선 항의 값. 용어집 후보 필터가 뺀 항은 이어 붙일 때도 뺀다. 형제 항은 이미 다 들어 있어 붙이지 않는다.
- **인용**: 그 조의 모든 항이 가진 `cites`를 합쳐 한 번씩만 따라간다. 이미 조 전체로 들어간 조를 가리키는 인용은 같은 내용이 두 번 들어가므로 뺀다.
- **법 인용 제한** (`LAW_CITES_FROM_HITS`): 외부 법령 인용(`외부연결`)은 검색 결과에 오른 항이 직접 인용한 것만 따라간다.
- **강조** (`HIGHLIGHT_HITS`): 그 조를 상위로 올린 항 앞에 `▶`(`HIT_MARK`)를 붙이고, 답변 입력의 근거 머리에 역할(질문으로 찾은 조문 / 인용된 조문(참고) / 같은 조 다른 항)을 적는다 (`답변_설계.md` 8.9절).
- **왜**: 조 단위 색인은 조 청크 하나가 모든 항의 인용을 들고 있어 따라오는 근거가 많고(평균 2.0개, 항→조 0.8개), 인용 조문이 검색으로 찾은 조문과 같은 모양이라 핵심 조문이 묻혔다. 조 단위에서 오답이었다가 항→조에서 오답이 아니게 된 10문항 중 8문항은 조 단위 쪽 인용 근거가 더 많았다.
- **측정** (100문항, 답변·채점 luna): 조 단위 오답 13 / 금지 위반 11 → 항→조 5 / 4 → +강조·법 인용 정리 6 / 5(정답 30, 충실도 0.900). 검색은 조 단위가 조금 낫다(Hit@1 0.46 대 0.41, Hit@10 0.89 대 0.84). 검색 지표는 항을 조로 바꿔 센다.
- **채점 단위**: 검색 평가(`rank_trace`)는 항 결과를 조 ID로 바꾸고 같은 조는 첫 번째만 센다. 답변에 조 전체가 넘어가므로 맞는 조의 아무 항이나 찾으면 된다. 정답 항이 몇 위였는지는 아직 따로 세지 않는다.

## 10. 검색 순서 (구현 기준)

0. (켰을 때만) 질문 나누기 (9.5절, `config.QUERY_PLAN`, 기본 끔). 아래 1~9를 하위 질문마다 따로 돌린 뒤 순위별로 번갈아 합친다
1. GPT 질문 바꿔쓰기 시작 (9.2절, `USE_REWRITE`). `FAST_PIPELINE`이면 기다리지 않고 2~3을 먼저 한다
2. 메타데이터 필터로 문서 범위 제한 (`filters`)
3. 원래 질문으로 벡터 검색 상위 50개, BM25 상위 50개 (같은 범위 안에서)
4. 바꿔 쓴 검색어·용어집 신호(동의어 사전은 끔)를 합친 검색어로 벡터·BM25를 한 번 더 돌려 후보에 더한다
5. 가중 RRF 결합 (벡터 0.7, 키워드 0.3)
6. 상위 30개 리랭킹 (원래 질문)
7. 용어집 수치 근거 제외 적용 (9.3절, 리랭킹 뒤, 항 단위)
8. 조 단위 색인: 상위 k개에 형제 항 확장 (3,000자 상한), `cites` 1단계 확장.
   항→조(9.6절): 서로 다른 조 k개로 합쳐 조 전체를 넘기고, 인용을 합쳐 1단계 확장 (법 인용 제한·중복 제거)
9. 답변 단계로 전달 (근거 조립 뒤 용어집 수치 근거 제외 한 번 더)
