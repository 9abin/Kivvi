# 261012-1500 챗봇 통합: 권한형 개정 기능과 가빈 DB 합치는 방식

- 관련 TODO: [regulation-db-sharing](../plans/todo/regulation-db-sharing.md), [chatbot-integration](chatbot-integration.md)
- 변경 범위: 합의안 `docs/archive/chatbot/chatbot-integration-proposal.md`, `scripts/id_map.py`, `out/id_map/` (git 제외)

## 요약
팀 방향이 "챗봇 화면 하나 + 권한 있는 사람에게 개정 기능"으로 바뀌었다. 가빈 DB(PostgreSQL+pgvector, `documents`·`chunks`)와 같은 DB에 `amend` 스키마를 따로 두고 `chunk_id`를 공통 키로 쓰는 안을 만들었다.
ID 대응 실측: 우리 항 키 4,496개 중 4,460개(99.2%)가 대응. 남은 차이는 가빈 쪽 내규관리규정 제11~26조 누락, 우리 파서의 항 합침 29건·조 누락 2개, 이름 규칙 차이.

## 주요 결정 (제안, 가빈 합의 전)
| 결정 | 이유 | 대안 |
|---|---|---|
| 같은 DB, 스키마 분리 (`public` 가빈 / `amend` 우리 / `law` 석희) | 조인 한 번으로 챗봇 답변 ↔ 개정 기능 연결. 담당 경계가 스키마로 분명 | 별도 DB 두 개: 조인 불가, ID 동기화 필요 / 가빈 표에 칸 추가: 담당 섞이고 챗봇 적재 때 덮어씀 |
| 개정 초안은 `public.chunks`에 넣지 않음 | 챗봇이 승인 전 문안으로 답하면 안 됨. 내규관리규정 제22~24조(공포·시행) | 상태 칸으로 구분: 챗봇 질의마다 필터를 빠뜨리면 바로 사고 |
| 공통 키 = 가빈 `chunk_id` | 챗봇이 이미 쓰는 키여야 답변의 인용 조항에서 개정 화면으로 바로 넘어감. 둘 다 항 단위라 99.2% 그대로 대응 | 우리 ID를 공통으로: 가빈 재적재 필요 |
| 인용 관계는 `amend.edge` 표, `cites` JSON은 챗봇용으로 유지 | JSON에는 역방향(누가 나를 인용하나) 색인이 어렵고, 간선마다 신뢰도·개정일이 필요 | `cites`만 사용: 영향 분석 불가 / `cites` 폐기: 가빈 답변 로직 수정 필요 |
| 운영 벡터는 가빈 HNSW 공유, 평가 때만 우리 벡터 | 모델(BGE-m3)·차원·청크 단위가 같음. 가빈 벡터는 보정본(`body_search`)에서 만들어 평가에는 정답이 섞임 | 항상 따로: 저장·재색인 두 번 |
| DB 역할 3개(`chatbot_ro`·`editor`·`loader`), 결정 기록은 INSERT만 | 화면을 우회해도 권한이 지켜지고, 사람 결정은 고칠 수 없게 | 앱 권한만: DB 직접 접속하면 무력화 |
| 버전은 `amend.article_version`에 | 가빈 표는 현행본만. 대비표·과거 재현·"개정 검토 중" 표시에 옛 문안 필요 | 가빈 표에 시행일·종료일: 챗봇 질의 전부 수정 |

## 변경 사항
- `scripts/id_map.py`: 가빈 `chunks.jsonl`의 ID·조항·상태만 읽어(본문·보정 칸 안 읽음) 대응표와 불일치 목록 생성. 단일 항 조(양방향), 가빈 조 단위 청크, 우리 파서 항 합침을 구분
- 실측 (가빈 master `5aea0b1`):

| 구분 | 건수 |
|---|---|
| 그대로 같음 / 단일 항 조 | 4,422 / 38 |
| 가빈에 없음: 내규관리규정(39141) 제11~26조 | 36 키 (16개 조) |
| 우리 파서가 항을 합침 (항 기호가 앞 항에 붙어 합쳐지거나 빠짐) | 29 (자금세탁행위 방지 업무지침 21, 문서관리규정 4 등) |
| 우리 파싱에 없음: 문서관리규정 제45조·제50조 | 3 키 |
| 윤리헌장 이름 규칙 | 5 |

- 버린 해석: "가빈만 있는 키 = 가빈 오류"로 일괄 분류 → 실제로는 우리 파서 쪽 누락·합침이 32건이라 원인별로 나눔.
