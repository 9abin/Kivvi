# 08. 시연 시나리오 (10/20 발표)

시연 한 번에 8~9분. 「설치 첫날 → 법령 반입 → 변경 감시 → 개정 요청 → 영향 검토 → 승인 → 공포 → 함께 개정 초안」을 한 화면(규정 도우미)에서 보인다.
준비물: Docker Desktop(`docker start reg-db`), Ollama(qwen3.5:9b, qwen2.5:7b), `uv run --extra db python app/web_server.py` → http://127.0.0.1:8765, 화면은 개정 담당자 역할로 시작.
**시연 전 확인 (각 1줄)**: 화면 오른쪽 위 연결 표시가 초록(청크 대응 끊김 없음), `/api/status`의 `stale`이 0, 채팅 모델 준비(`/api/chat/status`의 ready), 시험으로 만든 개정안의 처리(아래 「시험 흔적」)를 미리 정한다.
261015 리허설: 아래 장면 2·3·4와 공포 후 함께 개정 초안까지 API로 끝까지 돌려 확인 (리포트 47).

## 장면 1. 질문 (1분) — 일반 직원
- 일반 직원 역할: 「육아휴직은 몇 번까지 나눠 쓸 수 있나요?」 → 답변의 [n]을 눌러 오른쪽에 근거 원문. 답은 근거에 있는 것만, 개정 중이면 「개정 검토 중」 배지.
- 말할 것: 직원은 질의응답만 보인다. 개정 기능은 권한이 있는 사람에게만 보인다.

## 장면 2. 법령 반입과 변경 감시 (2분) — 개정 담당자
- 「변경 감시」: 반입된 법률 DB 두 판이 목록에 있다 (10/07판 232개, 현재 판 284개).
- 10/07판 선택 → 「기준으로만 기록」(설치 첫날). 현재 판 선택 → 「탐색 시작」 → **새로 생김 4건** (약 3초. 261015 오탐 정리 전에는 5건).
- 각 결과에 **다음 행동**이 붙는다: 「초안 가능 — 법령명 정비」 1건(여성폭력기본법 → 여성폭력방지기본법), 「현업 판단 필요 — 바뀐 법령과 대조」 3건.
- 「법령명 정비 초안으로 이동」 → 「법령명 일괄 정비」에 새 판에서 찾은 이름까지 들어 있다 (옛 이름·오기 7종 → 규정별 개정문). 규정을 골라 개정안 생성(시연 중 1건만).
- 한 건의 「조문 열기」 → 법령 대조 카드: 바뀐 법령 조문과 우리 내규 문장, 법제처 해석례.
- 말할 것: 법을 새로 반입하면 「새로 생긴 문제」만 가려 주고, 고칠 수 있는 것은 초안까지, 업무 판단이 필요한 것은 현업에 넘긴다.

## 장면 3. 개정 요청 → 개정안 → 영향 검토 (3분) — 개정 담당자
- (선택) 조문을 몰라도 된다: 「조문 열기」 검색창에 「승진 심사 결과를 공개하도록 하고 싶다」 → 고칠 후보 조문 3개(모델 추정) → 승진지침 제11조를 고름. 위치는 사람이 고른다.
- 인사규정 제30조(육아휴직)에서 개정안 작성: 「분할 횟수를 최대 3회(…총 4회)로 늘려줘」 → 로컬 모델이 개정문 초안, 적용기가 원문과 맞는지 확인.
- 개정안 검토: 신·구조문 대비표, 영향 카드(충돌 해소: 취업규칙과 값이 같아짐, 법령 대조: 남녀고용평등법 「3회」와 숫자 대조). **카드마다 근거 종류**: 문서 명시 / 낱말 일치 / 모델 추정(점선, 담당자 판단 더 필요).
- **모델 가설 카드**(낮음, 점선): 로컬 모델이 「함께 확인할 주제」를 추론해 내규를 검색한 결과. 예: 당연면직 조항 삭제 → 「퇴직금 산정과 이어질 수 있음」. 근거가 아니라 가설이며 인과 판단은 현업의 몫이라고 말한다. 개정안 작성이 약 8초 더 걸린다(`HYPOTHESIS=0`으로 끔).
- **확인한 범위**: 어떤 경로로 몇 곳을 확인했는지, 그리고 구조상 확인하지 못하는 유형(맥락상 영향 등)을 함께 보여 준다.
- **개정 절차 안내**: 인사규정은 이사회 의결 대상(이사회규정 제3조제2항제10호), 대표이사 결재, 등록·공지. 근거 조문이 같이 나온다.
- 카드를 수락·기각하고 「검토자에게 제출」.

## 장면 4. 승인과 공포, 그리고 따라 고칠 곳 (1~2분)
- 역할을 **승인권자**로 전환 → 카드 결정은 막혀 있고 「승인」/「반려」만. 기안한 사람은 자기 개정안을 승인할 수 없다(서버가 거부).
- 승인 → 수락한 카드만 반영한 최종안. 개정 담당자로 돌아와 「공포 처리」.
- **공포하면 수락한 함께 개정안이 다른 내규의 초안으로 자동 생성**된다 (알림: 「함께 개정 초안 N건」). 공포된 개정이 반영된 본문 기준으로 다시 점검한다.
  - 함께 개정이 생기는 예(리허설): 승진지침 제14조 다음에 조를 신설하고 뒤 번호를 밀면 → 징계지침 제18조 「제15조」 → 「제16조」 초안.
  - 육아휴직 개정은 번호가 안 바뀌어 함께 개정 초안이 생기지 않는다. 이 장면을 보이려면 번호가 바뀌는 개정을 쓴다.

## 장면 5. 한계를 보이며 닫기 (1분)
- 평가 표 한 장: 인용으로 이어진 문제는 거의 다 잡고(오류 주입 0.99~1.00, 골든셋 깨짐 99/100), 점검 결과의 원문 대조 정밀도는 주 목록 약 52%, 모델 추정 근거는 「참고」로 내린다. 업무 판단이 필요한 항목은 현업 검수 과제.
- 말할 것: 완벽하게 잡는 것은 불가능하다. 목표는 「사람이 놓치기 쉬운 곳을 근거와 함께 먼저 보여 주고, 확인한 범위를 밝히고, 판단은 사람이 한다」.

## 막혔을 때
| 증상 | 조치 |
|---|---|
| 화면이 「예시 데이터」 | DB 컨테이너(`docker start reg-db`)와 서버를 확인, 접속은 `127.0.0.1`. Docker Desktop이 재부팅 뒤 안 켜져 있을 수 있음 |
| 채팅이 느리다(20~35초) | 질문을 미리 한 번 해서 모델을 올려 둔다. 시연은 근거 원문이 먼저 보이는 순서로 |
| 위치 찾기·개정안 작성이 느리다 | GPU 8GB를 채팅 모델·Ollama 모델이 나눠 씀(7.8GB 사용). 쓰지 않는 Ollama 모델을 내린다(`ollama stop 모델`) |
| 연결 표시가 「청크 대응 끊김」 | `uv run --extra db python scripts/amend_load.py` (db-sharing-guide §6) |
| 개정안 작성이 실패 | 요청을 더 구체적으로(조·항·값). 「뒤 번호를 밀어」는 밀릴 범위에 가지번호 조(제4조의2)가 있으면 안 됨 → 「제3조의2로 신설」처럼. 안 되면 미리 만든 개정안(W261013-162409)을 연다 |
| 위치 찾기가 「확실하지 않음」 | 규정의 낱말과 다른 말(숙박비 ↔ 체재비)이면 못 찾을 수 있다. 규정 이름을 함께 적는다 |
