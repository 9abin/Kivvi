# 02. 기술 스펙

원본 기획 기준에 261006 설계 결정을 더했다. 확정되지 않은 것은 (미결)로 표시한다.
설계 근거: [261006-1340-04-db-design-baseline](../../reports/261006-1340-04-db-design-baseline.md)

## 환경

- 내부망 가정, 로컬 LLM (미결: 후보 2~3개 테스트)
- 임베딩: BGE-m3 (BGE-m3-ko 대비 오탐 적음, [보고서](../../reports/261006-1554-09-vector-index.md)). 청크 = 본문 조의 항(호·목 포함) + 「규정명 > 제N조(제목)」 접두어, 90건 4,467개 (윤리헌장은 전문 + 「하나」 항목 5개)
- 벡터 저장: 원본 `.npy` + 임시 Chroma (`out/vector/`). 엔진 합의 후 pgvector로 이전
- GPU: RTX 4070 Laptop 8GB (확인). 캐시 모델: bge-m3, BGE-m3-ko, bge-reranker-v2-m3, Qwen2.5-3B-Instruct
- RDB 엔진 (미결): PostgreSQL + pgvector 권장. 역방향 인덱스, 재귀 질의, 벡터 근사 검색을 한 DB에서 처리하고 법률 DB와 조인 가능. SQLite는 벡터 확장 별도 필요
- 그래프 분석: NetworkX (RDB에서 매번 메모리로 적재). 별도 그래프 DB는 쓰지 않음

## 점검 대상 오류 유형

| 유형 | 내용 | 탐지 방식 |
|---|---|---|
| 법령 개정 미반영 | 규정이 인용한 법조문이 개정·삭제·이관됐는데 규정은 그대로 | 법률 DB(법제처 원본의 조문변경여부·시행일·개정문) × 우리 법령 인용, 인용 쪽 마지막 개정일과 비교 → 대조 요청 ([261007-1629-23](../../reports/261007-1629-23-law-db.md)) |
| 법령 내용 불일치 | 명시 인용 없이 같은 사항을 법과 다르게 정함 | 법령 검색 + LLM, 판정 없이 표시 |
| 내부 참조 오류 (대상 없음) | 존재하지 않는 조·항 인용 (F3) | SQL |
| 내부 참조 오류 (대상 불일치) | 대상은 있으나 내용이 인용 문맥과 다름, 번호 밀림 (F1·F2·F4~F6) | 인용 제목 대조(규칙) + 설명구·reranker 순위(후보), 대안 조문은 참고 제시 ([리포트](../../reports/261006-1603-10-semantic-check.md)) |
| 규정 간 인용 오류 | 폐지되거나 명칭이 바뀐 규정 인용 | SQL |
| 구 명칭·용어 잔존 | 바뀐 부서명·기관명이 남아 있음 | SQL (`term`) |
| 용어 정의 불일치 | 정의 조문의 개념 관계(상위·하위·동의어)와 다르게 쓰임 (예: 「무기계약직(일반직)」) | `term` 관계 + 사용 문맥, 판정 없이 표시 |
| 개정 미반영 | 인용 대상이 전부개정·번호 재배열·이동된 뒤 인용 쪽이 갱신되지 않음 (확인된 인용 오류 17건 중 15건 패턴) | 원문 개정 표시·연혁 날짜 비교, 강한 신호만 단독, 나머지는 기존 결과의 근거로 ([261007-1601-22](../../reports/261007-1601-22-history-signal.md)) |
| 근거 소멸 조항 | 삭제·폐지된 조문이나 제도에 의존하는 조항 (X1·X3·X4) | `edge` 도착이 삭제·폐지 상태, 판단 불가로 표시 |
| 규정 간 수치 충돌 | 같은 사항을 다르게 정한 규정 조문 | `slot` 주제키 조회 + LLM, 판정 없이 표시 |

엣지 상태값(`ok`, `missing_*`, `title_mismatch`, `name_mismatch`, `unknown_regulation`, `external_rule`, `law_pending`)과 오류 유형 대응: [261006-1544-08](../../reports/261006-1544-08-citation-edges.md)

부칙의 옛 명칭·옛 번호 리다이렉트(예: 내규관리규정 부칙 제2조)와 옛 부칙의 경과조치는 오류에서 제외한다.
범위 제외: 책임·권한 공백 (권한이 직무전결규정·직제규정에 모여 있어 오탐이 크고 정답 데이터 없음). → [261006-1347-05](../../reports/261006-1347-05-extra-check-cases.md)

## 챗봇과의 관계

규정 원문 DB는 공유하고 산출물은 분리하는 안을 제안 중이다. 수정안 승인은 개정이 아니며, 규정 DB는 공지된 개정본의 시행일 기준으로만 바뀐다. → [261006-1148-02](../chatbot/261006-1148-02-chatbot-db-relation.md)

## 운영 방식: 기준선 + 변경분

1. 원문은 오류가 있는 그대로 적재한다. 원문은 고치지 않는다.
2. 최초 1회 전수 점검으로 **기준선**(기존 이슈 목록)을 만든다. 이것이 첫 결과물이다.
3. 담당자가 승인한 결과는 **보정 계층**(엣지의 의도 대상, 용어 매핑)에 반영한다.
4. 이후 변경(새 조항, 수정안, 법령 반입)은 **변경분만** 보고한다: (변경 반영 상태의 finding) − (기준선 finding). 기존 이슈는 "기존 미해결"로 따로 표시한다.

## 변경 점검: 후보 수집 → 정밀 점검

전수 LLM 비교(약 300만 쌍)는 불가능하다. 초안 1건만 분석한 뒤 인덱스로 후보를 모으고, 후보에만 규칙과 LLM을 적용한다.

| 경로 | 찾는 것 | 조회 |
|---|---|---|
| 나가는 인용 | 초안이 인용한 조문·법조문 | `edge` 출발 인덱스 |
| 들어오는 인용 | 이 조문을 인용하는 조문 (수정·삭제·번호 변경 파급) | `edge` 도착 인덱스 |
| 위임·준용 사슬 | 상위 규정, 하위 지침 | 재귀 질의 2단계 |
| 같은 주제 값 | 같은 주제키 조문 | `slot` 주제키 인덱스 |
| 용어 | 정의 조문, 구 명칭 | `term` |
| 의미 유사 | 상위 k개 | 벡터 근사 검색 |
| 같은 규정 | 정의 조문, 앞뒤 조문 | 규정ID |

후보 전체에 SQL 규칙 → 주제·의미가 겹치는 후보에만 LLM 비교 → finding에 발견 경로 기록.
놓침 대비: 후보 재현율을 주입셋으로 측정하고, 같은 주제 묶음 전체 점검을 주기적으로 따로 돌린다.

## 인용 없이 이어지는 영향 (261015)
후보 수집 경로에 정의 용어(정의 조의 용어를 쓰는 곳), 의미 이웃(조문 대 조문 유사도, 점수 ≥ 0.78 + 다음 이웃과의 간격 ≥ 0.03, 아니면 참고), 같은 내규 신설 중복(점수 ≥ 0.82 + 1위-2위 간격 ≥ 0.04), 가설 카드(로컬 LLM이 추론한 「함께 확인할 주제」)를 더했다. 모든 카드에 근거 종류(문서 명시 / 낱말 일치 / 모델 추정)를 붙이고 점검 결과에 「확인한 범위」를 함께 낸다. 모델 추정 카드는 낮음·참고로만, 개정안당 6장까지. 기준선 점검은 근거가 약한 묶음(의미 비교만, 부칙의 옛 번호, 재탐색에서 지금 인용한 조가 1위)을 「참고」로 내리고, 인용이 없거나 내용이 다른 곳에는 옮겨 간 곳 후보를 붙인다. 근거: 리포트 43~50.

## 개정문 적용과 대비표 (v0)

개정문을 규정 사본에 적용해 신·구조문대비표를 만든다(`regcheck.amend`, `scripts/amend.py`). 원문·규정 DB는 바꾸지 않는다.
지원 문장: 「중 "A"를 "B"로 한다」(조·항·호·목, 제목), 「중 "A"를 삭제한다」, 「를 삭제한다」, 「를 다음과 같이 한다」(조·항), 「의 다음에 제X조를 다음과 같이 신설한다」, 「제A조부터 제B조까지를 각각 제C조부터 제D조까지로 한다」.
못 읽거나 대상이 없으면 멈춘다. 출력 `out/changes/{id}/changeset.json`: 문장, 조문별 변경, `label_map`(원래 조문ID → 새 번호, 삭제는 null), 대비표 행. 근거: [261007-1145-14](../../reports/261007-1145-14-amendment-compare.md)

## 변경안 점검 (v0)

`regcheck.change_check`, `scripts/check_change.py`. changeset 하나 → 인용받음·문서 인용(관련 조항 표), 같은 제목(메타데이터), 의미 유사(보조), 재검사로 후보 수집 → 깨짐·새 충돌 후보·해소 후보·확인 필요·법령 대조·판단 불가로 분류. 번호 이동은 같은 규정 안 인용 = 깨짐(새 번호 제안), 다른 규정 = 확인 필요(부칙 「다른 내규와의 관계」에 달림). 값 비교는 같은 제목 후보에만. 출력 `out/changes/{id}/check.json`, 시나리오(`eval/scenarios/`) 채점 포함. 근거: [261007-1152-15](../../reports/261007-1152-15-change-check.md)

## 검토 화면과 결정 기록 (v0)

`app/review_app.py`(Streamlit). 결정은 `eval/review_log.jsonl`에 덧붙이기만 한다(`regcheck.review`): 열쇠(위치·문구·종류 해시), 이전·다음 상태, 검토자, 일시, 의견. 마지막 줄이 현재 상태. finding_log 테이블의 PoC 형태. 근거: [261007-1158-16](../../reports/261007-1158-16-review-screen.md)

## RDB 테이블

**현재 구현 (261012)**: 아래 설계 중 ①원문·②관계·④점검 계층을 가빈 규정 DB 안 `amend` 스키마로 구현 (`sql/amend_schema.sql`, 로컬 사본, 합의 전). 가빈 표(`public.documents`·`chunks`)는 읽기만, 공통 키는 가빈 `chunk_id`, 역할 4개 → [261012-1540-31-amend-schema](../../reports/261012-1540-31-amend-schema.md), [합의안](../chatbot/chatbot-integration-proposal.md). ③의미 계층(`slot`·`term`·`embedding`)과 법률 DB 표는 아직 파일·SQLite.

담당 구분은 [law-db-interface](todo/law-db-interface.md), [regulation-db-sharing](todo/regulation-db-sharing.md)에서 확정한다.

### ① 원문 계층
| 테이블 | 주요 컬럼 | 담당 |
|---|---|---|
| `regulation` | 규정ID, 규정명, 위계(정관·규정·지침), 소관부서, 최종 개정일, 시행일, 상태(시행·폐지) | 챗봇과 공유 제안 |
| `article_version` | 조문ID, 규정ID, 단위(본문·부칙·별표·별지), 조·항·호·목, 제목, 본문, 시행일, 종료일, 상태(현행·폐지·초안) | 챗봇과 공유 제안 |
| `form` | 서식ID, 규정ID, 서식 번호, 제목, 개정 표시, 근거 조문ID, 텍스트 보관 여부 | 박형건 |
| `appendix_table` | 별표ID, 규정ID, 항목, 조건, 값, 단위 | 확인 필요 (챗봇 TAG와 공유) |
| `amendment` | 규정ID, 개정일, 개정 내용 요약, 부칙 | 확인 필요 |

### ② 관계 계층 (관련 조항 표)

구현: `out/relations/relations.jsonl`, 컬럼과 정확도는 [리포트 11](../../reports/261006-1744-11-relations.md). "그래프"는 그래프 DB가 아니라 이 표 + 역방향 조회를 뜻한다. 영향 관계는 유사도가 아니라 같은 열쇠(조문 번호·용어·대상·속성)로 미리 연결하고, 수정할 때는 조회만 한다.

| 테이블 | 주요 컬럼 | 담당 |
|---|---|---|
| `edge` | 출발 조문ID, 유형, 적힌 대상(원문 표현·해석 결과), **의도 대상**(담당자 확인), 해석 상태(정상·대상 없음·의심·확인됨), 출처(정규식·LLM·수작업) | 박형건 |

- 유형: 인용, 위임, 준용, 정의, 버전 대체, 법 이관, 명칭 변경
- 도착은 조문, 법조문, 규정(문서 단위 위임) 중 하나
- 인덱스: 출발, 도착 양쪽. 영향 분석은 의도 대상이 있으면 의도 대상을 따른다
- 원본 기획의 `citation`·`reg_law_citation`을 이 테이블로 통합

### ③ 의미 계층
| 테이블 | 주요 컬럼 | 담당 |
|---|---|---|
| `slot` | 조문ID, 주제키, 대상, 속성, 값, 단위, 조건 | 박형건 |

## 별표·별지 처리

261006 간이 집계: 별지 231개, 별표 84개.
- **별지서식**은 본문 조문과 분리된 `form` 단위로 메타데이터만 저장한다. 서식 안의 인용은 `edge`로 뽑고 인용 문장은 원문 표현에 남긴다. 본문의 "별지 제N호서식" 참조(약 575건)로 근거 조문을 연결하고 실제 서식과 맞는지 점검한다. 레이아웃은 ALIO 원문 링크로 대신한다.
- 계약서·안내문형 서식(약 10개, 예: 사옥관리지침 임대차계약서, 개인정보 위탁계약서)은 텍스트를 보관한다. 이 서식 안의 「제N조」는 본문 조문과 섞이지 않게 별지 단위로 구분한다.
- **별표** 중 수치 기준표(숫자 3개 이상 약 28개)만 `appendix_table`로 구조화한다.
