# RAG 검색 단계 실험 안내 (하루 작업)

- 작성: 2026-10-17, 박형건
- 대상: 같은 사양 PC(GPU 8GB, RAM 32GB, Windows)를 쓰는 팀원
- 예상 시간: 준비 1시간 + 실행 5~6시간 + 정리 1시간
- 관련: [1차 결과 리포트 53](../../reports/261016-1800-53-rag-combo-results.md), [평가셋 v2 리포트 54](../../reports/261017-0030-54-golden-domain-check-candidates.md)

## 1. 왜 하는가

답변 품질의 병목은 생성 LLM이지만, 그건 이 PC로 더 밀어붙이기 어렵다(답변 생성은 API와 비교해 한계 · 향후 과제로 남긴다). 대신 **답변 전 단계(검색)** 는 싸게 돌릴 수 있고 개선이 숫자로 보인다. 검색 단계의 손잡이를 한 표로 정리하고, 정확도와 시간 · LLM이 읽는 양의 균형점을 찾는다.

검색 흐름: 질문 (→ 바꿔 쓰기) → 후보 검색(벡터 + 키워드) **상위 N개** → 리랭커 → (LLM 선택: 리랭크 **상위 P개** 중 고름) → 답변 모델에 **K개** 넘김

| 손잡이 | 실험 값 | 지금 값 | 왜 보는가 |
|---|---|---|---|
| 임베딩 | bge-m3 / Qwen3-Embedding-4B | Qwen3-4B | 4B가 크게 앞섰다. 8B는 4B와 차이가 없어 제외 |
| 하이브리드 가중치 (벡터 : 키워드) | 0.7:0.3 / 0.85:0.15 / 1.0:0 | 0.7:0.3 | 0.7:0.3은 bge-m3 때 정한 값. 강한 임베딩에서는 키워드가 잡음일 수 있다 |
| 질문 바꿔 쓰기 (LLM) | 켬 / 끔 | 켬 | 질문당 LLM 호출 1번. 끄면 빨라진다 |
| 리랭커 | bge-reranker-v2-m3 / 없음 / **없음 + LLM 선택(LLM이 리랭커 대신)** | bge | 임베딩이 강하면 효과가 작아질 수 있다. 종류 비교(bge 대 Qwen3-Reranker)는 차이가 없어 제외 |
| **N** 리랭커에 넘기는 후보 수 | 20 / 30 / 50 | 30 | 늘리면 천장이 오르지만 리랭커가 헷갈릴 수 있다 |
| LLM 선택 | 끔 / 켬 | 켬 | 켜면 조금 오르지만 질문당 수 초 |
| **P** 선택 때 LLM이 보는 후보 수 | 10 / 16 / 24 | 16 | LLM이 읽는 양 |
| **K** 답변 모델에 넘기는 근거 수 | 5 / 8 / 10 / 12 / 16 | 10 | 답변 LLM이 읽는 양 (가장 비싼 단계) |

## 3. 준비 (1시간)

1. 가빈 저장소를 `origin/master`(커밋 `c11c97b` 이후)로 받고, 그 저장소의 가상환경을 만든다(`uv sync` 등 저장소 안내대로).
2. 저장소 루트에 `.env`를 만든다: `PG_HOST`, `PG_PORT`, `PG_DATABASE`, `PG_USER`, `PG_PASSWORD` (공유 DB 접속 정보, 박형건에게 받기). DB는 읽기만 한다.
3. Ollama 모델 받기:
   ```
   ollama pull qwen3-embedding:4b-q8_0
   ollama pull qwen3:30b-a3b-instruct-2507-q4_K_M
   ```
   bge-m3와 bge 리랭커는 처음 실행할 때 자동으로 받는다.
4. 박형건이 준 `rag_retrieval_bundle_v2.zip`(약 55MB)을 **저장소 루트에 풀기**. 들어 있는 것:
   - `configs/combo/round2/ret_*.toml` 기본 설정 8개 (임베딩 2 × 리랭커 2 × 선택 2)
   - `scripts/combo_weight_run.py` 가중치 · 후보 수를 바꿔 실행하는 래퍼 (가빈 코드는 고치지 않음)
   - `scripts/ret_grid.sh` 실행, `scripts/ret_summary.py` 결과 표
   - `eval/answer_eval_100_tiered_v2.jsonl`, `eval/rewrite_none.json` (바꿔 쓰기 끔용 빈 파일)
   - `eval/combo/answer_eval_100_tiered_v2/` 캐시: 30B 바꿔 쓰기 결과, 문서 임베딩(4B · bge-m3). 이게 있으면 문서 임베딩(각 15~20분)과 바꿔 쓰기를 다시 안 한다
5. 확인: 아래 1단계를 시작하고, 첫 조건이 끝났을 때 화면에 `결과 저장:` 줄이 나오는지 본다. `Traceback`이 나오면 `logs/` 폴더의 해당 로그를 박형건에게 보낸다.

## 4. 실행

모든 명령은 저장소 루트의 Git Bash에서. 가상환경 python 경로가 `.venv/Scripts/python.exe`가 아니면 앞에 `PY=경로`를 붙인다.

### 1단계: 선택 끔, 임베딩 · 가중치 · 바꿔 쓰기 · 리랭커 24개 조건 (1~1.5시간)

```
bash scripts/ret_grid.sh 0
```

- 임베딩(2) × 리랭커(2) × 바꿔 쓰기(2) × 가중치(3) = 24개. N = 30
- LLM을 쓰지 않는다(바꿔 쓰기는 캐시). 조건당 2~4분
- **K(5 · 8 · 10 · 12 · 16)는 한 번 실행에서 모두 계산된다.** 추가 비용이 없다

### 2단계: 선택 끔, 후보 수 N (30분)

1단계 **상위 2개 조건**만 N = 20, 50으로 다시 돌린다(30은 1단계 결과).

```
WIN=20 bash scripts/ret_grid.sh one 0 qwen4b_bge 0 100
WIN=50 bash scripts/ret_grid.sh one 0 qwen4b_bge 0 100
```

인자: `one <선택 0|1> <임베딩_리랭커> <바꿔쓰기 0|1> <가중치 070|085|100>`. 임베딩_리랭커는 `qwen4b_bge`, `qwen4b_none`, `bgem3_bge`, `bgem3_none`. 위 예시의 조건은 1단계 결과에 맞게 바꾼다.

### 3단계: 선택 켬, 선택 후보 수 P, LLM이 리랭커를 대신하는 경우 (2~2.5시간)

1단계 · 2단계에서 고른 **최종 후보 1개**와 **지금 운영 설정**(qwen4b_bge, 바꿔 쓰기 켬, 0.7, N 30)을 선택 켬으로, P = 10, 16, 24 각각 돌린다. 30B가 질문마다 K = 5 · 8 · 10에 대해 한 번씩 고르므로 조건당 15~20분.

```
POOL=16 bash scripts/ret_grid.sh one 1 qwen4b_bge 1 070            # 지금 운영 설정
POOL=10 bash scripts/ret_grid.sh one 1 qwen4b_bge 0 100            # 최종 후보 (예시)
POOL=16 bash scripts/ret_grid.sh one 1 qwen4b_bge 0 100
POOL=24 bash scripts/ret_grid.sh one 1 qwen4b_bge 0 100
```

N을 바꾼 후보라면 앞에 `WIN=50` 등을 같이 붙인다.

**LLM이 리랭커를 대신하는 경우**도 같은 단계에서 본다. 리랭커 없음 + 선택 켬이면 교차 인코더 없이 30B가 검색 순서(RRF) 상위 P개를 직접 읽고 고른다. 리랭커가 없으니 P를 크게(30이면 후보 전부) 잡아야 공정하다. 조건당 15~25분.

```
POOL=16 bash scripts/ret_grid.sh one 1 qwen4b_none 0 100
POOL=30 bash scripts/ret_grid.sh one 1 qwen4b_none 0 100
```

(바꿔 쓰기 · 가중치는 최종 후보와 같게 맞춘다.) 비교: 「리랭커 bge + 선택 켬」과 「리랭커 bge + 선택 끔」 대비 정확도와 시간. 1차 실험(9B)에서는 LLM이 리랭커를 대신하지 못했다(−1.6~−6.4%p). 30B에서도 같은지 확인한다.

### 4단계: 시험용 확인 (가능하면, 30분~1시간)

개발용 100문항에서 여러 조건을 골랐으므로, **최종 후보 1~2개와 지금 운영 설정만** 시험용(holdout) 문항으로 한 번 확인한다. 시험용 파일 위치는 김가빈에게 확인한다(설정 주석에는 `eval/answer_eval_holdout.jsonl`로 적혀 있다). 시험용은 바꿔 쓰기 캐시가 없어 30B가 처음부터 돈다.

## 5. 결과 정리

```
python scripts/ret_summary.py eval/combo_rw1_w070_c30/answer_eval_100_tiered_v2/results_qwen3-embedding-4b-q8_0_bge-reranker-v2-m3_qwen3-30b-a3b-instruct-2507-q4_k_m_S0.json
python scripts/ret_summary.py eval/combo_rw1_w070_c30/answer_eval_100_tiered_v2/results_qwen3-embedding-4b-q8_0_bge-reranker-v2-m3_qwen3-30b-a3b-instruct-2507-q4_k_m_S0.json --k 8
```

- 인자는 기준 결과 파일(지금 운영 설정, 선택 끔). 모든 결과를 표로 내고 `out_ret_summary.csv`로 저장한다
- `--k`는 짝지은 비교 · 전부확보 · 시간을 어느 K로 볼지(기본 10). K = 5 · 8 · 10으로 각각 돌려 보면 「K를 줄여도 되는가」가 보인다
- `기준대비@K`는 질문 단위 짝지은 차이와 95% 구간. **구간이 0을 포함하면 「차이 없음」으로 본다**

| 열 | 뜻 |
|---|---|
| 후보수 · 선택 | N, 선택 여부와 P |
| 후보 천장 | 후보 N개 안에 필수 근거가 든 비율 |
| 리랭크16 | 리랭크 상위 16개 안 비율 |
| 최종@K | 답변 모델에 넘기는 근거 K개 안 비율 (**주지표는 최종@10**, K를 줄일 수 있는지는 @5 · @8과 비교) |
| 전부확보@K | 필수 근거를 모두 넘긴 문항 수 (99문항 중) |
| Hit@1 | 리랭크 1위가 필수 근거인 문항 수 |
| 검색p50 | 질문 하나의 검색 시간 중앙값 (바꿔 쓰기 + 후보 + 리랭크 + 선택) |

## 6. 주의

- `config.py`(운영 설정)와 가빈 코드는 고치지 않는다. 가중치 · N은 래퍼가 실행 중에만 바꾼다
- **가중치 · N은 캐시 파일 이름에 안 들어간다.** 스크립트가 `eval/combo_rw<바꿔쓰기>_w<가중치>_c<N>/` 폴더로 나누고, P는 결과 파일 이름 끝(`_p16`)으로 나눈다. 손으로 돌릴 때 폴더를 섞으면 결과가 틀린다
- 30B를 쓰는 동안(3 · 4단계) RAM이 빠듯하다. 브라우저 등 큰 프로그램을 닫는다. 실행이 끝났는데 python 프로세스가 남아 메모리를 잡고 있으면 작업 관리자에서 끈다
- 바꿔 쓰기 끔은 **LLM 바꿔 쓰기만** 끈다. 동의어 확장과 용어집 신호어(코드 규칙)는 그대로 붙는다
- 같은 조건을 다시 돌리면 결과 파일은 `_2`, `_3`이 붙고, `ret_summary.py`는 가장 최근 것만 쓴다
