# RAG 실험 파이프라인 (발표 스토리 기준)

- 작성: 2026-10-17, 박형건
- 목적: 지금까지의 조합 실험과 남은 실험을 **하나의 흐름(스토리)** 으로 묶는다. 단계마다 「가설 → 실험 → 지표 → 실패 분석 → 다음 단계로 가는 이유」를 남긴다
- 관련: [1차 조합 결과 리포트 53](../../reports/261016-1800-53-rag-combo-results.md), [평가셋 v2 리포트 54](../../reports/261017-0030-54-golden-domain-check-candidates.md), [검색 단계 팀원 실험 안내](rag-retrieval-experiment.md)

## 0. 한 줄 스토리

> 기준 임베딩(bge-m3)은 질문과 조문이 직접 대응하지 않는 질문에 약했다 → LLM 기반 임베딩(Qwen3-Embedding-4B)으로 바꾸자 그 유형이 크게 좋아졌고, 8B로 키워도 더 나아지지 않았다 → 검색 부품 중에서는 리랭커보다 임베딩이 결정적이었다 → 근거를 잘 찾아도 로컬 30B의 답변은 아쉬웠다 → 결국 품질은 **임베딩과 답변 생성 LLM**이 정한다. 우리 하드웨어 제약 때문에 답변 생성은 가성비 좋은 API(luna)로 상한선을 확인했고, 운영 서버급 로컬 LLM은 향후 과제로 남긴다.

## 1. 단계별 파이프라인

| 단계 | 질문(가설) | 바꾸는 것 | 상태 |
|---|---|---|---|
| ① 기준선 | 지금 운영 임베딩(bge-m3)은 어디서 못 찾는가 | 없음 (기준) | 완료 |
| ② 임베딩 교체 | LLM 기반 임베딩이 추론형 질문을 더 잘 찾는가 | bge-m3 → Qwen3-Embedding-4B | 완료 |
| ③ 체급 확인 | 더 크면 더 좋은가 | 4B → 8B | 완료 |
| ④ 검색 부품 | 리랭커 · 가중치 · 바꿔 쓰기 · 개수(N · P · K) 중 무엇이 중요한가 | 4B 고정, 부품만 | 일부 완료, 나머지 팀원 ([안내](rag-retrieval-experiment.md)) |
| ⑤ 답변 생성 | 근거를 잘 찾으면 로컬 LLM으로 충분한가 | 답변 LLM: 로컬 30B / API | 30B 완료, API 남음 |
| ⑥ 정리 | 무엇이 품질을 정하는가, 운영에서는 어떻게 | - | 발표 전 |

## 2. 공통 고정 조건

| 항목 | 값 |
|---|---|
| 평가셋 | `eval/answer_eval_100_tiered_v2.jsonl` (100문항, 필수/보조 근거, 유형 8가지). 정답 근거가 색인에 있는 99문항으로 검색을 잰다 |
| 리랭커 | bge-reranker-v2-m3 (④에서만 바꿈) |
| 바꿔 쓰기 · LLM 선택 · 답변 | Qwen3-30B-A3B-Instruct-2507 q4 (로컬, Ollama). ⑤에서만 답변 모델을 바꿈 |
| 근거 개수 | 후보 30 → 리랭크 상위 16 → 선택 10 → 답변에 10개 |
| 채점 | gpt-5.6-luna, tiered(필수 요지 대조) |
| 실행 환경 | GPU 8GB · RAM 32GB, Ollama 주소 `127.0.0.1` |

## 3. 지표

| 구분 | 지표 | 뜻 |
|---|---|---|
| 검색 | **최종@10** (주지표) | 답변 모델에 넘긴 근거 10개 안에 필수 근거가 든 비율 |
| 검색 | 후보@30 | 후보 30개 안 비율 (임베딩의 천장) |
| 검색 | 전부 확보 | 필수 근거를 모두 넘긴 문항 수 |
| 검색 | **유형별 최종@10** | 질문 유형 8가지별로 나눠 본 값 (실패 분석의 뼈대) |
| 답변 | 정답 / 부분 / 오답 / 답못함 | LLM 채점 판정 |
| 답변 | 금지 위반 | 틀린 단정 (할루시네이션의 한 형태) |
| 공통 | 짝지은 차이와 95% 구간 | 같은 질문끼리 비교. **구간이 0을 포함하면 「차이 없음」** |
| 공통 | 시간 p50 | 질문 하나의 검색 · 답변 시간 |

## 4. 단계별 내용

### ① 기준선: bge-m3 (완료)

- 결과: 최종@10 **0.810** (선택 켬), 0.802 (선택 끔)
- 실패 분석(유형별 최종@10):

  | 유형 (문항 수) | bge-m3 |
  |---|---|
  | 수치 기준 (24) | 0.92 |
  | 단일 조문 사실 (7) | 0.89 |
  | **일부만 답 가능 (26)** | **0.66** |
  | **규정에 없음 (4)** | **0.25** |

- 해석: 질문 말이 조문에 그대로 있는 질문(수치, 단일 조문)은 잘 찾는다. **질문과 정답 조문이 말로는 멀고 연결해서 생각해야 하는 질문**(「강아지가 죽었는데 휴가 있나요?」 → 경조휴가 목록, 「부모님 가게 돕는 것도 겸직?」 → 영리업무 금지)에서 크게 떨어진다
- 다음 단계로 가는 이유: 이런 연결은 문장 의미를 더 깊게 보는 LLM 기반 임베딩이 나을 것이다

### ② 임베딩 교체: Qwen3-Embedding-4B (완료)

- 결과: 최종@10 **0.889** (+6~8%p, 짝지은 비교에서 유의). 일부만 답 가능 0.66 → **0.83**, 규정에 없음 0.25 → **1.00**
- 4B가 새로 찾은 10문항 중 8개가 「일부만 답 가능 · 규정에 없음」. 4B가 놓친 쪽으로 바뀐 문항은 2개
- 남은 실패: 「회사 메일 열람」 → 정보보안관리지침 접근기록 조항처럼, 정답이 간접 근거인 질문 몇 개

### ③ 체급 확인: Qwen3-Embedding-8B (완료)

- 결과: 최종@10 0.897 (+1%p, **유의하지 않음**). 후보 천장은 조금 오르지만(0.929 → 0.960) 최종 근거에서는 차이가 사라진다
- 결론: 임베딩 효과는 4B에서 포화. GPU 메모리(8B는 약 5GB 더)를 생각하면 **4B가 비용 대비 최적**

### ④ 검색 부품 (일부 완료, 나머지는 팀원)

| 부품 | 지금까지 결과 | 남은 것 |
|---|---|---|
| 리랭커 유무 | 약한 임베딩에서는 +9~14%p로 꼭 필요, 4B에서는 +0.8%p로 효과 작음 | 4B 기준 재확인 |
| 리랭커 종류 | bge 대 Qwen3-Reranker-4B 재현율 차이 없음, Qwen3 쪽이 30초 이상 느림 | 하지 않음 |
| 하이브리드 가중치 | 벡터 비중을 올리면 최고 0.905 (방향은 일관, 유의하지 않음) | 4B · bge-m3 각각 3가지 |
| 질문 바꿔 쓰기 | 끄면 검색 1.56초 → 0.27초, 재현율 거의 같음 | 조합별 확인 |
| 후보 수 N | 30 → 50이면 리랭크 상위 16 재현율이 오히려 떨어짐(0.921 → 0.897) | 20 / 30 / 50 |
| 선택 후보 P · 답변 근거 K | - | P 10 / 16 / 24, K 5~16 |
| LLM이 리랭커 대신 | 9B에서는 못 함(−1.6 ~ −6.4%p) | 30B로 확인 |

- 결론(예상): **임베딩이 결정적이고 리랭커는 「있으면 충분」**. 남은 손잡이는 정확도보다 **시간과 LLM이 읽는 양을 줄이는 데** 쓴다

### ⑤ 답변 생성: 로컬 30B 대 API (30B 완료, API 남음)

- 30B를 기준으로 고른 이유: 9B는 LLM 선택에서 「K개를 고르라」는 지시를 63~71% 어겼다(30B는 3~7%). **어느 정도 역할을 하려면 30B급은 있어야 한다**고 판단했다. 밀집형 32B(EXAONE 4.0)는 같은 20문항에서 30B와 정답 수가 같고 이 PC에서 8배 느려 제외했다
- 30B 결과: 정답 40 / 부분 25 / 오답 31 / 답못함 4. 오답 · 부분 · 답못함 60개 중 **47개는 필수 근거를 받고도 틀렸다** → 검색이 아니라 답변 단계의 문제. 주된 오류는 「확인 필요라고 해야 할 때 단정」(과잉 단정)
- API 비교 (남음):
  - **검색 · 선택 결과는 30B 실행 그대로 고정**하고 답변 모델만 바꾼다. 차이를 답변 모델 탓으로만 돌리기 위해서
  - 답변 모델: gpt-5.6-luna (가성비, 팀 기존 사용)
  - **채점 편향 주의**: 답변도 luna, 채점도 luna면 자기 채점이다. 다음 중 하나를 함께 한다
    1. 계열이 다른 API 모델로 한 번 더 채점해 순위가 같은지 본다
    2. 사람이 20~30문항을 판정해 LLM 채점과 일치도를 본다 ([검토 페이지](https://claude.ai/artifact/TkgEEN35xT55qJTjpRKLE1)의 메모 사용)
  - 같은 표로 비교: 정답 · 오답 · 금지 위반 · 「현업확인 = 부재」 28문항 정답 수 · 답변 시간
- API는 폐쇄망 운영에서 쓸 수 없으므로 **「상한선 참고치」** 로 표시한다

### ⑥ 결론 · 한계 · 향후 과제

- 결론: 품질은 **임베딩(찾기)과 답변 생성 LLM(쓰기)** 이 정한다. 임베딩은 4B로 최적화를 마쳤고, 답변 LLM은 하드웨어 제약 때문에 API로 상한선을 확인했다
- 한계
  - 평가셋 100문항(구간 약 ±10%p), 팀이 만든 질문이라 실제 직원 질문과 분포가 다를 수 있다
  - 정답 해석이 들어간 18문항(현업확인 = 해석)은 현업 확인 전이다
  - LLM 채점이고, 사람 판정과의 일치는 15문항으로만 확인했다
  - 개발용에서 조건을 골랐으므로 시험용(holdout) 확인이 필요하다
- 향후 과제
  - 운영 GPU 서버에서 더 큰 로컬 LLM으로 답변 생성 재평가
  - 답변 구조 개선: 「직접 정한 조항이 있는가」를 먼저 판단하는 두 단계 답변, 답변 뒤 단정 · 숫자 검사
  - 운영 단계 평가: 현업 담당자가 답변 표본을 주기적으로 검수하고, 틀린 사례를 평가셋에 더하는 순환
