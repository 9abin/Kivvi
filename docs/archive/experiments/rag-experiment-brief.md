- 받는 사람: 팀원 PC에서 일하는 Claude. 이 문서를 처음부터 끝까지 읽고 순서대로 진행한다

- 최종 산출물: `reports/rag-story-<날짜>.md` 리포트 1개와 결과 폴더 묶음 (8절)

## 0. 목표

발표(10/20)에 쓸 **「검색 · 답변 품질을 무엇이 정하는가」 스토리를 데이터로 찾는다.** 예상 흐름은 아래와 같지만 **가설일 뿐**이다. 데이터가 다르게 나오면 데이터를 따르고, 다르게 나왔다고 리포트에 쓴다.

> 기준 임베딩(bge-m3)이 어떤 질문에서 실패한다 → 원인을 보고 LLM 기반 임베딩(Qwen3-Embedding-4B)으로 올린다 → 무엇이 좋아졌는지 확인 → 8B로 더 올려 본다(포화 여부) → 검색 부품(리랭커 · 가중치 · 바꿔 쓰기 · 개수) 중 무엇이 중요한지 본다 → 근거를 잘 찾아도 로컬 30B 답변이 아쉬운지 본다 → API 답변과 비교해 한계와 향후 과제를 정리한다

**각 단계가 끝날 때마다 반드시 「원인 분석」을 하고 기록한다(5절 양식).** 숫자만 적지 말고, 왜 그 숫자가 나왔는지 실제 질문과 조문을 읽고 설명한다. 이 기록이 다음 단계를 고르는 근거가 된다.

## 1. 지켜야 할 규칙

1. **가빈 코드와 운영 설정(`config.py`)은 고치지 않는다.** 바꿔야 할 값은 `scripts/combo_weight_run.py`(래퍼)와 `--set`으로만 바꾼다
2. **공유 DB는 읽기만** 한다
3. **외부로 아무것도 보내지 않는다.** 1~4단계는 로컬 모델(Ollama)과 공유 DB만 쓴다
4. 결론은 **짝지은 비교와 95% 구간**으로 낸다. 구간이 0을 포함하면 「차이 없음」이라고 쓴다. 「좋아 보인다」로 결론 내지 않는다
5. 질문 단위 실패 사례를 인용할 때 **질문 원문, 정답 조문, 시스템이 가져온 것**을 같이 적는다. 추측으로 원인을 만들지 않는다. 확인 못 하면 「추정」이라고 쓴다
6. 막히면(같은 오류 2번, 30분 넘게 진전 없음) 멈추고 사람에게 로그와 함께 묻는다

## 2. 준비 (1시간)

1. 가빈 저장소(`9abin/kvic-internal-regulations-review`)를 `origin/master`로 받고 저장소 안내대로 가상환경을 만든다. 이후 모든 명령은 **저장소 루트, Git Bash**에서 실행한다
2. 저장소 루트 `.env`: `PG_HOST`, `PG_PORT`, `PG_DATABASE`, `PG_USER`, `PG_PASSWORD`(공유 DB, 사람에게 받기)
3. Ollama 모델:
   ```
   ollama pull qwen3-embedding:4b-q8_0
   ollama pull qwen3-embedding:8b
   ollama pull qwen3:30b-a3b-instruct-2507-q4_K_M
   ```
4. 사람에게 받은 `rag_experiment_package.zip`을 저장소 루트에 푼다. 들어 있는 것:
   - `configs/combo/round2/ret_<임베딩>_<리랭커>_S<선택>.toml`: 임베딩 `bgem3` · `qwen4b` · `qwen8b`, 리랭커 `bge` · `none`, 선택 `S0`(끔) · `S1`(켬)
   - `scripts/combo_weight_run.py` 하이브리드 가중치 · 후보 수를 실행 중에만 바꾸는 래퍼
   - `scripts/ret_grid.sh` 검색 실행, `scripts/ret_summary.py` 결과 표, **`scripts/ret_analyze.py` 원인 분석**
   - `scripts/ans_run.sh` 답변 단계(25문항씩 나눠 실행), `scripts/merge_answer_chunks.py` 합치기
   - `eval/answer_eval_100_tiered_v2.jsonl` 평가셋(100문항, 질문 유형 8가지, 필수/보조 정답 근거, 현업확인 표시), `eval/rewrite_none.json`
   - `eval/combo/answer_eval_100_tiered_v2/`: 30B 바꿔 쓰기 결과와 문서 임베딩 3종(bge-m3 · 4B · 8B). 이게 있으면 문서 임베딩(모델당 15~35분)을 건너뛴다
5. 확인: `bash scripts/ret_grid.sh one 0 bgem3_bge 1 070`이 2~5분 안에 `결과 저장:`을 출력하면 준비 끝

## 3. 실행할 때 알아 둘 것 (이전 실험에서 겪은 문제)

- **긴 실행이 메모리 부족으로 꺼질 수 있다.** Claude Code는 기다리는 동안 메모리가 부족하면 백그라운드 실행을 끈다. 30B를 쓰는 단계(선택 켬, 답변)는 RAM 32GB에서 빠듯하다. 그래서 답변 단계는 `ans_run.sh`로 25문항씩 저장하며 돌리고, 기다리는 동안 짧은 명령으로 진행 상황을 자주 확인한다. 그래도 꺼지면 남은 묶음만 다시 돌린다
- **끝난 python 프로세스가 메모리를 붙잡고 남을 때가 있다.** 결과 파일이 저장됐는데도 같은 설정의 python이 남아 있으면 끈다
- **Ollama 주소는 `127.0.0.1`.** 설정 파일에 이미 들어 있다(`localhost`는 윈도우에서 호출마다 약 2초가 붙는다)
- **가중치 · 후보 수는 캐시 파일 이름에 안 들어간다.** `ret_grid.sh`가 `eval/combo_rw<바꿔쓰기>_w<가중치>_c<후보수>/` 폴더로 나눈다. 손으로 돌릴 때도 이 규칙을 지킨다
- 같은 설정을 다시 돌리면 결과 파일 이름 끝에 `_2`가 붙는다. 분석에는 가장 최근 파일을 쓴다

## 4. 단계

공통 고정: 리랭커 bge-reranker-v2-m3, 바꿔 쓰기 · 선택은 30B, 후보 30 → 리랭크 16 → 최종 10, 평가셋 v2. 주지표는 **최종@10**(답변 모델에 넘긴 근거 10개 안에 필수 근거가 든 비율). 결과 파일 위치는 `eval/combo_rw1_w070_c30/answer_eval_100_tiered_v2/results_<임베딩>_..._S<0|1>[_p16].json`이다.

### 1단계: 기준선 bge-m3 (20분)

```
bash scripts/ret_grid.sh one 0 bgem3_bge 1 070
bash scripts/ret_grid.sh one 1 bgem3_bge 1 070
```

원인 분석:
```
python scripts/ret_analyze.py types  bge=<bge-m3 S1 결과>
python scripts/ret_analyze.py misses bge=<bge-m3 S1 결과>
```
- 질문 유형 8가지 중 **어디서 낮은지** 찾는다
- 놓친 질문 10개 이상을 직접 읽고 묶는다. 예: 질문 말이 조문에 그대로 있는데도 놓쳤는가, 질문과 정답 조문이 말로는 멀고 연결해서 생각해야 하는가(「강아지가 죽었는데 휴가?」 → 경조휴가 목록), 정답이 「규정에 없음」을 보여 주는 간접 근거인가, 약어 · 구어(「법카」)인가
- 놓친 단계(후보 30 밖 / 리랭크에서 탈락 / 최종에서 탈락) 중 **임베딩 탓(후보 30 밖)이 얼마인지** 본다
- 기록: 「bge-m3는 ○○ 유형에 약하다. 이유는 ○○로 보인다. 그래서 다음 단계에서 ○○를 시험한다」

### 2단계: Qwen3-Embedding-4B (20분)

```
bash scripts/ret_grid.sh one 0 qwen4b_bge 1 070
bash scripts/ret_grid.sh one 1 qwen4b_bge 1 070
```

원인 분석:
```
python scripts/ret_analyze.py paired bge=<bge S1> q4b=<4B S1>
python scripts/ret_analyze.py types  bge=<bge S1> q4b=<4B S1>
python scripts/ret_analyze.py diff   bge=<bge S1> q4b=<4B S1>
python scripts/ret_analyze.py misses q4b=<4B S1>
```
- 1단계에서 찾은 약한 유형이 **실제로 좋아졌는가**. 4B가 새로 찾은 질문들이 그 유형인가
- 4B가 오히려 놓친 질문도 읽는다(있다면 왜)
- 4B도 못 찾는 질문은 어떤 종류인가(임베딩을 바꿔도 남는 한계)

### 3단계: Qwen3-Embedding-8B (20분)

```
bash scripts/ret_grid.sh one 0 qwen8b_bge 1 070
bash scripts/ret_grid.sh one 1 qwen8b_bge 1 070
```

원인 분석: 2단계와 같은 명령을 `q4b` 대 `q8b`로. 확인할 것
- 후보@30(천장)과 최종@10이 **각각** 얼마나 오르는가. 천장은 오르는데 최종이 안 오르면, 늘어난 정답이 리랭크 · 선택에서 다시 빠진다는 뜻이다. `misses`로 어느 단계인지 본다
- 8B가 의미 있게 낫지 않으면 「4B에서 포화」로 결론 내고, 비용(GPU 메모리 · 시간)과 함께 적는다

### 4단계: 검색 부품 — 무엇이 중요한가 (2~3시간)

임베딩은 2 · 3단계 결론에 따라 고른 것(예상: 4B)으로 고정하고, 부품을 하나씩 바꾼다. bge-m3로도 같은 비교를 하면 「임베딩이 약할 때와 강할 때 부품 효과가 다른가」가 보인다.

| 부품 | 명령 (예: 임베딩 qwen4b) | 볼 것 |
|---|---|---|
| 리랭커 유무 | `one 0 qwen4b_none 1 070` 대 `one 0 qwen4b_bge 1 070` (bge-m3도 같이) | 임베딩이 강할수록 리랭커 효과가 줄어드는가 |
| 하이브리드 가중치 | `one 0 qwen4b_bge 1 085`, `one 0 qwen4b_bge 1 100` | 0.7 : 0.3은 bge-m3 때 정한 값. 강한 임베딩에서 키워드가 잡음이 되는가 |
| 바꿔 쓰기 | `one 0 qwen4b_bge 0 070`, `one 0 qwen4b_bge 0 100` | 끄면 정확도와 시간이 각각 어떻게 되는가 |
| 후보 수 N | `WIN=20 bash scripts/ret_grid.sh one 0 ...`, `WIN=50 ...` | 늘리면 천장은 오르지만 리랭커가 헷갈리는가(리랭크16 비교) |
| 선택 켬 · P | `POOL=10/16/24 bash scripts/ret_grid.sh one 1 ...` (조건당 15~20분) | LLM이 읽는 양을 줄여도 되는가 |
| LLM이 리랭커 대신 | `POOL=16`, `POOL=30`으로 `one 1 qwen4b_none ...` | 30B 선택이 교차 인코더 리랭커를 대신할 수 있는가 |
| 답변 근거 K | 선택 끔 결과의 최종@5 · 8 · 10 · 12 · 16 (추가 실행 없음) | K를 줄여도 되는가 |

`one` 인자: `<선택 0|1> <임베딩_리랭커> <바꿔쓰기 0|1> <가중치 070|085|100>`.

정리: `python scripts/ret_summary.py <기준 결과> [--k 10|8|5]`가 모든 결과를 표와 `out_ret_summary.csv`로 낸다. 원인 분석은 바뀐 질문 위주로 `diff`를 쓴다. 기록할 결론 예: 「임베딩을 바꾼 효과(+○%p)가 리랭커 유무(+○%p)보다 컸다」.

### 5단계: 답변 생성 — 로컬 30B (**이번 범위 아님**, 박형건이 따로 실행. 참고용으로 남겨 둠)

4단계에서 고른 **최종 검색 설정 1개**로 답변까지 돌린다. 검색 · 선택 결과는 그 설정의 캐시를 그대로 쓴다.

```
TAG=p16 bash scripts/ans_run.sh eval/combo_rw1_w070_c30 configs/combo/round2/ret_qwen4b_bge_S1.toml local
python scripts/merge_answer_chunks.py ans_local.json eval/combo_rw1_w070_c30_ans_local_q*/answer_eval_100_tiered_v2_q*/answers_*.json
```
(바꿔 쓰기 끔 설정이면 앞에 `RW=0`도 붙인다. 묶음 하나에 30~60분. 먼저 `... local 1`로 첫 묶음만 돌려 판정이 나오는지 확인한다.)

원인 분석:
- 판정(정답 · 부분 · 오답 · 답못함), 금지 위반, 평가셋의 `현업확인` 표시별(해석 · 부재 · 없음) 정답 수
- 오답 · 부분 · 답못함 문항마다 **필수 근거를 받았는데 틀렸는가, 근거를 못 받아서 틀렸는가**를 나눈다(답변 결과의 `entries`와 평가셋 근거 비교)
- 근거를 받고도 틀린 답변 10개 이상을 읽고 오류를 묶는다. 예: 「확인 필요」라고 해야 할 때 단정함, 숫자를 다른 조문에서 가져옴, 다른 대상(임원 · 공무직) 규정을 적용함, 예외를 빠뜨림
- 기록: 「검색은 ○%를 맞혔는데 답변은 ○개가 틀렸고, 그중 ○개는 근거를 받고도 틀렸다 → 병목은 답변 LLM」인지 아닌지

참고로 로컬 LLM을 30B로 정한 이유(1차 실험): 9B는 LLM 선택에서 「K개를 고르라」는 지시를 63~71% 어겼고(30B는 3~7%), 밀집형 32B(EXAONE 4.0)는 같은 문항에서 30B와 정답 수가 같았지만 이 사양에서 8배 느렸다.

### 6단계: 답변 생성 — API 비교 (**이번 범위 아님**, 박형건이 따로 실행. 참고용으로 남겨 둠)

**검색 · 선택은 5단계와 똑같이 두고 답변 모델만** gpt-5.6-luna로 바꾼다.

```
TAG=p16 bash scripts/ans_run.sh eval/combo_rw1_w070_c30 configs/combo/round2/ret_qwen4b_bge_S1.toml api
python scripts/merge_answer_chunks.py ans_api.json eval/combo_rw1_w070_c30_ans_api_q*/answer_eval_100_tiered_v2_q*/answers_*.json
```

- **채점 편향 주의**: 답변도 luna, 채점도 luna면 자기 채점이라 API 쪽이 후하게 나올 수 있다. 다음 중 하나를 꼭 한다
  1. 사람에게 로컬 · API 답변 20문항씩을 판정해 달라고 요청하고, LLM 채점과의 일치율을 적는다
  2. 계열이 다른 API 채점 모델을 쓸 수 있으면 한 번 더 채점한다(쓸 수 있는지 사람에게 먼저 묻는다)
- 비교 표: 정답 · 부분 · 오답 · 답못함 · 금지 위반 · 「현업확인 = 부재」 정답 수 · 답변 시간
- 같은 질문에서 로컬은 틀리고 API는 맞힌 답변을 5개 이상 나란히 놓고, 무엇이 달랐는지 적는다
- API는 폐쇄망 운영에서 쓸 수 없으므로 리포트에는 「상한선 참고치」로 쓴다

## 6. 해석 기준

- 차이는 짝지은 비교로 본다(`ret_analyze.py paired`). 구간이 0을 포함하면 「차이 없음」
- 99문항이라 1~2문항 차이는 잡음일 수 있다. 유형별 표는 문항 수가 적은 유형(4~8문항)에서 크게 흔들리니 문항 수를 함께 적는다
- 평가셋의 `현업확인 = 해석` 18문항은 정답 자체가 해석에 기대므로, 답변 정답 수는 「전체」와 「해석 문항 제외 82문항」 두 가지로 적는다

## 7. 이미 알려진 사실 (같은 환경에서 다시 나오는지 확인용)

1차 실험(10/16~17, 같은 사양 PC)에서 나온 값이다. 다시 돌려 크게 다르면 환경 차이를 먼저 의심하고 사람에게 알린다.

- 최종@10 (선택 켬): bge-m3 0.810, Qwen3-4B 0.889, Qwen3-8B 0.897
- 4B 기준 리랭커 없음 0.857 (선택 끔), 벡터만(가중치 1.0) 0.905 (선택 켬)
- 로컬 30B 답변: 정답 40 · 부분 25 · 오답 31 · 답못함 4
