# RAG 조합 실험 가이드

임베딩 · 리랭커 · LLM 조합을 로컬 모델(8GB GPU)로 비교해 최적 조합을 정한다. 4명이 나눠서 수행한다.

## 1. 비교 변수와 사용 모델

| 변수 | 수준 | 모델 / 실행 방식 |
|---|---|---|
| 임베딩 (E) | E1 기준 | `BAAI/bge-m3` (SentenceTransformer, fp16, GPU, DB `regulations_team`) |
| | E2 도전 | `Qwen/Qwen3-Embedding-0.6B` (1024차원, DB 사본 `regulations_team_qwen3`, 질문 지시문 `config.EMBED_QUERY_INSTRUCT`) |
| | (선택 확장) | `Qwen3-Embedding-4B` (2,560차원, Ollama `qwen3-embedding:4b-q8_0`): DB 벡터 컬럼이 1024차원 고정이라 스키마 변경 또는 1024차원 축소가 필요. 박형건 담당 |
| 리랭커 (R) | R0 | 없음 (RRF 순서 그대로) |
| | R1 기준 | `BAAI/bge-reranker-v2-m3` (CrossEncoder, fp16, GPU) |
| | R2 도전 | `Qwen/Qwen3-Reranker-4B` (transformers, fp16, GPU 6GiB + 나머지 CPU 오프로드) |
| LLM (L) | L1 | `qwen3.5:9b` (Ollama) |
| | L2 | `qwen3:30b-a3b-instruct-2507-q4_K_M` (Ollama, MoE) |
| 선택 단계 (S) | 끔 / 켬 | 켬: 리랭크 상위 16개 중 LLM이 8~10개 선택 |

### LLM이 쓰이는 자리
| 기호 | 역할 | 이 실험에서 쓰는 LLM |
|---|---|---|
| R′ | 질문 바꿔 쓰기 | L1, L2 (각자 담당 LLM이 직접 생성) |
| S | 리랭커 뒤 근거 선택 | L1, L2 |
| G | 답변 생성 | L1, L2 (상위 조합에만 실행) |
| V | 충돌 확인, 근거 검사, 채점 | 채점 모델은 **후보(L1, L2)에 없는 모델로 확정 필요** (미정) |
| 참고 기준선 | 저장된 바꿔 쓰기 캐시 | `gpt-5.6-luna`가 만든 캐시 (비교 기준으로만 사용) |

후속 비교(본 실험 이후): LLM만 API 모델로 교체 — `gpt-5.6-luna`, 업스테이지 Solar(모델 ID 확인 필요).

## 2. 실험 조합과 담당

E(2) × R(3) × L(2) × S(2)의 24개 중 아래 20개를 4명이 나눠 수행한다. 한 사람이 임베딩과 LLM을 고정하고 리랭커와 선택만 바꾼다.

| 담당 | 임베딩 | 리랭커 | LLM | 선택(S) | 실행 수 |
|---|---|---|---|---|---|
| 이민형 (쉬운 조합) | `bge-m3` | 없음, `bge-reranker-v2-m3` | `qwen3.5:9b` | 끔 · 켬 | 4 |
| 한석희 | `Qwen3-Embedding-0.6B` | 없음, `bge-reranker-v2-m3` | `qwen3:30b-a3b-instruct-2507-q4_K_M` | 끔 · 켬 | 4 |
| 김가빈 | `Qwen3-Embedding-0.6B` | 없음, `bge-reranker-v2-m3`, `Qwen3-Reranker-4B` | `qwen3.5:9b` | 끔 · 켬 | 6 |
| 박형건 | `bge-m3` | 없음, `bge-reranker-v2-m3`, `Qwen3-Reranker-4B` | `qwen3:30b-a3b-instruct-2507-q4_K_M` | 끔 · 켬 | 6 |

- `Qwen3-Reranker-4B`는 후보 목록당 약 43분이 걸려 대각선 두 칸(김가빈, 박형건)에만 둔다. 임베딩 두 수준과 LLM 두 수준에서 각각 한 번씩 관찰된다.
- 이민형의 칸(bge-m3 · 9B · 리랭커 없음/bge)은 기준 구성이므로 시작 전 공통 기준 실행을 겸한다.
- 30B 담당(한석희, 박형건)은 RAM 약 18GB 이상 필요. 4명의 PC 사양은 동일(RTX 4070 Laptop 8GB)로 확인됨.
- 박형건은 추가로 `Qwen3-Embedding-4B`를 선택 확장으로 측정한다(후보 단계 지표까지).

## 3. 고정 조건
- 평가셋: 개발용 `answer_eval_100_tiered.jsonl` (필수 126 · 보조 64 근거). 시험용 `answer_eval_holdout`은 마지막에 상위 2개 조합에만 1회.
- 후보 단계: 벡터 상위 50 + BM25 상위 50, 원질문과 바꿔 쓴 질문 각각, 가중 RRF(벡터 0.7 · 키워드 0.3, k=60), 상위 30.
- 리랭커 입력: `[문서명 조항] 본문_검색`, 점수 입력은 원질문.
- 근거 구성(형제 항 확장, 인용 복구, 8,000자 예산)과 LLM 프롬프트, 온도 0은 모두 동일.
- 코드 커밋 해시와 평가 파일 해시를 결과에 기록.

## 4. 실행 순서

GPU 메모리 제약으로 단계를 나눠 실행하고 중간 결과를 저장한다. 단계 사이에 `ollama stop`으로 GPU를 비운다.
**모든 단계는 질문별 소요 시간을 결과와 함께 저장한다** (5.3절).

| 단계 | 내용 | 저장 |
|---|---|---|
| ① 바꿔 쓰기 | 담당 LLM으로 질문 전체 생성 | `rewrite_<L>.json` |
| ② 후보 | 담당 임베딩으로 문서·질문 임베딩, 후보 30개 | `emb_<E>.npy`, `cands_<E>_<L>.json` |
| ③ 리랭크 | R0 · R1 · R2 각각 점수 계산 | `rerank_<E>_<L>_<R>.json` |
| ④ 선택 끔 | 상위 k개를 그대로 사용 | 지표 계산 |
| ⑤ 선택 켬 | 리랭크 상위 16에서 LLM 선택 | `select_<조합>.json` |
| ⑥ 답변·채점 | 주지표 상위 조합에만 (5.4절: 답변 생성 → LLM 채점 3종 → RAGAS 3지표) | `answer_runs/<조합>/` |

시작 전 **공통 기준 실행**: 4명 모두 기본 구성(E1 · R1 · 선택 끔 · luna 바꿔 쓰기 캐시)을 돌려 아래 값과 일치하는지 확인한다.
- 후보 30개 안 필수 근거 0.904 (113/125)
- 리랭크 후 필수 Recall@8 0.800, @16 0.896, Hit@1 41/98
- 시간 기준값(RTX 4070 Laptop 8GB): bge 리랭크 질문당 0.3초, 질문 임베딩 bge-m3 15ms

## 5. 지표

단위: **질문**. 근거는 서로 다른 조·별표(노드)로 센다. 색인에 없는 근거(부칙, 별지, 삭제 조)는 제외하고 개수를 표에 적는다.

### 5.1 단계별
| 단계 | 지표 |
|---|---|
| 바꿔 쓰기 | 후보 Recall@30 변화(원질문만 대비), 실패율(빈 출력, 형식 위반), 없는 규정명·조 번호 포함 여부 |
| 후보 | 필수 근거 Recall@10 · @30 · @50, 벡터 단독 Recall@30 |
| 리랭크 | 필수 근거 Recall@k (k=5 · 8 · 10 · 16), Hit@1, MRR, nDCG@8(필수 2 · 보조 1), 후보 Recall@30 대비 보존율 |
| 선택 | 선택 후 Recall@8 · @10, 선택이 살린 필수 근거 수와 버린 수, 출력 이상률(개수 위반, 파싱 실패, 후보 밖 선택) |
| 최종 근거 | 필수 근거 Recall(확장·인용 복구 후), 질문 단위 전부 확보율, 평균 조 수와 글자 수 |
| 답변 | 5.4절 참고 (LLM 채점 정답 · 부분 · 오답 · 답못함, 금지 위반, RAGAS 충실도 · 관련성 · 문맥 재현, 답불가 질문의 거절, 보류율) |
| 효율 | 5.3절 참고 (단계별 시간 p50 · p95, 질문당 총 시간, GPU 피크 메모리, RAM, 모델 적재 시간, 토큰 수) |

### 5.2 주지표와 보호 지표
- **주지표**: 최종 근거 Recall(필수) at k=8.
- **부지표**: 질문 단위 전부 확보율, Hit@1, MRR, 보조 근거 Recall.
- **보호 지표** (하나라도 어기면 채택하지 않음): 질문당 검색 시간(5.3절의 합계, 허용선 제안: 수십 초 이내), 8GB에서 실행 가능, 유형별 부분집합에서 현행 대비 뚜렷한 하락 없음.
- 답변 지표(5.4절)는 주지표가 비슷한 상위 2~3개 조합을 가를 때만 사용한다. 이때 `tiered` 정답 수를 주 지표로, `question` · `strict`와 RAGAS 3지표를 보조로 본다.

### 5.3 시간·자원 측정

**무엇을 재는가** (질문마다, 초 단위, 모두 결과 파일에 저장)

| 항목 | 정의 |
|---|---|
| 바꿔 쓰기 | LLM 호출 시작부터 응답 완료까지 |
| 후보 | 질문 임베딩 + 벡터 검색 + BM25 + RRF 합치기 |
| 리랭크 | 후보 30개 점수 계산 (캐시 적중이면 원래 계산 시간을 함께 기록) |
| 선택 | LLM 호출 시작부터 응답 완료까지 (선택 끔이면 0) |
| 확장 | 형제 항 · 인용 복구 · 근거 조립 |
| **검색 합계** | 바꿔 쓰기 + 후보 + 리랭크 + 선택 + 확장 |
| 답변 (⑥ 실행 시) | 첫 글자까지, 답 완성까지 |

**어떻게 재는가**
- 단계마다 `time.perf_counter()`로 감싸고, 첫 질문의 모델 적재 지연은 따로 적는다 (측정에서 제외하지 말고 「적재 시간」으로 별도 기록).
- 시간을 아끼려고 **캐시를 쓰는 단계는 원래 계산 시간을 캐시에 같이 저장**했다가 합계에 더한다. 그렇지 않으면 선택 켬과 큰 리랭커의 시간이 실제보다 짧게 나온다.
- 다른 프로그램(웹 서버, 다른 Ollama 모델)을 끄고 측정한다.

**요약에 넣는 값**
- 단계별 p50 · p95, 검색 합계 p50 · p95
- 모델 적재 시간, 토큰 수(입력 · 출력, LLM 호출 단계)
- GPU 피크 메모리 (`nvidia-smi` 또는 `torch.cuda.max_memory_allocated`, Ollama는 `ollama ps`), RAM 피크, 양자화 · 오프로드 여부(Qwen3 리랭커 4B는 CPU 오프로드)
- 측정 환경 한 줄: GPU, RAM, 드라이버, 모델 태그, `num_ctx`

**해석**
- 같은 사양(RTX 4070 Laptop 8GB)에서 측정한 값끼리만 비교한다.
- 시간은 정확도와 같은 표에 놓고 효율-정확도 산점도의 가로축으로 쓴다.

### 5.4 답변 단계: LLM 채점과 RAGAS (가빈 평가 코드 그대로)

답변은 비싸므로 **주지표가 비슷한 상위 2~3개 조합과 기준 조합**에만 실행한다. 모든 조합에 같은 순서로 같은 명령을 쓴다.

| 순서 | 명령 (저장소 루트, `<tag>` = 조합 이름) | 출력 |
|---|---|---|
| ① 답변 생성 | `python -m src.eval.run_answer_eval --tag <tag> --questions eval/answer_eval_100_tiered.jsonl [--select-pool 16]` | `eval/answer_runs/<tag>/runs.jsonl` |
| ② LLM 채점 (필수 요지) | `python -m src.eval.judge_answers <tag> --questions eval/answer_eval_100_tiered.jsonl --mode tiered` | `judged_t.jsonl` |
| ② LLM 채점 (질문 중심) | 같은 명령에 `--mode question` | `judged_q.jsonl` |
| ② LLM 채점 (엄격) | 같은 명령에 `--mode strict` | `judged.jsonl` |
| ③ RAGAS 스타일 | `python -m src.eval.ragas_from_runs <tag> --retrieval eval/questions_100_retrieval.jsonl --questions eval/answer_eval_100_tiered.jsonl` | `ragas.jsonl` |

**뽑는 지표**

| 구분 | 지표 | 정의 |
|---|---|---|
| LLM 채점 | 정답 · 부분 · 오답 · 답못함 (질문 수) | 채점 모드 3종별로 각각. 주 채점은 `tiered`(필수 요지만 담으면 정답), `question`과 `strict`는 참고 |
| | 요지 충족률 | 정답 요지 항목별 충족 비율 (필수 · 보조 분리) |
| | 금지 내용 위반 수 | 금지 내용이 답에 들어갔거나 정답과 반대 단정 |
| | 답불가 질문의 거절 정확도 | 평가셋 `답가능여부` 칸 기준 |
| RAGAS | 충실도 (faithfulness) | 답변 문장 중 실제로 넘긴 근거에 있는 문장의 비율 |
| | 관련성 (answer relevancy) | 답이 질문의 요지를 다뤘는가 (0~1) |
| | 문맥 재현 (context recall) | 정답 근거 조문의 핵심 내용이 넘긴 근거 안에 있었는가 (0~1, 검색 정답이 있는 문항만) |
| 보조 | 보류율 | 코드 검사가 답을 막은 비율 |

**채점 규칙**
- **채점 모델은 하나로 고정**하고 후보 LLM(`qwen3.5:9b`, `qwen3:30b-a3b`)이 아닌 모델을 쓴다. 현재 설정은 `JUDGE_MODEL = gpt-5.6-luna`이며 가빈의 기존 결과(정답 29 · 부분 59 · 오답 4 · 답못함 8, 충실도 0.891 · 관련성 0.958 · 문맥 재현 0.702)와 같은 채점 모델이라 비교가 된다. 외부 API이므로 공개 규정 문장과 평가 질문만 보낸다.
- 채점은 **답을 만든 조합 이름을 모르게** 한다 (가빈 코드가 이미 그렇게 함).
- **채점 잡음**: 같은 답을 2회 채점해 판정이 바뀐 비율을 기록한다 (가빈 측정: 약 13%, 정답 ±2). 조합 간 차이가 이 잡음보다 작으면 동률로 쓴다.
- 답변 생성도 같은 조합을 2회 돌려 변동을 본다 (상위 조합만).
- 로컬 모델이 만든 답은 채점 모델이 luna여도 **채점은 동일 기준**이라 비교 가능하지만, 폐쇄망 안에서 채점까지 해야 한다면 로컬 채점 모델로 바꾼 별도 기준선이 필요하다 (이번 실험 범위 밖).

**비용·시간**: 질문 100개 기준 답변 100회 + 채점 3모드 × 100회 + RAGAS(질문당 여러 호출). 답변 단계 시간(첫 글자 · 답 완성)은 5.3절 방식으로 같이 기록한다.

## 6. 분석

| 분석 | 방법 |
|---|---|
| 단계별 탈락 지점 | 필수 근거를 못 얻은 이유를 후보 밖 / 리랭크에서 k 밖 / 선택에서 버림 / 확장 후 누락 / 색인 없음으로 분해 (조합별 누적 막대) |
| 요인별 효과 | 리랭커 값어치(R0 대 R1), LLM이 리랭커를 대신하는지(R0+선택 켬 대 R1+선택 끔), 선택의 추가 가치(켬 − 끔), R2 값어치(R2 대 R1), 임베딩 효과, LLM 효과 |
| 교호작용 | E × R, R × S, E × L |
| 부분집합 | 평가셋의 `유형`, `난이도`, `질문자`별 결과 |
| 효율-정확도 | 가로 시간 · 세로 주지표 산점도, 파레토 조합 표시 |

통계:
- 질문 단위 부트스트랩 구간으로 보고하고, 조합 간 차이는 같은 질문끼리 짝지어 비교(이진 결과는 McNemar).
- 같은 설정을 2회 반복해 변동 크기를 구하고, 그보다 작은 차이는 동률로 처리한다.
- 요인별 효과 중심으로 해석하고, 24개 조합의 순위 매기기는 피한다.
- 개발용으로 고르고, 시험용은 상위 2개 조합에 1회만 사용한다.
- 동률이거나 차이가 구간 안에 있으면 현행(E1 · R1)을 유지한다.

## 7. 질문별 저장 필드

`질문 id`, `조합(E, R, L, S)`, `바꿔 쓴 질문`, `후보 30개(순위, 점수)`, `리랭크 순서와 점수`, `선택된 노드`, `최종 근거 노드`, `단계별 필수 · 보조 적중 여부`, `답변`, `판정 라벨(채점 모드 3종)`, `RAGAS 3지표`, `단계별 시간(바꿔 쓰기 · 후보 · 리랭크 · 선택 · 확장, 초)`, `캐시 사용 여부`, `토큰 수(입력 · 출력)`, `오류 메시지`.

결과 파일은 입력 파일과 조합 이름으로 저장하고 덮어쓰지 않는다.

## 8. 산출물
