# 오류 원장 및 평가 라벨링

> **현재 상태**: 이 문서가 설명하는 Streamlit 라벨링 화면(왼쪽 메뉴 "RAG 평가셋 라벨링", "오류 원장 입력" 등)과
> `eval/error_ledger.jsonl` 오류 원장 워크플로우는 **이 저장소에 아직 포함되지 않았습니다.**
> 이 문서는 `feature/rag-eval-labeling` 브랜치의 설계·기준을 기록으로 남긴 것이고,
> 그 작업으로 만들어진 결과물인 `eval/questions.jsonl`(질문 277개)만 이 저장소에 가져왔습니다.
> 화면과 오류 원장을 가져올지는 별도로 판단합니다. 아래 내용은 그 화면이 들어올 때를 대비한 기준입니다.

Streamlit 실행:

```powershell
uv run streamlit run app/streamlit_app.py
```

왼쪽 메뉴 **RAG 평가셋 라벨링** 페이지에서는 `eval/questions.jsonl`의 질문을 추가·수정·삭제할 수 있다. 기존 평가 포맷 `{"q": "...", "유형": "내용|문서명|항번호", "정답": ["문서ID_조문ID"]}`을 유지하고, 선택 필드 `세부유형`을 추가로 둘 수 있다. 정답 조문은 한 개 이상 고를 수 있으며, 규정별 원문 조문을 검색해 여러 규정에서 근거를 추가할 수 있다. 화면은 선택한 조문의 ID와 원문 본문을 보여 준다. `out/chunks.jsonl`의 `본문`은 원문이며 검색용 보정 텍스트인 `본문_검색`은 라벨링에 사용하지 않는다. 저장 시 중복 질문·미존재 조문 ID·빈 정답·유형 오류를 검사한다. 기존 질문도 편집·삭제할 수 있고 전체 JSONL을 다운로드할 수 있다. 평가 실행기는 정답 ID가 PostgreSQL 색인에도 있는지 별도로 검사한다.

### 평가셋 구성 (2026-10-07 라벨링)

`eval/questions.jsonl`은 질문 277개다. 앞쪽 31개는 기존 질문이며 지우거나 고쳐 쓰지 않았다. 단, "직원채용지침에서 신입직원 채용 시 채용절차는 어떻게 되나요?"는 원래 정답(제2조 제1항, 적용범위)을 남긴 채 실제 채용절차 조문인 제2조 제2항(NCS 기반 채용절차)과 제5조 제1항(전형 순서)을 정답에 추가했다. "성과급은 어떤 기준으로 지급하나요?"는 규정명이 없어 성과급지급지침·급여규정도 답이 될 수 있지만, 정답 범위는 라벨 작성자가 정할 일이라 그대로 두었다. 나머지 246개는 90개 규정 원문 조문(`out/chunks.jsonl`의 `본문`)을 하나씩 읽고 규정마다 2~4개씩 만든 질문이다. 90개 규정 모두 평가 질문이 하나 이상 있다.

| 유형 | 새 질문 수 | 작성 기준 |
| --- | --- | --- |
| 내용 | 153 | 규정명 없이 실제 사용자 표현으로 묻는다 |
| 문서명 | 65 | 질문에 규정명을 넣는다 |
| 항번호 | 28 | 규정명 + 제○조 제○항 형태로 묻는다 |

선택 필드 `세부유형`은 정답 근거의 구조를 나타낸다. 값은 `단일조문`, `복수조문`(여러 조문이 함께 정답), `용어정의`(정의 조항이 근거), `조문간인용`(같은 규정의 다른 조문 참조), `문서간인용`(다른 규정 참조), `표·서식`(표·별표·별지 서식 근거) 중 하나다. 새 질문 246개에는 모두 붙어 있고, 기존 31개는 `미지정`으로 집계된다. 평가 실행기는 유형별 지표 아래에 세부유형별 지표도 출력한다.

라벨링 기준:

- 정답은 색인 대상 청크만 쓴다(`상태=정상`이고 부칙이 아닌 청크, `src/index/build.py`의 `is_indexed`와 같은 기준). 삭제 조문·부칙을 정답으로 저장하면 검증 오류가 난다.
- 규정명 없는 `내용` 질문에서 다른 규정에도 같은 내용의 조문이 있으면 그 조문도 정답에 넣는다. 예: 근로시간은 복무규정 제13조 제1항과 취업규칙 제13조 제1항, 회계연도는 회계규정 제3조와 정관 제42조, 고액현금거래 3영업일 보고는 두 자금세탁방지 내규.
- 원문의 오류(같은 항 번호 중복, 다른 수당을 말하는 문장, 잘못된 조문 인용 등)가 걸린 조문은 정답으로 쓰지 않았다. 예: 복지후생 운영지침 제9조 ⑤가 두 번 나오는 항, 전산업무지침 제14조가 인용한 정보보안관리지침 제30조. 이런 사례는 오류 원장에서 다룬다.
- 페이지의 **평가셋 구성과 규정별 커버리지**에서 유형·세부유형 분포와 질문이 없는 규정을 확인할 수 있다. 저장된 질문 목록은 유형·세부유형·규정·검색어로 거를 수 있다.

처음 열리는 **오류 원장 라벨링** 페이지는 DB 검색과 분리되어 있다. 원본 `한국벤처투자_내부규정` 폴더와 `out/text/{고유번호}.txt`를 사용하며, 현재 원본 90건(HWP 84, HWPX 3, PDF 3)을 찾는다. 원문 파일은 다운로드해 확인할 수 있다. 추출 텍스트의 파싱 실수는 원문 오류로 기록하지 않는다.

## 작업 화면

- **오류 원장 입력**: 한 문제당 한 행을 `eval/error_ledger.jsonl`에 저장한다. 위치는 원문 기준이며, `expected` 표시 형식과 `answer`는 처리 분류에 맞게 검증한다.
- **확인 대기열 판정**: `eval/review_queue.csv`가 있을 때 후보별 판정을 `eval/review_decisions.jsonl`에 별도 저장한다. 대기열 20%(올림)는 서로 다른 두 사람이 판정하며, 일치율을 별도로 계산한다. 정상은 정상, 애매는 두 번째 검토, 버그는 프로그램 버그 목록 대상이다. 단독 판정 오류는 오류 원장 행 작성으로 연결한다. 이중 판정 또는 추가 합의가 필요한 후보는 개별 판정만 보존하고, 합의 후 오류 원장에 한 행으로 등록한다.
- **독립 정밀 검토**: 담당 21건을 제외한 문서에서 무작위 조문 표본 묶음을 만든다. 묶음의 20%(올림)는 다른 검토자가 같은 표본 코드를 열어 독립 판정한다. 표본과 중복 검토 대상은 `eval/independent_sample_batch.json`에 보존한다. 이 화면은 RAG 청크·검색 결과·오류 원장·`corrections.json`을 표시하지 않는다. 검토 범위와 문제가 없는 조문도 `eval/independent_review.jsonl`에 남긴다. 추가 합의가 필요한 오류 발견은 개별 finding을 독립 기록에 보존하고, 합의 후 오류 원장에 한 행으로 등록한다.

원장 필드: `id`, `reg_id`, `unit`, `article`, `para`, 선택적 `para_note`, `quote`, `type`, `handling`, `answer`, `basis`, 필수 `expected`, `source`, `judge`, `date`, 선택적 `link`와 `group`.

원본을 덮어쓰거나 수정하지 않는다. 인용 `quote`는 원문 그대로 복사하고 저장 전에 원본 파일을 직접 확인한다. JSONL은 UTF-8로 저장되며 라벨 파일은 RAG 질문 데이터 `eval/questions.jsonl`과 별개다.

확인 대기열 CSV의 기본 위치는 `eval/review_queue.csv`다. 권장 헤더는 `candidate_id,reg_id,unit,article,para,quote,basis,type`이며 추가 열은 후보 미리보기에 보존된다.

현재 로컬 라벨 파일에는 팀 공용 잠금·동시 편집 조정이 없다. 여러 사람이 동시에 같은 로컬 파일에 쓰지 말고, 검토 ID와 판정자 이름을 유지한 채 팀의 공유 저장 방식에서 병합한다.
