# 답변 설계 (④ 단계)

검색된 근거로 질문에 답하는 단계를 정리한다.
근거를 찾는 과정은 `검색_설계.md`, 화면과 실행 방법은 아래 6절을 본다.

**기준일: 2026.10.06**
**상태: 1차 구현 완료, 검증 전**

---

## 1. 흐름

```
질문 → Searcher.search() → Searcher.assemble() → 근거 번호 부여 → OpenAI 모델 → 인용 검사 → 답변
```

- `src/answer/pipeline.py`의 `Assistant.ask()`가 전체를 묶습니다.
- 근거가 0개면 모델을 부르지 않고 고정 문구로 답합니다.

---

## 2. 모델

| 항목 | 값 |
|---|---|
| 모델 | `gpt-4o-mini` (`config.py`의 `OPENAI_MODEL`) |
| API | OpenAI Responses API (`client.responses.create`) |
| 키 | 프로젝트 상위 폴더의 `.env` (`OPENAI_API_KEY`). Git에서 무시됨 |

모델을 바꾸려면 `OPENAI_MODEL`만 고칩니다. 이전에는 `gpt-5.1`로 확인했고, 품질 비교는 골든셋 이후입니다.

---

## 3. 근거 형식

모델에는 근거를 번호와 함께 넘깁니다.

```
[1] 급여규정 제17조 제1항 | 조문상태: 현행 | 개정: 2025년도 ...
(본문)
정정안내: ... (있을 때만)
```

- 번호는 답변의 `[n]` 인용과 같습니다.
- 근거 순서는 검색 결과(정확 조회 → 검색) → 인용 대상 → 형제 항입니다. 세부 규칙은 `검색_설계.md` 0.3절을 봅니다.

---

## 4. 답변 규칙

시스템 지시(`SYSTEM_PROMPT`)로 요청한 규칙입니다.

| 규칙 | 내용 | 강제 여부 |
|---|---|---|
| 근거 한정 | 제공된 근거에 있는 내용만 쓴다 | 지시만 (보장 안 됨) |
| 없음 | 근거가 질문에 답하지 못하면 "제공된 규정에서 확인되지 않습니다"라고 쓰고 담당 부서 확인을 안내한다 | 지시만. 검사 코드 없음 |
| 인용 | 문장마다 `[n]`을 붙인다 | 인용 번호 검사만 함 |
| 부칙 | "현행 기준이 아님"으로 밝힌다 | 지시만 |
| 삭제 | "삭제된 조항입니다"로 밝히고, 현행 기준으로 말하지 않는다 | 지시만 |
| 정정안내 | 근거에 있으면 답변 끝에 "※ 정정 안내"로 붙인다 | 지시만 |
| 충돌 | 근거끼리 다르면 둘 다 보여주고 판정하지 않는다 | 지시만. 판정 로직 없음 |
| 외부 법령 | 근거가 아니다 | 지시만 |

### 4.1 자동으로 검사하는 것
- 답변이 근거 범위 밖의 번호(`[9]`처럼 없는 번호)를 쓰면 경고합니다.
- 답변에 인용이 하나도 없는데 "확인되지 않습니다"도 없으면 경고합니다.

### 4.2 구현됨 (점수 구간, 충돌 표시)
- **점수 구간** (`config.py`, 임시값): 1위 리랭커 점수가 0.3 미만이면 `none`, 0.3~0.6이면 `partial`, 0.6 이상이면 `answer`.
- **충돌**: 근거가 2개 이상이면 모델에게 "서로 다른 내용을 말하는 조문 쌍"만 JSON으로 찾게 합니다. 찾은 쌍은 화면에서 위계와 개정일과 함께 나란히 보여줍니다. 판정은 하지 않습니다.
- **정확 조회**: 조문이 확정된 경우에는 점수 구간을 적용하지 않습니다.

### 4.3 아직 없는 것
- **충돌의 자동 판정 (위계 우선, 개정일 우선)**: 보류. 판정 기준은 사용자가 정해야 하고, 지금은 표시만 합니다.
- **인용 내용 검사**: 답변 문장이 인용한 조문의 내용과 맞는지 확인하는 기능.
- **임계값 조정**: 평가셋 이후 (7절).

## 7. 점수 구간과 출력 형식

### 7.1 구간 (2026.10.07 재보정)

| 1위 리랭커 점수 | 모드 | 답변 방식 | 모델 호출 |
|---|---|---|---|
| 0.05 미만 | `none` | "이 질문과 관련된 내용을 찾을 수 없습니다. 담당 부서에 확인해 주세요." | 안 함 |
| 0.05 이상 | `answer` | 모델이 근거 범위 안에서 답변 | 함 |
| (정확 조회 포함) | `answer` | 기준을 적용하지 않음 | 함 |

- 임계값은 `config.py`의 `ANSWER_NONE_BELOW`(0.05), `ANSWER_PARTIAL_BELOW`(0.05, `NONE_BELOW`와 같은 값)에 있습니다. 두 값을 같게 둬서 `partial`(점수만 보고 고정 문구로 답하던 중간 구간)이 사실상 비활성화됩니다. 코드(`decide_mode`)는 그대로 두고 값만 바꿨습니다.

**바꾼 이유**: 처음 정한 0.3/0.6은 질문 35개(대부분 정답을 보고 만든 질문)로 잡은 값이었습니다. 이후 진짜 블라인드 질문(v3)으로 실제 점수 분포를 보니, **"답 있음"과 "답 없음" 질문의 점수가 0.03~0.6 구간에서 크게 겹쳐서 점수 하나로는 못 가른다**는 것을 확인했습니다 (예: "없음" 질문이 0.602, "있음" 질문이 0.015인 경우도 있었음). 그래서 확실히 아무것도 없는 구간(0.05 미만)만 막고, 그 위는 모델 판단(`SYSTEM_PROMPT`의 "답할 수 없으면 찾을 수 없었다고 써라" 규칙)과 사후 검사(10절 `verify()`)에 맡기기로 했습니다. 자세한 점수 분포와 검색_설계.md의 측정 과정은 PR #2를 참고합니다.

**효과 (v3, 질문 16개 "답 있음" 기준, 재보정 전 → 후)**

| 지표 | 전(0.3/0.6) | 후(0.05) |
|---|---|---|
| answer 모드로 실제 답한 질문 | 10/16 | **16/16** |
| LLM-judge 평균 정확성 | 2.31/5 | **3.38/5** |
| LLM-judge 근거충실 위반 | 10/16 | **6/16** |
| context_recall (RAGAS 스타일) | 0.17 | **0.40** |

**남은 위험**: "답 없음" 질문(v3_edge, 19개) 중 점수로 자동 차단되는 것이 6개로 줄었습니다(전에는 더 많았음). 나머지 13개는 이제 모델이 답을 시도합니다. 직접 확인해 보니 그중 일부는 **제가 "없음"으로 잘못 라벨링했던 것**(예: "휴가 신청 며칠 전"은 실제로 복무규정 제20조에 있었음)이었지만, **"명절 상품권"처럼 완전히 다른 주제의 조문(대외 접대 금지 규정)을 갖다 붙여 오답을 만든 진짜 문제 사례**도 있었습니다. 13개를 전부 검토하지는 못했습니다 — 다음 작업 후보입니다.

### 7.2 출력 형식 (`SYSTEM_PROMPT`)

1. 첫 문장: 결론 (근거 번호 포함)
2. 세부 내용: 불릿, 최대 5개, 각 불릿 끝에 [n]
3. 부칙이나 삭제 조문을 썼으면: "※ 참고: [n]은 부칙(현행 기준 아님)입니다" 또는 "※ 참고: [n]은 삭제된 조항입니다"
4. 정정안내가 있으면: "※ 정정 안내: …"
5. 길이: 기본 3~5문장

### 7.3 충돌 표시

- 근거가 2개 이상이면 모델에게 충돌 쌍만 JSON으로 묻습니다 (`CONFLICT_PROMPT`).
- 쌍이 있으면 화면에 "⚠ 같은 주제의 조문이 서로 다른 내용을 말합니다"와 두 조문을 나란히 보여줍니다. 위계와 개정일은 문서에 적힌 사실이라서 함께 보여줍니다.
- **확인되지 않은 것**: 충돌 탐지가 실제로 충돌을 찾는지 아직 검증하지 않았습니다. 이사회 질문에서는 쌍이 찾아지지 않았는데, 충돌이 없는 것인지 놓친 것인지는 평가셋에서 확인합니다.

### 7.4 근거 순서와 참고 문구 (구현 완료)

- **근거 순서**: 현행 조문을 먼저 모델에게 넘기고, 부칙·삭제는 뒤로 보냅니다. 번호도 이 순서를 따릅니다.
- **참고 문구는 코드가 만듭니다**: 부칙·삭제 근거를 인용했을 때 "※ 참고: [n]은 …"을 답변 끝에 붙입니다. 모델이 번호를 잘못 붙이는 일을 막기 위해서입니다. 정정 안내도 같은 방식입니다.
- **모델에게 주지 않는 정보**: 문서의 개정표기는 모델에게 넘기지 않습니다. 모델이 개정일을 조문의 삭제일로 잘못 읽은 적이 있어서입니다. 화면에는 그대로 보여줍니다.
- **지시 강화**: 근거에 없는 일반 조언을 붙이지 않고, 날짜는 근거 본문에 적힌 것만 쓰고, "결론:" 같은 머리말을 쓰지 않습니다.
- **남은 문제**: 근거 밖 문장을 완전히 막지는 못합니다. 예: "포인트 관련 규정은 직위해제와 관련이 없습니다" 같은 판단을 모델이 덧붙이는 경우가 있습니다. 평가셋에서 확인합니다.

## 8. 프롬프트 (코드와 같은 내용)

프롬프트는 `src/answer/generate.py`에 있습니다. 이 절은 **현재 프롬프트 전문**입니다. 프롬프트를 고치면 코드와 이 절을 같이 고칩니다.

### 8.1 답변 프롬프트 (`SYSTEM_PROMPT`)

```
너는 한국벤처투자 내부규정을 설명하는 도우미다. 아래 규칙과 출력 형식을 반드시 지킨다.

[규칙]
1. 제공된 근거([1], [2] …)에 적힌 내용만 사용한다. 근거에 없는 내용은 추측하지 않는다.
2. 문장마다 근거 번호를 [1]처럼 붙인다. 여러 근거면 [1][2]처럼 붙인다.
3. 근거의 규정 이름, 조, 항은 표기를 그대로 쓴다. 새로 만들지 않는다.
4. 근거끼리 내용이 달라도 어느 쪽이 맞는지 판정하지 않는다. 각 근거의 내용을 번호와 함께 적는다.
5. 근거가 질문의 핵심에 답하지 못하면, 답할 수 있는 부분만 말하고 나머지는 "찾을 수 없었습니다"라고 쓴다.
6. 근거에 없는 일반 조언이나 예측을 덧붙이지 않는다. 예: "논의가 필요합니다", "달라질 수 있습니다" 같은 문장은 근거에 적혀 있을 때만 쓴다.
7. 근거는 번호순으로 현행 조문이 먼저 나온다. 현행 근거로 먼저 답하고, 부칙이나 삭제 근거는 답의 근거로 쓰지 않는다.
8. 부칙·삭제 여부와 정정 안내는 답변에 쓰지 않아도 된다. 시스템이 따로 붙인다.
9. 날짜는 근거 본문에 적힌 날짜만 쓴다. "개정" 표기는 문서 전체의 개정일이지 조문의 시행일이나 삭제일이 아니다.

[출력 형식]
- 첫 문장: 결론을 바로 문장으로 쓴다 (한두 문장, 근거 번호 포함). "결론:" 같은 머리말을 붙이지 않는다.
- 이어서 세부 내용을 불릿으로 쓴다. 최대 5개. 각 불릿 끝에 [n].
- 길이: 기본 3~5문장. 조문 원문을 길게 옮기지 않는다.
```

### 8.2 충돌 확인 프롬프트 (`CONFLICT_PROMPT`)

```
아래 근거 중에서, 같은 주제를 다루면서 서로 다른 내용을 말하는 조문 쌍을 찾는다.
- 출력은 JSON 배열만 쓴다. 예: [[1, 3]]
- 쌍이 없으면 []만 쓴다.
- 같은 내용을 반복하는 조문은 충돌이 아니다. 주제가 다르면 충돌이 아니다.
- 설명은 쓰지 않는다.
```

### 8.3 모델에게 넘기는 근거 형식

```
[1] 급여규정 제17조 제1항 | 조문상태: 현행 | 위계: 규정
(본문)
정정안내: ... (있을 때만)
```

- 개정표기는 넘기지 않습니다. 모델이 문서 개정일을 조문 날짜로 잘못 읽은 적이 있어서입니다.
- 근거 순서는 현행 먼저, 부칙·삭제는 뒤입니다.

### 8.4 코드가 붙이는 문구 (모델이 쓰지 않음)

- 부칙 근거를 인용했을 때: `※ 참고: [n]은 부칙 조항이라 현행 기준이 아닙니다.`
- 삭제 근거를 인용했을 때: `※ 참고: [n]은 삭제된 조항입니다.`
- 정정안내가 있는 근거를 인용했을 때: `※ 정정 안내 [n]: …`
- 애매함 구간과 없음 구간의 문구는 `pipeline.py`의 `partial_answer()`와 `NONE_MESSAGE`에 있습니다 (7절).

## 9. LangChain 전환 (구현 완료, 2026.10.07)

처음에는 보류했지만, 이후 다시 결정해서 전환했습니다. **알고리즘을 바꾼 것이 아니라 인터페이스만 LangChain 형식으로 감쌌습니다.**

- **검색**: `src/search/langchain_retriever.py`의 `RegulationRetriever(BaseRetriever)`가 기존 `Searcher.search()`를 그대로 호출하고, 결과를 LangChain `Document`로 바꿔 돌려줍니다. 정확 조회, 가중 RRF, 리랭킹, 필터, 형제 항·인용 확장 로직은 전혀 바뀌지 않았습니다.
- **답변**: OpenAI SDK를 직접 부르던 것을 `ChatOpenAI`(LangChain)로 바꿨습니다 (`src/answer/generate.py`).
- **추적**: `.env`에 `LANGCHAIN_API_KEY`가 있으면 LangSmith 추적이 자동으로 켜집니다 (`LANGCHAIN_TRACING_V2`).
- 프롬프트와 규칙은 8절과 동일합니다. LangChain은 호출 방식만 바꿨습니다.

## 10. 문장 단위 근거 검사 (구현 완료, 평가 전)

답변의 각 불릿이 인용한 근거 본문과 실제로 맞는지, 별도 모델 호출로 다시 확인합니다 (`Generator.verify`, `VERIFY_PROMPT`).

- 입력: 질문, 모델이 쓴 답변 전체, 근거 전문
- 출력: 근거에 없는 내용을 담은 불릿 문장 목록 (JSON 배열). 모두 맞으면 `[]`
- 결과는 답변을 고치지 않고 **경고로만** 붙입니다 (`result["warnings"]`, `result["unsupported"]`). 화면에서 경고로 보여줍니다.
- 확인된 사례: "직위해제된 직원은 매월 15일을 기준으로 월할 계산이 이루어질 수 있습니다"라는 문장을 근거 밖이라고 정확히 잡았습니다.
- **한계**: 모델 호출이 하나 더 늘어서 비용과 시간이 늘어납니다. 검사 자체도 모델이 하므로 완벽하지 않습니다. 놓치거나 과하게 잡을 수 있습니다.
- **측정 전**: 골든셋이 없어서 이 검사가 실제로 얼마나 정확한지는 아직 모릅니다. 골든셋에 "근거 밖 문장이 포함된 질문"을 넣어서 확인해야 합니다.

### 10.1 충돌 탐지 보완

같은 문서의 같은 조에 속한 서로 다른 항은 충돌 후보에서 미리 제외합니다 (`pipeline.py`의 `_same_article`). 같은 조의 항들은 서로 보완하는 내용이지 충돌이 아니기 때문입니다.

또한 `CONFLICT_PROMPT`에 "같은 단어를 쓰지만 다른 것을 규정하면 충돌이 아니다"를 구체적인 예시와 함께 넣었습니다. 처음에는 "감사의 종류"(감사규정 제5조)와 "감사의 직무"(직제규정 제5조, 정관 제30조)를 충돌로 잘못 잡았습니다. 둘 다 "감사"라는 같은 단어를 쓰지만 다른 질문(종류 vs 직무)에 대한 답이라서 충돌이 아닙니다. 지시를 구체적인 예시로 고친 뒤에는 잡히지 않았습니다.

## 11. 답변 품질 평가: LLM-as-a-Judge, RAGAS 스타일 지표 (구현 완료, 2026.10.07, PR #2)

검색 품질(Hit@k, MRR)과 별개로, **최종 답변의 품질**(정확한가, 질문에 실제로 답했는가, 근거 밖 얘기를 안 했는가)을 재는 두 가지 평가를 추가했습니다. 둘 다 "모델이 답을 채점하는" LLM-as-a-Judge 방식입니다.

### 11.1 평가셋에 대한 중요한 전제

세 가지 질문 세트가 있고, 성격이 다릅니다.

| 세트 | 개수 | 만든 방법 | 신뢰도 |
|---|---|---|---|
| v1 (`questions.jsonl`) | 277 | **조문 원문을 보면서** 만듦 | 검색 성능 측정엔 유용하지만 점수가 쉽게 나옴 (천장 효과) |
| v2 (`questions_v2.jsonl`) | 12 | 제가(Claude, 같은 세션) 만듦. 원문을 다시 읽진 않았지만, 이미 이 저장소를 많이 읽은 상태라 **완전한 블라인드가 아님** | 참고용 보조 세트 |
| v3 (`questions_v3.jsonl` + `questions_v3_edge.jsonl`) | 16(답 있음) + 19(답 없음/부분) | **원본 규정 파일을 전혀 열어본 적 없는 별도 세션**이 만듦 | **진짜 블라인드. 이 절의 기준 세트** |

처음에는 v2와 v3를 "블라인드 세트"로 합쳐서 측정했는데, v2가 진짜 블라인드가 아니라는 게 확인되어 **v3만으로 다시 측정**했습니다. 아래 수치는 모두 v3 기준입니다. v2는 섞지 않습니다.

### 11.2 LLM-as-a-Judge (`src/eval/judge.py`)

**측정 항목 (질문당)**
- **정확성 (0~5)**: 답변이 정답 근거(정답으로 라벨링된 조문 + 같은 조의 다른 항)의 내용과 실제로 맞는지. 모델에게 질문·답변·정답 근거를 주고 점수와 이유를 JSON으로 받습니다.
- **근거충실 위반 (true/false)**: 답변이 **실제로 검색되어 쓰인 근거**에 없는 내용을 말했는지. `Generator.verify()`(10절)와 역할이 비슷하지만, judge는 평가 파이프라인에서 독립적으로 다시 채점합니다.

**정답 근거를 넓힌 이유**: 처음엔 라벨링된 조문 하나만 정답 근거로 썼는데, 시스템이 **같은 조의 다른 항**(형제 항)을 같이 인용하면 "근거충실 위반"으로 잘못 잡혔습니다. 예를 들어 질문의 정답이 제5조 제1항인데 시스템이 제5조 제2항도 같이 썼다면, 이건 위반이 아니라 정상적인 확장입니다. 그래서 `judge.py`는 정답 조문의 **형제 항까지 포함**해 정답 근거를 구성합니다 (`store.siblings()` 사용).

**결과 (v3, 질문 16개 "답 있음" 기준)**

| 시점 | 평균 정확성 | 근거충실 위반 |
|---|---|---|
| v2+v3 섞어서 측정 (방법 오류, 폐기) | 3.29/5 | - |
| v3만, 임계값 재보정 전(0.3/0.6) | 2.31/5 | 10/16 |
| v3만, 임계값 재보정 후(0.05) | **3.38/5** | **6/16** |
| v3만, 프롬프트 규칙 10 추가 후(주제 혼동 방지) | 3.31/5 | 8/16 |

마지막 줄(프롬프트 규칙 추가 후)이 재보정 직후보다 살짝 낮아진 것은, 표본이 16개뿐이라 **개별 질문 1~2개가 바뀌면 평균이 흔들리는 노이즈 범위**입니다. 통계적으로 유의한 개선이라고 주장하지 않습니다. 다만 "겸직" 질문처럼 **다른 대상(임원 vs 직원)의 규정을 섞어 쓰던 자기모순 사례**는 개별적으로 확인했을 때 고쳐졌습니다.

**재보정 전(0.3/0.6) "근거충실 위반 10/16"의 실제 내용**: 10건 전부가 할루시네이션(지어낸 근거)은 아니었습니다. 그중 **9건은 "원래 답이 있는 질문인데 점수 임계값에 걸려 `none`(모름) 모드로 빠져서 근거 자체가 아예 없었던 경우"**였고, 진짜로 틀린 근거를 지어낸 경우는 1~2건(예: "인수인계 기간을 2일"이라고 사실과 다르게 말함)뿐이었습니다. 이 구분이 재보정(7.1절)의 직접적인 근거였습니다 — 문제의 대부분이 "모델이 틀리게 답한 것"이 아니라 "답할 수 있는데 못하게 막아둔 것"이었기 때문입니다.

**Hit@10(0.81)과 평균 정확성(2.31/5, 재보정 전)이 왜 이렇게 다른가**: Hit@10은 "검색이 정답을 찾았는가"만 봅니다. 정확성은 "최종 답변이 좋은가"를 봅니다. 검색은 찾았어도 리랭커 점수가 임계값보다 낮으면 모델이 그 근거를 쓰지도 못하고 "모르겠다"고 답했기 때문에, 검색 지표와 답변 품질 지표 사이에 큰 차이가 생겼습니다. 이 간극이 바로 7.1절 재보정의 동기입니다.

- 재현: `uv run python -m src.eval.judge`

### 11.3 RAGAS 스타일 지표 (`src/eval/ragas_style.py`)

실제 `ragas` 패키지는 쓰지 않았습니다. `ragas>=0.2`는 `langchain-core<1.0`을 요구하는데, 이 프로젝트는 이미 `langchain-core>=1.6.7`로 전환되어 있어(PR #1) 직접 충돌합니다(설치 시도로 확인). 구버전(`ragas==0.0.22`)은 설치는 되지만 `langchain.callbacks` 모듈이 최신 LangChain에서 제거되어 임포트 시 바로 깨집니다. 그래서 **지표 정의만 가져와서** 우리 데이터·프롬프트로 가볍게 구현했습니다.

**측정 항목 (0~1, 모두 LLM 채점)**
- **충실도 (faithfulness)**: 답변의 문장(또는 불릿) 중 몇 개가 실제로 쓰인 근거에서 나왔는지의 비율. `judge.py`의 근거충실과 비슷하지만 true/false가 아니라 비율로 봅니다.
- **관련성 (answer_relevancy)**: 답변이 질문의 요지를 실제로 다뤘는지. 내용이 맞는지는 안 보고, "동문서답인지"만 봅니다. "모른다"고 솔직히 답한 경우도 회피가 아니므로 관련성은 높게(0.8~1.0) 줍니다.
- **문맥재현 (context_recall)**: 정답 근거(조문 전체)의 핵심 내용이 **검색 단계에서 가져온 근거** 안에 들어 있었는지. 답변에 그 내용을 썼는지는 안 보고, 검색이 그 내용을 찾아왔는지만 봅니다.

**결과 (v3, 질문 16개 "답 있음" 기준)**

| 시점 | 충실도 | 관련성 | 문맥재현 |
|---|---|---|---|
| v2+v3 섞어서 측정 (방법 오류, 폐기) | - | - | 0.29 |
| v3만, 임계값 재보정 전(0.3/0.6) | 0.84 (n=5) | 0.86 (n=16) | 0.17 (n=9) |
| v3만, 임계값 재보정 후(0.05) | - | - | **0.40** |
| v3만, 프롬프트 규칙 10 추가 후 | - | - | 0.00 (n=3) |

`n`은 그 지표를 실제로 계산할 수 있었던 질문 수입니다. 충실도·문맥재현은 답변이 `answer` 모드로 근거를 쓴 경우에만 계산되므로, 재보정 전에는 16개 중 5~9개만 해당됐습니다(나머지는 `none`/`partial` 모드라 "근거"가 없어서 측정 대상에서 빠짐). 관련성은 모드와 관계없이 모든 질문(질문에 답을 시도했든, "모르겠다"고 했든)에 대해 계산되므로 n=16입니다. 마지막 줄(프롬프트 규칙 추가 후)은 n=3이라 대표성이 없어 참고 수치로만 남깁니다.

**해석**: 관련성은 꾸준히 높고(모델이 "모른다"고 솔직히 답함), 문맥재현은 낮습니다(0.17~0.40). 이 조합이 의미하는 것은 — **모델이 거짓으로 답을 지어내지는 않지만, 검색이 정답 근거를 충분히 못 찾아오고 있다**는 것입니다. 답변 프롬프트를 더 고쳐도 한계가 있고, **검색 단계(Hit@10이 16개 중 3개를 놓침, 검색_설계.md 0.1절 v3 표)** 개선이 더 중요한 다음 단계입니다.

- 재현: `uv run python -m src.eval.ragas_style`

### 11.4 두 평가의 공통 한계

- **표본이 작습니다 (16개).** 개별 질문 1~2개의 결과가 평균을 크게 흔듭니다. 추세("재보정 후 나아졌다")는 믿을 수 있지만, 소수점 둘째 자리까지의 차이를 근거로 삼지 않습니다.
- **채점자도 LLM입니다.** `judge.py`, `ragas_style.py` 모두 `gpt-4o-mini`로 채점하므로, 채점 자체의 오차가 있습니다. 사람 검증은 하지 않았습니다.
- **다음 작업 후보**: 더 많은 블라인드 질문 확보(다른 팀원에게 받기), 검색 단계에서 놓친 3개 질문(출장비, 성과급, 의무교육) 원인 분석.
